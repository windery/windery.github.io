# 日报语言风格固化方案

状态：2026-10-17 已按本方案的单刊 v2 版本接入生成规则与发布校验；四篇独立文章后置。文中六字段已改为内部核对项，正文使用自然段。

## 目标与参照

四篇继续独立产出。共同的语言目标是：主体明确、结论直接、解释具体、证据可追溯、自然段连贯，读者能据此理解事件、项目或方法。

以 `docs/daily-review/2026-10-16/` 的四篇真实稿作为 v1 语言参照。它们是写法参照，不作为后续新闻、价格、功能或榜单数据的来源。此前虚构样例仅保留为失败对照。

## 一、保存认可稿，建立唯一规范

落地时增加以下材料，避免把完整规则重复复制到多个提示词中：

- `.agents/skills/ai-daily/editorial-style.md`：唯一权威写作规则，约一至两页，含通用规则与四篇各自的重点。
- `.agents/skills/ai-daily/references/style-v1/`：保留本次获认可的四份稿件快照，附认可范围和版本清单。后续改稿不自动覆盖这个参照版本。
- 现有 `SKILL.md`：增加明确的加载步骤，指向规范与本次要写的文章类型对应的参照稿。

定时任务只引用同一 skill 和规范路径，不维护第二份写作规则。首次接线时检查现有旧版编辑要求，清理“六字段逐条展示”等冲突；必要信息继续核对，但不强制在正文机械列字段。

## 二、把风格写成可执行的编辑规则

| 维度 | 每次怎样写 | 怎样审 |
|---|---|---|
| 主体 | 标题或首段写明厂商、产品、项目或作者的名称，随后才使用代词 | 单看标题和导语，能说出谁做了什么 |
| 开头 | 直接给本篇最重要的事实或结论，接着交代相关场景 | 删除开头后若信息没有减少，重写开头 |
| 解释 | 用具体机制、步骤、代码行为或案例解释“为什么” | 换成另一个项目名仍成立的段落，需要补具体内容或删除 |
| 段落 | 一段推进一个意思，句子之间说明因果、过程或条件 | 清单只用于步骤、对比、榜单和选题卡，不把整篇写成字段表 |
| 术语 | 保留准确术语，首次需要时用一句话解释 | 解释服务于理解本文，避免旁逸到大段基础科普 |
| 判断 | 先给依据，再给与证据强度匹配的结论；编辑建议明确归属 | 厂商宣传、作者体验、代码观察与本站实测没有混用 |
| 限制 | 在对应结论附近写具体边界，同一限制集中说明 | “未实测”等声明没有在每段重复，也没有代替实质信息 |
| 来源 | 链接贴近其支持的事实，数据保留口径与时间 | 读者能从该链接核实相关主张，来源不是孤立堆在文末 |
| 来源元信息 | 简写为“原文发布日期 · 来源名称：链接” | 采集窗口、时区换算、覆盖数量、核查过程及试写说明保存在内部记录，不进入文章正文 |
| 标题与强调 | 标题表达对象与内容，加粗只突出关键结论或条件 | 不用“重磅”“颠覆”等热度词替代事实 |
| 收尾 | 给与本文相关的适用条件、实际入口或来源说明 | 不附一段可套用到任何文章的“值得关注”总结 |

不固定每段长度、小标题数量或每篇字数。材料少就短，复杂机制允许展开；风格一致不要求文章形状相同。

日期默认采用原文标注的发布日期；精确时间和时区换算留在内部核查记录。用户要求的简洁来源标注取代早期稿件长段“来源与时效”说明。直接影响理解的产品条件或证据边界仍在相关叙述中简短说明，不扩写成采编报告。

### 对照示例

- 未通过：“一个主流模型家族完成换代。”
- 认可方向：“GitHub 在 10 月 15 日正式推出两项代码安全能力：AI Scan……，agentic autofix……。”主体和变化都具体。
- 未通过：“这个工具很有潜力，值得开发者关注。”
- 认可方向：先解释 TokenSpeed 的请求状态、缓存引用和执行计划，再说明适合自托管模型的团队。
- 未通过：“作者分享了一套高效的 AI 工作流。”
- 认可方向：写明 Simon 先开本地预览、用语音修正展示规则，再用键盘把 Git 子进程导入改成 API。

上述示例只说明写法，未来引用其事实时仍需重新核对。

## 三、每次按同一过程生成

1. **准备材料。** 先整理具名主体、日期、关键事实、证据链接及不确定处；工具篇还要有源码版本与关键实现。材料不足时缩小范围或跳过，不能靠修辞补内容。
2. **加载参照。** 读取统一规范和对应类型认可稿。只借鉴叙述方式，不复用旧稿中的事实与结论。
3. **写稿。** 先完成连贯正文，再安排必要的小标题、列表与来源。
4. **事实审查。** 对照材料逐项核对主体、数字、时效、因果和归属。发现不支持的主张先修正事实。
5. **语言审查。** 对照认可稿检查空泛开头、解释不足、清单堆砌、限制重复和通用结尾。指出具体句段并改写，不只输出“通过”。改写新增事实时回到事实审查。
6. **保存审核记录。** 记录使用的规范版本、认可稿版本、发现的问题和修改结果。它不进入读者正文；未解决的重要事实或明显风格问题使该篇不能进入交付阶段。

事实审查与语言审查是两个独立步骤，可以由同一任务依次完成，不要求另起多个 Agent。

## 四、哪些可以自动检查

确定性检查适合覆盖：文件与栏目结构、占位词、来源链接缺失、版本记录、项目重复、榜单快照状态等。字段齐全不等于事实正确。

主体是否清楚、解释是否具体、语言是否连贯需要内容审查。自动检测泛词只能提示，不能单凭禁词或字数宣布文风合格。不设计一个“风格分数”替代逐段判断。

## 五、用新材料验证，再固定版本

接线后用三种真实输入做不发布演练：新上榜项目、持续在榜但未讲过的项目、没有未讲项目的榜单。检查选题行为及不同材料下的语言一致性；另从保留的新闻、方法和口播各检查一份新稿，避免只验证工具篇。

对有正文的输入，重点检查主体是否清晰、能否说出项目独有内容、限制是否克制、是否无需另读文章即可理解。仅列表的输入检查用途描述是否具体、数据是否可追溯，不为凑结构补正文。

第一轮演练由用户看实际稿件，确认后冻结 style-v1。后续用户明确提出的风格修正先归纳为一条规则并附改写例，再升级版本；不因某次生成稿偏离而反过来修改参照。

这能显著减少漂移，但不能保证生成文本每次绝对一致。可执行的保证是每次加载同一标准、用同一标准检查、发现不合格内容先修正再交付。

## 工具篇：已确认的新选题规则

- 只从当日 GitHub 全语言 Trending 日榜里的 AI 项目中选择正文对象；不再额外挑未上榜的成熟高星项目。
- 每天至多讲一个，已在正式日报正文介绍过的项目永久跳过，即使后来有重大更新。历史旧版正文介绍也计入；只在热榜列表出现不计入。
- “新上榜”指今天在榜、上一次成功采集的同口径榜单里没有。先选新上榜且未讲的，再选持续在榜但未讲的；这不是声称该项目历史上首次登榜。
- 本次 TokenSpeed 审阅稿暂不计入已讲记录；正式采用后才计入。
- 没有未讲项目时只发榜单。仍沿用证据门槛：有未讲项目但无法充分核实，也可只发榜单，并在内部记录原因。
- 榜单保留最多十项，沿用当前排序与字段；跨日可重复，正文已深挖对象同日不重复列出。

实施时采用项目稳定身份记录历史，同时保留名称及更名记录，避免改名或转移后被误当作新项目。榜单读取失败不算“今天没有新项目”，也不覆盖上一份成功快照；首次运行只建立观察基线，可从未讲的在榜项目选取，但不称为新上榜。发布失败不提前标为已讲，重试复用当次选择，避免同一天另选项目。
