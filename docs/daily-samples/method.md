# 每日方法｜先写失败案例，再让 Agent 改代码

> 虚构结构样例，仅供评审。模型、项目、事件与文章均非真实采集结果；未核查代码或实测，来源位置为占位。不可直接发布。

原文位置：一篇近 30 天内、此前未精读过的博客。此处为虚构文章的方法演示，不归属于任何真实作者。

## 今天为什么选它

它给出一个可以迁移到日常开发的步骤：把“看起来没问题”的主观判断，改成独立于实现的验收证据。读者今天就能在一个小任务中尝试，而不必先引入一套庞大框架。

## 核心方法

动手前，先描述一次真实操作和预期结果，再补充一个容易失败的边界条件。例如开发导出功能时，除了检查正常文件，还应明确空数据怎样处理、导出内容是否泄露无权查看的字段。

这份验收约定应来自需求，而不是根据 Agent 已写出的实现倒推。否则实现与检查可能共享同一个错误理解，得到“全部通过”的假象。

## 如何用在自己的任务里

1. 选择一个边界明确的需求，写清用户输入、操作和可观察结果。
2. 补一个关键失败场景，并说明系统应怎样响应。
3. 让 Agent 实现功能，同时保留原先的验收约定。
4. 按真实操作检查结果；失败时记录触发条件，反馈给 Agent 修正。
5. 交付时保留结果证据，并说明尚未覆盖的场景。

## 哪些地方不能照搬

开放式写作或视觉设计难以全部变成自动判断，仍需要人的审美与取舍。自动检查也只能证明所覆盖的条件，不能把几个通过的用例等同于整体可靠。

**今天可以做的小练习：** 从正在进行的任务里找出一个“完成”的说法，将它改写成别人能重复检查的操作和结果。

正式稿需要把原文观点、作者实验和编辑补充分别归属；若文章有代码或案例，应说明其适用条件，不能把编辑自拟的例子冒充作者证据。
