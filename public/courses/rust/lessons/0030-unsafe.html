unsafe：找到需要人工保证的契约

阅读 unsafe 时明确哪些条件不再由编译器证明。

拆解进阶语言结构建议 8–15 分钟

先建立一个判断方法

unsafe 允许少数额外操作，例如解引用裸指针、调用 unsafe 函数、访问可变静态变量、实现 unsafe trait、读取 union 字段。它没有关闭所有类型检查或普通引用规则。

阅读时先找安全契约：地址是否有效、对齐是否正确、对象是否已初始化、别名与生命周期是否满足要求。unsafe extern "C" 声明涉及外部 ABI；#[repr(C)] 影响布局，但不能单独保证任意跨语言传参安全。

依据：Rust 官方文档 · 对应章节

先预测，再运行

先说出输出、关键值的类型，以及它们是否仍可使用，再展开结果。

examples/l30.rs / Rust 2024
fn main() {
    let value = 7_i32;
    let pointer: *const i32 = &value;
    // SAFETY: pointer 来自仍然有效且正确对齐的 i32 引用；只读且未发生冲突修改。
    let observed = unsafe { *pointer };
    println!("{observed}");
}
展开预期输出与阅读解析
7
  1. 把引用转为裸指针本身可在安全代码中进行，解引用则需要 unsafe。
  2. value 在读取期间仍存在；这里用局部契约解释为什么本次读取有效。

运行：在 examples/rust-reading 中执行 cargo run --offline --example l30。所有主示例均为完整程序；练习里的失败片段会明确说明。参见 下载与运行说明。

常见误读通过编译或一次运行成功都不能证明任意 unsafe 代码健全。也不要为消除借用错误而直接改裸指针。

检查你的判断

unsafe 块会关闭全部借用检查吗？

查看完整判断依据

不会关闭。它开放特定操作，普通引用与类型规则仍适用。

合上解释，自己说一遍

若 value 已销毁再解引用 pointer，编译器未报错能否说明安全？

完成后查看参考解析

不能。裸指针有效性需要程序员保证，悬垂解引用会产生未定义行为。应改变拥有关系或避免把裸指针带出数据存活范围。
