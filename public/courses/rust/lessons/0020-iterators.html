迭代器链：逐层写出 Item 类型

读懂 filter、map、collect，而不是把它们当黑盒。

识别日常代码习惯建议 8–15 分钟

先建立一个判断方法

Iterator 的 next(&mut self) 返回 Option<Self::Item>。适配器 map、filter 通常惰性执行；collect、sum、for 等消费迭代器，才推动元素处理。

iter() 常产生 &T，iter_mut() 产生 &mut T，拥有集合上的 into_iter() 常产生 T。filter 的谓词接收对 Item 的引用，而 map 的闭包接收 Item 本身；这解释了链中经常多出来的一层 &。

依据：Rust 官方文档 · 对应章节

先预测，再运行

先说出输出、关键值的类型，以及它们是否仍可使用，再展开结果。

examples/l20.rs / Rust 2024
fn main() {
    let values = vec![1, 2, 3, 4];
    let result: Vec<i32> = values
        .iter()
        .copied()
        .filter(|n| *n % 2 == 0)
        .map(|n| n * 10)
        .collect();
    println!("{:?} {}", result, values.len());
}
展开预期输出与阅读解析
[20, 40] 4
  1. iter 的 Item 是 &i32；copied 之后 Item 为 i32。
  2. filter 的 n 是 &i32，map 的 n 是 i32；collect 根据目标 Vec<i32> 收集结果。
  3. values 只被借用，链完成后仍能读取长度。

运行：在 examples/rust-reading 中执行 cargo run --offline --example l20。所有主示例均为完整程序；练习里的失败片段会明确说明。参见 下载与运行说明。

常见误读collect() 需要知道目标集合，既可以标注变量类型，也可以写 collect::<Vec<_>>()。不要为修复引用层数而盲目加 *。

检查你的判断

本例 filter 闭包里的 n 是哪种？

查看完整判断依据

整数引用。copied 后 Item 是 i32，而 filter 仍接收 &Item，所以 n 是 &i32。

合上解释，自己说一遍

把 iter().copied() 改成 into_iter() 后，链里的 Item 如何变化？末尾 values.len() 呢？

完成后查看参考解析

Item 仍为 i32，但 Vec 所有权被 into_iter 消耗，末尾不能再访问 values。对 Vec<String> 也要按所有权规则推演，而不是套用整数的 Copy 特性。
