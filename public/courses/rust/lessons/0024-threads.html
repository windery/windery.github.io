Arc、Mutex 与线程边界

拆开跨线程共享、互斥访问和等待完成。

识别日常代码习惯建议 8–15 分钟

先建立一个判断方法

Arc<T> 使用原子引用计数共享拥有权，但不会自动让 T 的所有操作变成线程安全。Mutex<T> 管理互斥访问；lock 返回 guard，guard 被释放时解锁。因此 Arc<Mutex<T>> 常用于跨线程共享可变状态。

Send 表示值能安全转移到另一线程；Sync 表示 &T 能安全跨线程共享。普通 thread::spawn 的闭包受 Send 与 'static 约束。move 移入捕获值，不会把捕获的短命引用变成 'static。

依据：Rust 官方文档 · 对应章节

先预测，再运行

先说出输出、关键值的类型，以及它们是否仍可使用，再展开结果。

examples/l24.rs / Rust 2024
use std::{
    sync::{Arc, Mutex},
    thread,
};
fn main() {
    let value = Arc::new(Mutex::new(0));
    let other = Arc::clone(&value);
    let handle = thread::spawn(move || {
        let mut guard = other.lock().expect("lock poisoned");
        *guard += 1;
    });
    handle.join().expect("thread panicked");
    println!("{}", *value.lock().expect("lock poisoned"));
}
展开预期输出与阅读解析
1
  1. move 把 other 句柄移入子线程；value 留在主线程。
  2. join 确保子线程完成后再读计数；guard 离开作用域时自动解锁。

运行：在 examples/rust-reading 中执行 cargo run --offline --example l24。所有主示例均为完整程序；练习里的失败片段会明确说明。参见 下载与运行说明。

常见误读Rust 防止许多数据竞争，但不会自动避免死锁或逻辑竞态。生产代码也要明确处理线程 panic 和锁中毒，示例中的 expect 是简化。

检查你的判断

Arc 本身是否自动允许任意 T 并发修改？

查看完整判断依据

并不允许。Arc 管共享所有权，内部 T 的同步安全仍有类型约束与访问机制。

合上解释，自己说一遍

删除 join 以后为什么不能保证输出 1？如果多个线程不同顺序获取两把锁会怎样？

完成后查看参考解析

主线程可能先读到 0。不同顺序获取多把锁可能彼此等待形成死锁，即使代码通过借用检查也会发生。
