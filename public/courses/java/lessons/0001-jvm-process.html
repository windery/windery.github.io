一个 Java 进程里有什么

用 jcmd 和 MXBean 看清 JVM 自己启动的线程、GC 与参数。

JVM 运行时：从源码到运行建议 15–20 分钟

先建立一个判断方法

执行 java -cp out L01 之后，main 方法并不是第一件发生的事。JVM 先解析参数，按机器条件推导默认配置（HotSpot 称为 ergonomics），选定垃圾收集器和堆大小，启动自己的工作线程，然后才加载主类，在名为 main 的线程里调用 main。

这些线程分两类。第一类有 Thread 对象，Java 代码能看到：除了 main，还有处理引用队列的 Reference Handler、运行 finalize 的 Finalizer（finalization 已在 JDK 18 由 JEP 421 标记为待移除）、处理操作系统信号的 Signal Dispatcher、服务 java.lang.ref.Cleaner 的 Common-Cleaner。第二类是 JVM 内部线程：GC 线程、JIT 编译线程、执行 safepoint 操作的 VM Thread 等。它们不出现在 Thread.getAllStackTraces() 里，但 jcmd <pid> Thread.print 会全部列出。

默认配置不是固定值。JDK 21 在“服务器级机器”上默认使用 G1；可用处理器少于 2 个，或可用内存低于约 1792 MB 时，会退回 Serial。默认最大堆是可用内存的 1/4（MaxRAMPercentage=25）。在容器里，“可用”指容器限额，所以一个 1 核的 Pod 会悄悄换成单线程的 Serial GC。

先预测，再运行

先预测：输出里会有几个线程？会出现 GC 线程吗？会列出哪种收集器？

java-depth/src/L01.java / JDK 21
import java.lang.management.ManagementFactory;

public class L01 {
    public static void main(String[] args) {
        var runtime = ManagementFactory.getRuntimeMXBean();
        System.out.println("JVM: " + runtime.getVmName());
        System.out.println("当前线程: " + Thread.currentThread().getName());
        var names = Thread.getAllStackTraces().keySet().stream()
                .map(Thread::getName).sorted().toList();
        System.out.println("线程: " + names);
        for (var gc : ManagementFactory.getGarbageCollectorMXBeans()) {
            System.out.println("GC: " + gc.getName());
        }
    }
}
展开实际输出与阅读解析
JVM: OpenJDK 64-Bit Server VM
当前线程: main
线程: [Common-Cleaner, Finalizer, Notification Thread, Reference Handler, Signal Dispatcher, main]
GC: G1 Young Generation
GC: G1 Concurrent GC
GC: G1 Old Generation

在 4 核、16 GB 的 Linux 机器上以 JDK 21 运行。线程名单和 GC 名称会随 JDK 版本与机器条件变化。

  1. main 只是六个 Java 线程之一，其余五个都是 daemon 线程，由 JVM 在调用 main 之前创建。
  2. 名单里没有任何 GC 线程或编译线程。同一进程用 jcmd <pid> Thread.print 查看，还能看到 C1/C2 CompilerThread、VM Thread、GC Thread#0、G1 Conc#0 等十多个线程。
  3. GC MXBean 的名字暴露了收集器：三个 G1 开头的 bean 说明 ergonomics 选择了 G1。若以 -XX:ActiveProcessorCount=1 启动，名字会变成 Copy 与 MarkSweepCompact，也就是 Serial。

运行：在解压后的 java-depth 目录执行 ./run.sh l01，课程名之后可以追加 JVM 参数。参见 下载与运行说明。

常见误读“JVM 默认用 G1”只在服务器级机器上成立。容器限额会改变 ergonomics 的推导结果；线上服务应显式写出收集器和堆大小，或者至少用 jcmd <pid> VM.flags 确认实际生效的值。

检查你的判断

在限额 1 个 CPU、4 GB 内存的容器里，不加任何 GC 参数启动 JDK 21，默认使用哪种收集器？

查看完整判断依据

Serial。可用处理器少于 2 个时，机器不被视为服务器级，ergonomics 选择 Serial。可以用 -XX:ActiveProcessorCount=1 -Xlog:gc 复现：日志第一行是 Using Serial。

合上解释，自己说一遍

线上一个 Java 服务 CPU 很高，但业务日志很安静。只允许用 jcmd，你会先看哪两样东西？为什么只看 Thread.getAllStackTraces() 不够？

完成后查看参考解析

先用 jcmd <pid> Thread.print 间隔几秒连续采样，找一直处于 RUNNABLE 且栈相同的业务线程；再用 GC.heap_info 或 GC 日志确认是否在频繁 GC。CPU 可能被 GC 线程或 JIT 编译线程占用，而这些 JVM 内部线程不在 Thread.getAllStackTraces() 的结果里。配合 top -H -p <pid> 找出最忙的系统线程号，与 Thread.print 中的 nid 对照即可定位。
