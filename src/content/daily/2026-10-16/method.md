Simon Willison 在 10 月 9 日的博客里记录了一次具体开发：他一边做饭，一边用 Codex 的语音对话，为自己的 Django 博客增加 newsletter 归档。约半小时后功能大体完成；吃饭后的另一段约半小时，他切回键盘审查和修改，才部署上线。

## 先把预览打开

Simon 开始时没有立即打开语音。他先让 Codex 启动本地开发服务器并打开浏览器，使后续对话都有可查看的页面。做饭时，他可以瞥一眼预览，告诉 Agent 新页面哪里需要调整。

这个顺序影响了协作方式：他描述的是屏幕上已经出现的结果，而不必只凭文字汇报想象界面。原文也提到，视觉预览以及必要时能键入或粘贴内容，使这次体验不同于单纯对手机说话。

## 用语音讲清规则

文章保留了一段带犹豫和自我修正的转录。Simon 先说 newsletter 不要出现在标签页和日期归档，随后改口：不要出现在标签页和首页，但应该出现在发送当天的日期归档里。

他还区分了两类内容：Substack 周报主要是博客已有内容的副本，不必重复进入搜索；月度 newsletter 含独立内容，公开后应能搜索。这些要求决定了数据与展示行为，远比一句“帮我做个 newsletter 页面”明确。

最终新增的功能包含 Django 数据模型和迁移、管理后台、四种导入、按年归档，以及搜索集成。已合并的 [PR #719](https://github.com/simonw/simonwillisonblog/pull/719) 提供了可查看的代码记录。这个案例能学到的是把规则讲具体，不是期待模型自动补齐未表达的产品决定。

## 键盘完成审查

语音阶段结束后，Simon 让 Codex 创建分支和 PR，再到 GitHub 检查修改。他发现一个导入脚本采用 Git 子进程，而涉及私有仓库的导入，他更希望通过 API 完成，于是切回打字要求更换实现，并调整了页面展示。

私有数据导入还需要配置新的 API key，这部分同样让他回到键盘前。“Agent 已经写出功能”和“可以按现有系统的方式部署”之间，还有实际的接入与审查工作。PR 的最终说明记录了 HTTP 导入、私有内容读取配置，以及重复导入时更新已有记录的行为。[原文](https://simonwillison.net/2026/Oct/9/built-using-my-voice/) · [合并后的改动](https://github.com/simonw/simonwillisonblog/pull/719/files)

## 可以迁移到自己项目里的四步

1. **先建立可见反馈。** 对页面类任务，先启动预览，再开始连续讨论需求；让“这里不对”有共同参照。
2. **用语音讲业务关系。** 说清哪些内容出现在哪里、哪些要隐藏、什么时候能公开。允许改口，但让 Agent 复述最终采用的规则。
3. **遇到精确材料就切回键盘。** 报错、参数、代码位置和长例子适合直接粘贴，不必强行口述所有细节。
4. **交付前审查实际改动。** 检查导入方式、配置、权限与既有系统是否一致，而不只看预览页面是否漂亮。

适合先尝试的是自己熟悉的项目里、边界清楚的小功能。Simon 在动手前已知道这是一个相对简单的 Django 改动，也大致清楚需要模型、迁移、视图、模板和导入函数，并不是把陌生系统的设计全部交给语音对话。

作者最后的判断也有明确范围：这对同时处理其他事情很有用，但未必会成为他的日常主力方式；涉及细节时，打字、粘贴和直接指向代码仍更高效。可以先试一次“语音讲规则、预览看结果、键盘做收尾”的组合，不必把整个开发流程改成语音输入。
