TL;DR：Hindsight 的核心是 `MemoryEngine`。retain 先把文本切块，交给 LLM 抽取结构化事实，再算 embedding、解析实体，然后在一个数据库事务里写入事实和时间、语义、因果关联。recall 把“四种检索方式 × 多种事实类型”交给存储层一次完成，再经过 RRF 融合、cross-encoder 重排和时间、证据加权，最后按 token 预算截断。reflect 是一个带工具调用的 LLM 循环。写入之后，后台 worker 会把新事实整合成观察，并刷新相关的心智模型。

本文按“分层 → retain → recall → reflect → 后台整合 → 任务与配置 → 扩展点”的顺序说明各部分如何实现。概念定义见《项目概览》，部署和调用见《使用指南》。

## 模块分层

服务端代码集中在 `hindsight-api-slim/hindsight_api/`，按职责分为以下几层：

| 层次 | 职责 | 主要文件 |
| --- | --- | --- |
| 入口 | 解析命令行参数和配置，加载扩展，启动 uvicorn | `main.py`、`worker/main.py`、`admin/cli.py`、`mcp_local.py` |
| 接口层 | REST 路由、鉴权、准入控制、审计；MCP 工具 | `api/http.py`、`api/mcp.py`、`mcp_tools.py` |
| 编排层 | retain / recall / reflect / 整合 / 导入导出等所有操作的入口 | `engine/memory_engine.py` |
| 流程模块 | 各操作的具体流水线 | `engine/retain/`、`engine/search/`、`engine/reflect/`、`engine/consolidation/`、`engine/mental_model_refresh.py` |
| 模型适配 | LLM、embedding、重排模型的 provider 适配 | `engine/llm_wrapper.py`、`engine/providers/`、`engine/embeddings.py`、`engine/cross_encoder.py` |
| 存储 | 记忆相关表的读写接口与 Postgres 实现，数据库方言，文件存储 | `engine/memories/`、`engine/db/`、`engine/storage/`、`alembic/` |
| 异步任务 | 操作入队、worker 轮询执行 | `engine/task_backend.py`、`worker/poller.py` |
| 配置与扩展 | 环境变量、分层解析、扩展加载 | `config.py`、`config_resolver.py`、`extensions/` |

外围包都依赖这个服务端：`hindsight-clients/`（由 OpenAPI 生成的 SDK）、`hindsight-control-plane/`（Next.js 控制台，通过 API 路由代理到数据面）、`hindsight-cli/`（Rust CLI）、`hindsight-all/`（在进程内嵌入服务端），以及 `hindsight-integrations/` 下的各类集成。

`main.py` 有意把 `MemoryEngine`、`create_app` 改成首次使用时才导入。源码注释给出的原因是：uvicorn 多 worker 模式下每个子进程都要重新导入入口模块，如果导入太慢，子进程会在 5 秒健康检查前被反复杀掉。按注释中的实测，延迟导入后这部分耗时从约 6.6 秒降到约 0.3 秒。

依据：[CLAUDE.md](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/CLAUDE.md)、[hindsight-api-slim/hindsight_api/main.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/main.py)、[hindsight-api-slim/hindsight_api/engine/memory_engine.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/memory_engine.py)。

## Retain：从文本到记忆单元

HTTP 层（`api_retain`）先把多模态内容规范化为纯文本，图片存入内容寻址存储，文本中只保留占位符，然后按 `strategy` 分组交给 `MemoryEngine.retain_batch_async()`。引擎完成租户鉴权和可选的操作校验（OperationValidator）后，调用 `engine/retain/orchestrator.py` 的 `retain_batch()`。主要步骤如下：

1. 预处理：执行 Memory Defense 扫描（如果 bank 配置了策略），处理追加模式（append）和强制重新抽取；做 delta 判断，即同一 `document_id` 再次写入时，只重新处理内容哈希变化了的块。
2. 切块：默认每块最多 3000 字符。对话、JSONL 等结构化输入有专门的切块逻辑。
3. LLM 生产者：每个块并发调用一次事实抽取，并发上限由抽取模块内部的信号量控制（源码注释为 32）。默认 `concise` 模式下，每条事实包含 `what / when / where / who / why`、`occurred_start/end`、`fact_type`、`entities` 和 `causal_relations`。模型输出的 `assistant` 类型映射为 `experience`，其余映射为 `world`。抽取完的事实随即计算 embedding，放入队列。
4. 数据库消费者：从队列中按批取出结果，分三个阶段写入：
   - Phase 1：在独立连接上做实体解析（归一化、合并同名实体）。在当前的流式路径中，这一步不做语义近邻计算，留到 Phase 3。
   - Phase 2：在一个事务里写入 `memory_units`，再写 `unit_entities`，然后建立时间关联、语义关联（相似度阈值默认 0.7）和因果关联。检索依赖的数据要么全部写入，要么全部不写。
   - Phase 3：事务提交后，补算语义近邻（ANN）关联，属于尽力而为的步骤，失败不影响本次写入。
5. 收尾：写入文档正文，更新操作进度。然后提交后台任务：自动整合（`enable_observations` 和 `enable_auto_consolidation` 都开启时）、图维护、向量索引维护。这些任务失败只记录日志，不会让 retain 失败。

生产者-消费者的结构是为了控制内存占用。源码注释提到，一个超过 17000 个块的文档如果一次性抽取会导致内存溢出，现在每个小批次单独提交，提交后释放内存。同样的设计也支持崩溃恢复：重试时如果发现文档内容哈希相同、部分块已经提交，就跳过这些块。

依据：[hindsight-api-slim/hindsight_api/engine/retain/orchestrator.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/retain/orchestrator.py)、[hindsight-api-slim/hindsight_api/engine/retain/fact_extraction.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/retain/fact_extraction.py)、[hindsight-api-slim/hindsight_api/engine/retain/link_creation.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/retain/link_creation.py)、[hindsight-api-slim/hindsight_api/api/http.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/api/http.py)。

## Recall：四路检索与重排

`MemoryEngine.recall_async()` 的主要步骤如下：

| 步骤 | 做什么 | 实现位置 |
| --- | --- | --- |
| 0. 预算 | `budget` 映射为整数 `thinking_budget`：默认 `fixed` 策略下 low/mid/high 分别为 100/300/1000；`adaptive` 策略按 `max_tokens` 的比例计算 | `memory_engine._resolve_thinking_budget()` |
| 1. 查询向量 | 计算 query 的 embedding | `embeddings.py` |
| 2. 时间约束 | 从 query 中解析时间范围（例如“六月”），在线程池中运行，避免阻塞事件循环；调用方也可以直接传 `temporal_window` | `search/temporal_extraction.py`、`query_analyzer.py` |
| 3. 并行检索 | 调用存储层的 `recall_unified()`，一次返回每种事实类型的 semantic、BM25、graph、temporal 四路结果 | `search/retrieval.py`、`memories/postgres.py` |
| 4. 融合 | 每一路先截断到上限，防止某一路结果过多挤掉其他路；再用 RRF 融合，`score = Σ 1/(k + rank)`，k=60。也可以选 `interleave`（轮流取） | `search/fusion.py` |
| 5. 重排 | cross-encoder 对融合后的候选打分，候选数量受 `reranker_max_candidates` 限制 | `search/reranking.py`、`cross_encoder.py` |
| 6. 综合打分 | 以 cross-encoder 分数为基数，乘以时效、时间接近度、证据数（`proof_count`）三个加权因子，默认分别约为 ±10%、±10%、±5% | `reranking.apply_combined_scoring()` |
| 7. 截断与组装 | 按 `max_tokens` 截断，按需附带实体、原文块、观察的来源事实 | `memory_engine.py` |

在 Postgres 实现中，semantic 和 BM25 合并为一条 UNION 查询，与 temporal 查询共用一个连接；graph 检索以语义检索结果为种子，按事实类型并行执行。默认的图检索器是 `link_expansion`，它从种子出发沿三类关联扩展：

- 实体：通过 `unit_entities` 自连接，按共享实体的数量打分；每个实体最多扩展 200 条，避免高频实体让查询结果爆炸。
- 语义：写入时预先计算好的近邻图。
- 因果：权重额外加 1.0，被视为质量最高的信号。

综合打分采用乘法而不是加法。源码注释给出的理由是：这样加权的影响始终与相关度成比例，不受不同 cross-encoder 分数标定的影响。对于重排器只是透传、不提供真实分数的精简部署，代码会改用 RRF 排名作为基数，避免最终排序退化成单纯按时间排序。

依据：[hindsight-api-slim/hindsight_api/engine/search/retrieval.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/search/retrieval.py)、[hindsight-api-slim/hindsight_api/engine/search/fusion.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/search/fusion.py)、[hindsight-api-slim/hindsight_api/engine/search/reranking.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/search/reranking.py)、[hindsight-api-slim/hindsight_api/engine/memories/postgres.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/memories/postgres.py)、[hindsight-api-slim/hindsight_api/engine/memories/pg/link_expansion.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/memories/pg/link_expansion.py)。

## Reflect：带工具的推理循环

reflect 不是“先 recall 再总结”的单次调用，而是 `engine/reflect/agent.py` 中的 `run_reflect_agent()` 运行的一个原生工具调用循环。模型可以使用以下工具：

| 工具 | 读取内容 | 层级 |
| --- | --- | --- |
| `search_mental_models` / `read_mental_models` | 用户定义的心智模型 | 质量最高，命中且足够新时可以直接作答 |
| `search_observations` | 后台整合出的观察，附带新鲜度信息 | 中间层 |
| `recall` | 原始事实 | 作为事实依据 |
| `expand` | 展开某条记忆的上下文（原文块等） | 补充细节 |
| `done` | 提交最终答案 | 结束循环 |

模块注释把这种顺序称为分层检索：先查心智模型，再查观察，最后用原始事实兜底。几项循环上限的默认值分别是：最多 10 轮迭代、累计上下文 100,000 token、整次操作墙钟超时 300 秒。最后一轮会强制要求模型给出答案。bank 的 mission、disposition 和 directives（行为规则）都写进系统提示；directives 还会被编进 `done` 工具的参数约束中。调用方传入 `response_schema` 时，答案会再经过一次结构化输出生成。对于支持增量提示缓存的 provider，每一步的上下文都会缓存，结束后在后台清理。

依据：[hindsight-api-slim/hindsight_api/engine/reflect/agent.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/reflect/agent.py)、[hindsight-api-slim/hindsight_api/engine/reflect/tools_schema.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/reflect/tools_schema.py)、[hindsight-api-slim/hindsight_api/config.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/config.py)。

## 后台整合：观察与心智模型

观察的生成在 `engine/consolidation/consolidator.py` 中完成，入口是 `run_consolidation_job()`：

1. 解析 bank 的分层配置，构造整合专用的 LLM（可以与 retain 使用不同的模型）。
2. 读取尚未整合（`consolidated_at` 为空）的事实，按标签范围（observation scopes）分批。
3. 对每批事实调用 `_find_related_observations()`，用 recall 找出相关的已有观察。只要带了标签，就使用 `all_strict` 匹配，源码注释明确说这是为了防止跨用户、跨租户泄漏。
4. 把新事实和相关观察交给 LLM，LLM 返回 `creates / updates / deletes` 三类动作。新建和更新动作必须列出所依据的新事实 ID，删除动作只需给出观察 ID 和理由。
5. 在同一个事务里应用这些动作，并给消费掉的事实打上 `consolidated_at` 标记。观察保存在 `memory_units` 表中（`fact_type='observation'`），带有 `proof_count`、来源事实 ID 和变更历史；另有一步可选的去重裁决，防止重复创建相同的观察。
6. 整合结束后，刷新受影响标签下的心智模型。刷新过程是对一个有界快照执行 reflect，分为 `full`（整体重写）和 `delta`（对已有文档执行结构化增量操作）两种模式。心智模型也可以按 cron 表达式定时刷新（依赖 `croniter`）。

这里体现的设计取舍是“演进而不是覆盖”：新证据只会更新或删除具体某条观察，每次变更都保留历史和证据，从而让 bank 的认知能被追溯。

依据：[hindsight-api-slim/hindsight_api/engine/consolidation/consolidator.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/consolidation/consolidator.py)、[hindsight-api-slim/hindsight_api/engine/mental_model_refresh.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/mental_model_refresh.py)、[hindsight-api-slim/hindsight_api/engine/memory_engine.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/memory_engine.py)。

## 异步任务与配置分层

### 任务

异步 retain、整合、心智模型刷新、图维护、导入导出等操作，都会以一行记录写入 `async_operations` 表。`task_backend.py` 定义了三种后端：

| 后端 | 用途 |
| --- | --- |
| `BrokerTaskBackend` | API 服务把 PostgreSQL 当作消息代理，只负责写入任务 |
| `WorkerTaskBackend` | worker 进程使用，提交子任务时不执行任何操作，子任务由轮询取得 |
| `SyncTaskBackend` | 立即执行任务，用于测试和内嵌场景 |

`worker/poller.py` 用 `FOR UPDATE SKIP LOCKED` 并发领取任务，所以可以水平扩展多个 `hindsight-worker`。默认 `HINDSIGHT_API_WORKER_ENABLED=true`，API 进程自己也会运行 worker，单机部署不需要额外进程。整合任务按 bank 去重：如果已有排队中的整合任务，直接返回已有的操作 ID，不再新建。

### 配置

`config_resolver.py` 在每次请求时按“全局环境变量 → 租户配置（由扩展提供）→ bank 配置（数据库）”的顺序解析配置。多台 API 服务器共用数据库时，它们看到的 bank 配置是一致的。数据库迁移同时支持 PostgreSQL 和 Oracle：每个 Alembic 迁移文件都通过 `run_for_dialect` 分派到对应方言，CI 中有测试检查迁移文件是否遗漏了分派。

依据：[hindsight-api-slim/hindsight_api/engine/task_backend.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/engine/task_backend.py)、[hindsight-api-slim/hindsight_api/worker/poller.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/worker/poller.py)、[hindsight-api-slim/hindsight_api/config_resolver.py](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/hindsight-api-slim/hindsight_api/config_resolver.py)、[CLAUDE.md](https://github.com/vectorize-io/hindsight/blob/6d8b096786df335fc2cc1e5d6662092f0e1b8694/CLAUDE.md)。

## 可扩展点

扩展通过 `HINDSIGHT_API_<槽位>_EXTENSION=模块路径:类名` 加载。同一前缀下的其他环境变量（如 `HINDSIGHT_API_<槽位>_XXX`）会作为配置传给扩展。

| 想做的事 | 改动位置 | 说明 |
| --- | --- | --- |
| 自定义鉴权或多租户 | `TENANT` 槽位，实现 `TenantExtension.authenticate()` | 内置 `DefaultTenantExtension`（不鉴权）和 `ApiKeyTenantExtension`；多租户场景按租户返回不同的数据库 schema |
| 拦截或校验操作 | `OPERATION_VALIDATOR` 槽位 | 在 retain、recall、reflect、bank 写入等操作前执行，可以拒绝请求 |
| 增加 HTTP 路由或 MCP 工具 | `HTTP`、`MCP` 槽位 | 不需要修改核心路由 |
| 写入前过滤敏感信息 | `MEMORY_DEFENSE` 槽位，配合 bank 策略 | 内置基于正则的实现 `memory_defense_regex.py` |
| 替换记忆存储 | `MEMORIES` 槽位，实现 `engine/memories/base.py` 的接口 | 替换后由新实现独占该 bank 的记忆表；bank、操作等其他表仍在 Postgres 中。CI 中的测试禁止其他代码直接用 SQL 访问这些表 |
| 换向量索引或全文检索 | `HINDSIGHT_API_VECTOR_EXTENSION`（`pgvector`、`vchord`、`pgvectorscale`、`scann`）、`HINDSIGHT_API_TEXT_SEARCH_EXTENSION` | `docker/docker-compose/` 下有 vchord、pg_search、pgroonga 等示例 |
| 文件存储 | `HINDSIGHT_API_FILE_STORAGE_EXTENSION` | 内置 PostgreSQL、S3、GCS、Azure 实现 |
| 接入新的 LLM | `engine/providers/` 新增实现，并在 `llm_wrapper.py` 的白名单和 `config.py` 的默认模型表中登记 | OpenAI 兼容的服务通常只需配置 `HINDSIGHT_API_LLM_BASE_URL` |
| 调整抽取行为 | bank 配置 `retain_extraction_mode=custom` + `retain_custom_instructions`，或设置 `retain_mission` | 不需要改代码 |
| 订阅事件 | Webhook 接口 | 覆盖 retain、整合、刷新等生命周期事件 |

测试分为两层：`hindsight-api-slim/tests/`（619 个 `test_*.py` 文件，大多用 MockLLM 测试单个机制），以及 `hindsight-system-tests/`（黑盒测试，用一个模拟 OpenAI 和 Cohere 接口的 stub 服务驱动真实的 API 进程，专门检查多个步骤组合在一起时的问题）。依赖 LLM 判断的测试使用真实 LLM 加 LLM-as-judge 断言。
