TL;DR：这组技能通过可读指令协调 Agent、CLI 和本地状态。稳定复用依靠来源与节点身份，发布完成依靠回读或公开页面验证，而不是命令返回成功就结束。

## 指令层与执行层

SKILL.md 描述何时使用、读哪些材料、如何选择目标和什么结果算完成。Agent 负责理解任务并调用工具；飞书和 GitHub 的实际状态由外部服务保存。

因此，技能不是一个封装好的 HTTP 客户端。飞书命令参数与正文格式由当前 lark-cli 帮助和内置文档提供，避免技能文件长期缓存容易变化的接口细节。

## 名称用于展示，来源用于识别

两个仓库都可能叫 `tools`。如果只根据标题复用节点，文档就可能被写进另一个项目。project-to-feishu 用规范化 remote 与本地来源辅助匹配，项目节点保存身份信息，本地配置保存节点 token。

匹配按成本逐步展开：先查配置；未命中再查飞书候选节点；核对来源后复用；没有候选才新建。遇到多个无法辨认的候选时，将歧义交还用户，而不是猜一个。

Pages 采用同样的身份思路，但公开展示使用 `owner/repository`。路径是长期链接的一部分，因此已有项目通过来源匹配后继续使用原 slug。

## 两种写入语义

会话记录是一串历史事件。再次归档当前会话时新建文章，不把内容不断追加到同一篇。

项目说明是一份持续维护的知识。再次分析同一项目时先读原文，分清新增、更新和无需修改的文章，尽量保留文档身份与人工编辑。

这种区别决定了去重方式：会话技能主要复用项目工作区；项目技能还需要复用具体文章。

## 本地状态是索引

飞书两个技能使用各自的配置文件，记录知识库和项目节点；Pages 使用独立配置与结果状态。状态文件让后续运行快速命中目标，但不替代远端核验。

飞书状态丢失时，技能会根据项目名称和来源重新找回节点。创建成功后立即记录返回 ID，以免列表短暂不可见时误创建重复节点。网络错误导致创建结果不确定时，应先检查实际目标，再决定重试。

## 内容与发布分阶段验收

内容阶段检查主题、操作顺序、源码证据和跨篇一致性。飞书阶段逐篇回读正文与节点标题，防止正文替换意外影响目录标题。Pages 阶段检查导入差异、静态构建、部署 commit 与公开 URL。

这让失败状态可以精确表达：“草稿完成、推送成功、部署失败”与“已经上线”是不同结果。飞书连接失败也不阻止使用现有源码生成 Pages 文章，因为两个技能没有强制串联。

## 设计取舍

| 选择 | 带来的效果 | 代价 |
| --- | --- | --- |
| Markdown 指令描述流程 | 人可直接阅读和调整 | 执行质量仍依赖 Agent 和工具能力 |
| CLI 文档作为接口依据 | 随已安装版本查准确用法 | 执行时需要读取帮助 |
| 保存远端 ID 与来源 | 更新能复用既有文档 | 需要维护本地状态并核对远端 |
| 独立发布技能 | 可单独选飞书或 Pages | 不提供自动双向同步 |
