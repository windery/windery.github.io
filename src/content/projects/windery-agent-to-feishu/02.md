TL;DR：先安装所需技能，再明确输入项目与发布目的地。飞书流程依赖 lark-cli；Pages 流程依赖已有学习站、GitHub 访问与站点构建工具。

## 最小使用流程

有仓库访问权限时，可以按 README 安装：

```sh
npx skills add windery/agent-to-feishu -g
```

这是仓库声明的安装入口；本文没有在新机器上重跑安装。源仓库目前私有，未获访问权限的读者不能直接下载。安装完成后，在 Agent 中给出项目与目标：

```text
用 project-to-pages 阅读当前项目，生成项目概览、使用指南和工作原理，发布到我的学习站。
```

预期结果是一组 Markdown 文章、站点中的项目目录和可访问的公开页面。若只想先看内容，可以明确说“先生成草稿，不发布”。

## 先决定保存哪一种信息

需要把本次排障和决策留档时：

```text
把这次会话总结存到飞书，记录根因、关键决定和未完成项。
```

需要按代码重新建立项目说明时：

```text
用 project-to-feishu 阅读当前项目，重点写上手使用和工作原理。
```

后者会先组织完整草稿，再提供全文和计划落点供确认；确认过的内容无需重复确认。需求会保存在本地偏好中，下次沿用，单个项目的临时要求可以单独说明。

## 首次接入 Pages

Pages 技能需要知道四件事：站点仓库、公开网址、本地 checkout、允许公开的内容范围。这些信息保存在 `~/.project-to-pages/config.json`，不进入网页正文。没有配置时先定位已有学习站，不会凭空创建一个与用户无关的新站。

确定后，Agent 读取该站的 README 和导入器，以站点自己的规则准备内容。文章默认按照“作者/仓库”命名，同一来源再次运行会更新已有项目。可以说：

```text
用 project-to-pages 重新生成 mattpocock/skills 的项目解读；沿用已有网址。
```

## 既有文档如何复用

有本地草稿时，直接读取草稿及来源记录。只存在于飞书时，才需要通过 lark-cli 获取正文。用户要求“重新生成”时，旧文档只用于识别源码项目，内容从源码重写。

更新前会比较站内现有文章，保留人工修改。源码提交、文章日期、公开或私有来源分别记录；包含未提交改动的本地工作树不能写成某个公开 commit 的精确副本。

## 如何判断发布完成

本地生成文章只完成了准备阶段；构建通过也只说明静态产物可以生成。真正完成还需要推送站点变更、确认对应部署成功，并验证公开页面。

最终应拿到文章链接和来源版本。若其中一个环节失败，草稿与已完成提交保留，结果明确指出失败位置。这个流程按调用执行，没有飞书后台监听器。
