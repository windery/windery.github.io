TL;DR：windery/agent-to-feishu 是一组让 Agent 生成和归档技术文档的技能。会话记录存飞书，项目解读可以存飞书，也可以独立发布到 GitHub Pages。

## 三个技能，各自处理什么

这个仓库的主要产物是 Markdown 指令文件。执行它们的是已经具备读文件、运行命令和访问服务能力的 Agent。仓库本身没有常驻服务，也没有负责定时同步内容的后台进程。

| 技能 | 输入 | 主要产出 | 再次运行 |
| --- | --- | --- | --- |
| session-to-feishu | 当前会话中的事实和决定 | 一篇技术会话笔记 | 新建一篇，按项目归档 |
| project-to-feishu | 本地项目或 GitHub 仓库 | 按阅读需求组织的项目文档 | 定位原项目，更新已有文章 |
| project-to-pages | 源码或已有项目文章 | 学习站中的项目解读 | 保留网址，更新同来源项目 |

选择的关键是你想保存什么。如果要留下“这次为什么这样改”，使用会话归档；如果要系统理解“项目怎么工作”，使用项目解读。两个项目技能的内容目标相近，发布目的地不同，单独调用飞书技能不会顺带公开网站。

## 飞书如何组织内容

默认存在两棵独立目录：会话笔记库和项目文档库。会话库在项目工作区下面累计多次会话；项目库在项目节点下面维护一组文章。

项目文档的阅读目标包括快速了解、上手使用、理解原理和开发维护。它们决定内容重点，不强制每个项目都套四篇文章。小项目可以合并；机制复杂的项目可以把关键技术单独展开。

## Pages 增加了什么

project-to-pages 复用目标学习站已有的内容目录、样式、构建与部署流程。文章仍然用 Markdown 编辑，部署结束后验证公开网址。飞书不是它的必经步骤：给一个源码仓库，也能直接生成并发布。

为避免多个 `skills` 或 `tools` 混在一起，GitHub 项目采用 `owner/repository` 作为规范身份，新增目录默认采用 `owner-repository`。已有网址保持稳定。

## 阅读这个仓库的入口

| 文件 | 重点 |
| --- | --- |
| skills/session-to-feishu/SKILL.md | 会话总结、工作区定位、新建文章与回读 |
| skills/project-to-feishu/SKILL.md | 阅读需求、源码证据、同名项目识别与文档更新 |
| skills/project-to-pages/SKILL.md | 发布范围、来源命名、导入、构建与上线验证 |
| .claude-plugin/marketplace.json | 插件公开提供哪些技能目录 |
