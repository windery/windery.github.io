TL;DR：JOL（Java Object Layout）是 OpenJDK 下的一个小工具箱，用 Unsafe、Instrumentation 和 HotSpot Serviceability Agent 读出对象在当前 JVM 里的真实布局与占用。它回答“这个对象到底多大、字段怎么排、一张缓存图占多少内存”这类问题。

## 它解决什么问题

Java 语言规范不规定对象在内存里长什么样。字段顺序、对象头大小、引用是 4 字节还是 8 字节，都由具体 JVM 和启动参数决定。凭经验估算（“一个 `Integer` 大概 16 字节”）在大多数情况下够用，但遇到下面这些问题就不够了：

- 一个缓存放 100 万个条目，堆要预留多少？
- 某个类加了一个 `boolean` 字段，实例为什么没变大？又为什么有时突然多出 8 字节？
- 两个高频写的 `volatile long` 放在同一个对象里，会不会落在同一条 cache line 上？
- 堆超过 32 GB 关掉 compressed oops 以后，内存到底涨多少？

README 对自己的定位是：这些工具大量使用 Unsafe、JVMTI 和 Serviceability Agent（SA）来解码实际的对象布局、占用和引用关系，因此比依赖 heap dump 或规范假设的工具更准确。重点是“实际”：JOL 默认报告的是**当前这个 JVM 进程**里的布局，而不是理论值。

## 它能看到的几样东西

| 概念 | 含义 | JOL 里怎么看 |
| --- | --- | --- |
| 对象头 mark word | 存放锁状态、GC 年龄、identity hash code 等，64 位 JVM 上 8 字节 | `ClassLayout` 输出的 `(object header: mark)` 行，带解码说明，如 `non-biasable; age: 0`、`hash: 0x...` |
| 对象头 class word | 指向类元数据的指针；开启 compressed class pointers 时 4 字节，否则 8 字节 | `(object header: class)` 行 |
| 数组长度 | 数组额外占用的 4 字节长度槽 | `(array length)` 行 |
| 字段布局 | JVM 重新排列字段以减少空洞，并按字段大小对齐 | 每个字段的 `OFF`（偏移）和 `SZ`（大小） |
| 内部空洞 | 字段之间因对齐产生的浪费 | `(alignment/padding gap)`，汇总为 `internal` 损失 |
| 尾部对齐 | 对象总大小向上对齐到 `ObjectAlignmentInBytes`（默认 8） | `(object alignment gap)`，汇总为 `external` 损失 |
| Compressed oops | 64 位 JVM 上用 32 位编码引用，按位移还原地址 | `VM.current().details()` 的 `Compressed references (oops)` 行与 `Field sizes` 中 `ref` 列 |
| 对象图占用 | 从一个根对象出发、所有可达对象的数量与大小 | `GraphLayout.parseInstance(root).totalSize()` / `toFootprint()` |

注意最后一项：`GraphLayout` 统计的是**可达**对象的总和，不是 MAT 里基于支配树的 retained size。如果图里的对象也被别处引用（例如 `Integer` 缓存里的小整数、驻留字符串），它们同样会被计入。

## 仓库结构

根 `pom.xml` 声明了四个模块：

| 模块 | 内容 |
| --- | --- |
| `jol-core` | 核心库。`info` 包（`ClassLayout`、`GraphLayout`、`GraphStats` 等对外 API）、`vm` 包（`VM`、`VirtualMachine` 及 HotSpot 实现、SA 与 Instrumentation 支持）、`layouters` 包（真实布局与模拟布局）、`datamodel` 包（32 位、64 位、Lilliput 等数据模型）、`heap` 包（heap dump 读取），以及从外部并入的 `ljv` 包（用 Graphviz 画对象图） |
| `jol-cli` | 命令行工具，把 core 的能力包装成 `internals`、`footprint`、`heapdump-stats` 等子命令，构建出可直接 `java -jar` 运行的 `jol-cli.jar` |
| `jol-samples` | 28 个编号示例 `JOLSample_01_Basic` 到 `JOLSample_28_Difference`，覆盖字段对齐、继承空洞、`@Contended`、数据模型对比、锁状态与 mark word、数组、GC 搬移与对象图等主题 |
| `jol-benchmarks` | JMH 基准，测 JOL 自己遍历对象图的开销（`GraphInstanceBench`、`LinkedChainBench`） |

对日常使用来说，只需要关心 `jol-core`（作为依赖写代码）和 `jol-cli`（不写代码直接看）。`jol-samples` 是最好的教材：每个示例都有一段注释讲清楚它想演示什么，配合输出阅读，比读任何二手文章都快。

## 两种用法：真实布局与模拟布局

JOL 里有两类“布局器”（`Layouter`）：

- `CurrentLayouter`：问当前 JVM 要字段偏移，得到的是真实布局。`ClassLayout.parseClass(...)` 默认用它。
- `HotSpotLayouter`：按 HotSpot 的字段分配规则在纯 Java 里**模拟**布局，可以指定数据模型（32 位、64 位是否压缩引用、对齐字节数、Lilliput 头）和 JDK 版本（区分 JDK 15 之前和之后的新字段分配算法）。

前者用来回答“现在到底是什么样”，后者用来回答“如果换 JDK、换堆大小、关掉 compressed oops，会是什么样”。CLI 的 `internals-estimates` 和 `heapdump-estimates` 就是基于模拟布局。

## 对后端工程师的价值

| 场景 | JOL 帮你做什么 |
| --- | --- |
| 本地缓存容量规划 | 用 `GraphLayout` 量一份有代表性的缓存（比如 1000 个条目），除以条目数得到单条目成本，再乘以目标规模。你会发现 `HashMap<String, Integer>` 的单条目成本远大于 key 和 value 的“数据大小” |
| 选择数据结构 | 对比 `HashMap` 与原始类型集合、`List<Long>` 与 `long[]`、`String` 与 `byte[]` 的对象头和包装开销，用数字而不是直觉做决定 |
| 调整 DTO / 实体字段 | 看清字段被重排后的空洞，判断增减一个字段是否会让实例跨过 8 字节对齐边界 |
| 排查 false sharing | 验证两个热点字段的偏移距离，或者确认 `@Contended` 是否真的插入了填充 |
| 评估 JVM 参数 | 比较开关 `UseCompressedOops`、调整 `ObjectAlignmentInBytes` 对单个类和整份堆的影响；`heapdump-estimates` 能对一份真实 heap dump 做这种推演 |
| 理解锁与 hash | 观察 mark word 在 `hashCode()`、`synchronized` 前后的变化，配合 JVM 课程理解轻量锁、重量锁和 identity hash 的存放位置 |

一句话总结：JOL 把“对象内存布局”从一段需要背诵的理论，变成一段可以运行、可以修改参数再观察的实验。

## 先建立一个量级感

下面这些数字都来自 JOL 在 OpenJDK 21（Linux x86_64，默认参数，compressed oops 开启，8 字节对齐）上的实际输出，完整过程见使用指南：

| 对象 | 大小 | 说明 |
| --- | --- | --- |
| `new Object()` | 16 字节 | 12 字节对象头 + 4 字节尾部对齐 |
| `Integer` | 16 字节 | 头 12 + `int` 4 |
| `AtomicLong` | 24 字节 | 头 12 + 4 字节空洞 + `long` 8 |
| `long[3]` | 40 字节 | 头 12 + 长度 4 + 元素 24 |
| `String`（短 Latin-1 文本） | 24 + 24 字节 | `String` 对象本身 24，内部 `byte[]` 另算 |
| `HashMap.Node` | 32 字节 | hash、key、value、next 四个字段 |
| 一个 `HashMap<String, Integer>` 条目 | 约 104 字节 | 1000 个条目实测总计 104,256 字节 |

这张表不是用来背的。它说明两件事：第一，小对象的头和对齐开销经常超过数据本身；第二，这些数字随 JVM 参数而变，关掉 compressed oops 后同一张 `HashMap` 会涨到 128,464 字节。所以需要准确数字时，用 JOL 在目标环境里量。

## 版本现状

当前主分支版本号是 `0.18-SNAPSHOT`，Maven Central 上最新的正式版是 `0.17`（2023 年 2 月发布）。0.17 之后的 27 个提交包括 CLI 重做、并入 LJV、JDK 25 兼容、ZGC 地址处理和 heap dump 解析提速等改动。因此：

- 作为库使用时，`jol-core:0.17` 的核心 API（`ClassLayout`、`GraphLayout`、`VM`）与主分支一致，足够日常使用。
- 作为 CLI 使用时，0.17 发布版的子命令名称和主分支不同（详见[使用指南](/projects/openjdk-jol/02/)）。
