TL;DR：引入 jol-core 0.17，用 ClassLayout 看单个对象的头、字段偏移和对齐损失，用 GraphLayout 量一整张对象图的占用；不想写代码时用 jol-cli。本文的输出都来自 JDK 21 上的实际运行。

## 引入依赖

Maven Central 上 `jol-core` 的最新正式版是 `0.17`（`maven-metadata.xml` 中 `<release>0.17</release>`，2023-02 发布）。主分支当前是 `0.18-SNAPSHOT`，尚未发布。

```xml
<dependency>
    <groupId>org.openjdk.jol</groupId>
    <artifactId>jol-core</artifactId>
    <version>0.17</version>
</dependency>
```

Gradle 写法是 `implementation("org.openjdk.jol:jol-core:0.17")`。JOL 只支持 HotSpot / OpenJDK：`VM.current()` 会检查 `java.vm.name`，不含 `HotSpot` 或 `OpenJDK` 时直接抛出 `IllegalStateException`。

## 核心 API 一览

| API | 作用 |
| --- | --- |
| `VM.current().details()` | 打印当前 VM 模式：位数、compressed oops / class pointers 的位移与基址、对象对齐、各类型字段大小、数组元素大小和数组基址偏移 |
| `ClassLayout.parseClass(Foo.class).toPrintable()` | 只看类，不需要实例；VALUE 列显示 `N/A` |
| `ClassLayout.parseInstance(obj).toPrintable()` | 看具体实例，额外显示 mark word、class word 和字段当前值 |
| `ClassLayout#instanceSize()` / `getLossesInternal()` / `getLossesExternal()` | 以数字形式拿到实例大小和对齐损失，适合写进测试断言 |
| `GraphLayout.parseInstance(roots...)` | 从一个或多个根出发遍历所有可达对象 |
| `GraphLayout#totalSize()` / `totalCount()` | 可达对象的总字节数和总个数 |
| `GraphLayout#toFootprint()` | 按类汇总的 COUNT / AVG / SUM 表 |
| `GraphLayout#toPrintable()` | 按地址列出每个对象、它的大小和从根出发的路径 |
| `GraphLayout#subtract()` / `add()` | 对两次快照做差或求和，比如看一次操作新分配了什么 |
| `GraphStats.parseInstance(roots...)` | 只要 `totalCount()` / `totalSize()` 时的轻量版本，不保存每个对象的路径记录 |

`ClassLayout.parseClass` 和 `parseInstance` 都有带 `Layouter` 参数的重载，传入 `HotSpotLayouter(model, jdkVersion)` 就能模拟其他数据模型下的布局，`jol-samples` 里的 `JOLSample_10_DataModels` 演示了这种用法。

## 一个完整例子

下面的 `Demo.java` 依次看：一个业务类的布局、`Object` 在调用 `hashCode()` 前后的 mark word、一个 `long[3]`，以及一个装了 1000 个条目的 `HashMap<String, Integer>`。

```java
import org.openjdk.jol.info.ClassLayout;
import org.openjdk.jol.info.GraphLayout;
import org.openjdk.jol.vm.VM;
import java.util.HashMap;
import java.util.Map;

public class Demo {
    static class Order {
        boolean paid;
        long id;
        int amount;
        String sku;
    }

    public static void main(String[] args) {
        System.out.println(VM.current().details());
        System.out.println(ClassLayout.parseClass(Order.class).toPrintable());

        Object lock = new Object();
        System.out.println(ClassLayout.parseInstance(lock).toPrintable());
        System.out.println("hashCode: " + Integer.toHexString(lock.hashCode()));
        System.out.println(ClassLayout.parseInstance(lock).toPrintable());

        System.out.println(ClassLayout.parseInstance(new long[3]).toPrintable());

        Map<String, Integer> cache = new HashMap<>();
        for (int i = 0; i < 1000; i++) cache.put("key-" + i, i);
        GraphLayout g = GraphLayout.parseInstance(cache);
        System.out.println("totalCount = " + g.totalCount());
        System.out.println("totalSize  = " + g.totalSize());
        System.out.println(g.toFootprint());
    }
}
```

运行环境：OpenJDK 21.0.11，Linux x86_64，默认 JVM 参数，`jol-core-0.17.jar` 从 Maven Central 下载。用单文件源码模式直接运行：

```bash
java -cp jol-core-0.17.jar Demo.java
```

开头先是一条警告和 VM 信息：

```text
# WARNING: Unable to get Instrumentation. Dynamic Attach failed. You may add this JAR as -javaagent manually, or supply -Djdk.attach.allowAttachSelf
# VM mode: 64 bits
# Compressed references (oops): 3-bit shift
# Compressed class pointers: 0-bit shift and 0x7FD577000000 base
# Object alignment: 8 bytes
#                       ref, bool, byte, char, shrt,  int,  flt,  lng,  dbl
# Field sizes:            4,    1,    1,    2,    2,    4,    4,    8,    8
# Array element sizes:    4,    1,    1,    2,    2,    4,    4,    8,    8
# Array base offsets:    16,   16,   16,   16,   16,   16,   16,   16,   16
```

默认堆远小于 32 GB，所以 compressed oops 开启，引用（`ref`）占 4 字节。class pointer 的基址每次运行都会变，不必在意具体值。

`Order` 的布局：

```text
Demo$Order object internals:
OFF  SZ               TYPE DESCRIPTION               VALUE
  0   8                    (object header: mark)     N/A
  8   4                    (object header: class)    N/A
 12   4                int Order.amount              N/A
 16   8               long Order.id                  N/A
 24   1            boolean Order.paid                N/A
 25   3                    (alignment/padding gap)
 28   4   java.lang.String Order.sku                 N/A
Instance size: 32 bytes
Space losses: 3 bytes internal + 0 bytes external = 3 bytes total
```

几个值得注意的点：对象头是 8 + 4 = 12 字节；字段顺序被 JVM 重排了，`int amount` 填进了对象头后面的 4 字节空位，`long id` 落在 8 字节对齐的偏移 16；`boolean` 后面有 3 字节空洞，因为 4 字节的引用要按 4 对齐。

`Object` 在 `hashCode()` 前后：

```text
  0   8        (object header: mark)     0x0000000000000001 (non-biasable; age: 0)
  8   4        (object header: class)    0x00000e90
 12   4        (object alignment gap)
Instance size: 16 bytes

hashCode: 43c1b556
  0   8        (object header: mark)     0x00000043c1b55601 (hash: 0x43c1b556; age: 0)
```

identity hash code 一旦被计算，就被写进 mark word。一个没有字段的 `Object` 也要 16 字节，其中 4 字节是尾部对齐。

`long[3]` 多了一个 `(array length)` 槽：`12  4  (array length)  3`，元素从偏移 16 开始，共 24 字节，总计 40 字节。

最后是 `HashMap` 的对象图：

```text
totalCount = 4002
totalSize  = 104256
java.util.HashMap@7530ad9cd footprint:
     COUNT       AVG       SUM   DESCRIPTION
      1000        24     24000   [B
         1      8208      8208   [Ljava.util.HashMap$Node;
      1000        16     16000   java.lang.Integer
      1000        24     24000   java.lang.String
         1        48        48   java.util.HashMap
      1000        32     32000   java.util.HashMap$Node
      4002              104256   (total)
```

1000 个条目约 104 KB，平均每个条目约 104 字节，而“有效数据”只是一个几字节的字符串和一个 4 字节整数。`Node` 32 字节、`String` 24 字节、它的 `byte[]` 24 字节、`Integer` 16 字节，再加上 2048 个槽的桶数组（16 + 2048 × 4 = 8208）。用主分支构建的 jol-core 运行同一段代码，数值一致，只是表格改用了 `byte[]`、`java.util.HashMap.Node` 这样的可读类名并按 SUM 排序。

## 改一个参数再看

加上 `-XX:-UseCompressedOops` 重新运行（同时加了 `-Djdk.attach.allowAttachSelf`，见下一节）：

```text
# Compressed references (oops): disabled
# Field sizes:            8,    1,    1,    2,    2,    4,    4,    8,    8
...
 24   1            boolean Order.paid                N/A
 25   7                    (alignment/padding gap)
 32   8   java.lang.String Order.sku                 N/A
Instance size: 40 bytes
...
      1000        32     32000   java.lang.String
      1000        40     40000   java.util.HashMap$Node
      4002              128464   (total)
```

引用变成 8 字节，`Order` 从 32 涨到 40 字节，这张缓存图从 104,256 涨到 128,464 字节（约 +23%）。注意 class word 仍然是 4 字节：JDK 15 起 compressed class pointers 可以独立于 compressed oops 开启。这正是“堆超过 32 GB 要谨慎”的量化依据。

## 常用参数

| 参数 | 来源 | 作用 |
| --- | --- | --- |
| `-Djdk.attach.allowAttachSelf` | JDK | 允许 JOL 自我 attach 加载 agent，从而拿到 `Instrumentation`。JDK 21 上随后会打印 “A Java agent has been loaded dynamically” 警告，可再加 `-XX:+EnableDynamicAgentLoading` 消除 |
| `-javaagent:jol-cli-0.17-full.jar` | JDK | 静态加载 agent。`jol-core` 的 jar 没有 `Premain-Class`，不能用作 `-javaagent`（实测会报 “Failed to find Premain-Class”）；`jol-cli` 的 full jar 有 |
| `-XX:-UseCompressedOops` | HotSpot | 关闭压缩引用，模拟大堆 |
| `-XX:ObjectAlignmentInBytes=16` | HotSpot | 修改对象对齐，观察尾部对齐损失变化 |
| `-XX:-RestrictContended` | HotSpot | 让应用代码里的 `@Contended` 生效（`JOLSample_09_Contended` 的注释写明需要） |
| `-Djol.skipHotspotSAAttach=true` | JOL | 跳过 Serviceability Agent，启动更快，但 compressed oops 的基址与位移改为实验推测 |
| `-Djol.tryWithSudo=true` | JOL | SA attach 因权限失败时尝试用 `sudo` 重来 |
| `-Djol.skipDynamicAttach=true` / `-Djol.skipInstallAttach=true` | JOL | 跳过动态 attach / 跳过检查已安装的 agent |
| `-Djol.magicFieldOffset=true` | JOL | 公开 `Unsafe` 拒绝给出 record、hidden class 字段偏移时，改用内部 `Unsafe` 的“魔法”路径；源码注释明确说它会写对象内部，有风险 |
| `-DprintFirst=N` | JOL | 主分支里 `toFootprint()` 和 CLI 的表格默认只打印前 30 行，用它调整；0.17 的 `toFootprint()` 不截断 |

在 `-Djol.skipHotspotSAAttach=true` 下，`details()` 会打印三行 `# WARNING |`，提示 compressed references 的 base/shift 是猜出来的，计算出的地址“ARE NOT RELIABLE”。字段偏移和大小不受影响，只有 `addressOf` 和 `GraphLayout.toPrintable()` 的地址列需要 SA 才准确。

## 验证 false sharing 填充

`@Contended` 能在热点字段周围插入填充，避免多个线程写的字段落在同一条 cache line：

```java
import jdk.internal.vm.annotation.Contended;

static class Counters {
    volatile long hits;
    @Contended
    volatile long misses;
}
```

编译和运行都需要 `--add-exports java.base/jdk.internal.vm.annotation=ALL-UNNAMED`，运行还要 `-XX:-RestrictContended`。`parseInstance(new Counters())` 的输出：

```text
 16   8   long Counters.hits             0
 24 128        (alignment/padding gap)
152   8   long Counters.misses           0
160   0        (object alignment gap)
Instance size: 288 bytes
```

`misses` 前面多了 128 字节填充。实例真实大小是 288 字节，说明尾部还有一段填充；但如果用 `parseClass(Counters.class)`，JOL 会报 160 字节。`CurrentLayouter` 源码里有一条 TODO 正好说明了这一点：类布局在有尾部 `@Contended` 时计算不正确。需要准确大小时，用 `parseInstance` 并确保 Instrumentation 可用（输出里的 `Instance size` 来自 `Instrumentation.getObjectSize`）。

## 命令行工具 jol-cli

不想写代码时，下载 `jol-cli-0.17-full.jar`（Maven Central 的 `org/openjdk/jol/jol-cli/0.17/` 目录）。这个 jar 的 manifest 带有 `Launcher-Agent-Class`，用 `java -jar` 启动时自动获得 Instrumentation，不会有动态 attach 警告。

主分支源码（`jol-cli/.../Main.java`）注册的子命令：

| 命令 | 作用 |
| --- | --- |
| `internals` | 实例化类（优先无参构造器）并打印 `ClassLayout`，失败时退回 `parseClass` |
| `internals-estimates` | 同上，但用 `HotSpotLayouter` 模拟 JDK 8 / 15 / 23 / 25、32 位、Lilliput 等多种模式，把相同结果归组 |
| `externals` | 打印 `GraphLayout.toPrintable()`：可达对象、地址、路径 |
| `footprint` | 打印 `GraphLayout.toFootprint()` |
| `heapdump-stats` | 单遍读取 `.hprof` 输出类直方图 |
| `heapdump-estimates` | 推算同一份 heap dump 在不同 VM 模式下的占用 |
| `heapdump-duplicates` / `heapdump-strings` / `heapdump-boxes` | 找内容重复的对象、重复字符串和重复的装箱整数 |

类相关命令都接受 `-cp` 指定额外 classpath，例如：

```bash
java -jar jol-cli.jar internals -cp target/classes com.example.Order
java -jar jol-cli.jar footprint java.util.concurrent.ConcurrentHashMap
java -jar jol-cli.jar heapdump-estimates app.hprof
```

不带参数或用 `help` 查看列表；README 里写的 `-h` 实际会先打印 “Unknown operation: -h” 再输出帮助。**注意版本差异**：0.17 发布版的命令是 `internals`、`externals`、`footprint`、`estimates`、`heapdump-estimates`、`heapdumpstats`、`shapes`、`string-compress`，与主分支不同。想用上表的命令，需要从源码 `mvn clean verify` 构建，或使用 README 提到的 builds.shipilev.net 构建。

## 注意事项

- **结果属于当前 VM**：JDK 版本、位数、堆大小、`UseCompressedOops`、对齐参数、GC 都会改变结果。写进文档或评审的数字，要注明运行环境。
- **单文件源码模式的限制**：`java Demo.java` 运行时，对自定义类调用 `parseInstance(...).toPrintable()` 会抛出 `Class is not found`，因为 JOL 通过自己的类加载器按名字重新加载类，看不到源码启动器在内存里编译的类。`parseClass`、JDK 类和数组不受影响。遇到这个问题就先 `javac` 再运行。
- **可达不等于独占**：`GraphLayout` 统计所有可达对象，包括被共享的对象。量缓存时，用代表性数据、关注单条目的边际成本更可靠。
- **地址会变**：GC 可能在遍历中搬移对象。`toPrintable()` 会重试最多 10 次并打印 “Addresses are stable after N tries”；`subtract()` 按地址判断对象身份，源码注释建议先做几次 GC 让堆安静下来。
- **数值是快照**：`parseInstance` 读取的字段值和 mark word 是调用那一刻的状态。
