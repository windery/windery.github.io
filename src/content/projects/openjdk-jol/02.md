TL;DR：JOL 把“问 JVM”和“算布局”分开：VirtualMachine 用 Unsafe、Instrumentation 和 Serviceability Agent 获取偏移、大小与压缩指针参数，Layouter 把类结构变成 ClassLayout，GraphWalker 用反射沿引用遍历出 GraphLayout。拿不到真实数据时，它用小实验推测并在输出里明确警告。

下文路径都相对于 `jol-core/src/main/java/org/openjdk/jol/`。

## 三层结构

| 层 | 关键类型 | 职责 |
| --- | --- | --- |
| VM 访问 | `vm/VM`、`vm/VirtualMachine`、`vm/HotspotUnsafe` | 提供字段偏移、字段与数组元素大小、对象头大小、对齐、地址、按偏移读内存 |
| 类结构与布局 | `info/ClassData`、`layouters/*`、`datamodel/*`、`info/ClassLayout` | 用反射收集字段，再由布局器决定每个字段的偏移，最后计算损失并输出表格 |
| 对象图 | `info/GraphWalker`、`info/GraphLayout`、`info/GraphStatsWalker` | 从根出发遍历引用，为每个可达对象记录路径和大小 |

`VirtualMachine` 是一个接口，但在这个 commit 里只有一个实现：包内可见的 `HotspotUnsafe`。所有“问 JVM”的操作都汇集到它身上。

## VM.current()：三种信息源

`vm/VM.java` 的 `current()` 是整个库的入口，第一次调用时组装出单例：

```java
String name = System.getProperty("java.vm.name");
if (!name.contains("HotSpot") && !name.contains("OpenJDK")) {
    throw new IllegalStateException("Only HotSpot/OpenJDK VMs are supported");
}
Unsafe u = tryUnsafe();               // 反射读取 Unsafe.theUnsafe
Instrumentation inst = null;
try {
    inst = InstrumentationSupport.instance();
} catch (Exception e) {
    System.out.println("# WARNING: Unable to get Instrumentation. " + e.getMessage());
}
try {
    UniverseData saDetails = ServiceabilityAgentSupport.instance().getUniverseData();
    INSTANCE = new HotspotUnsafe(u, inst, saDetails);
} catch (Exception e) {
    System.out.println("# WARNING: Unable to attach Serviceability Agent. " + e.getMessage());
    INSTANCE = new HotspotUnsafe(u, inst);
}
```

三种信息源分工明确：

| 来源 | 提供什么 | 缺失时的后果 |
| --- | --- | --- |
| `sun.misc.Unsafe` | `objectFieldOffset`、`arrayBaseOffset`、`arrayIndexScale`、`getInt/getLong/getObject` 等按偏移读取 | 必需，拿不到就无法工作 |
| `java.lang.instrument.Instrumentation` | `getObjectSize(obj)`，即 JVM 认定的真实对象大小 | `sizeOf` 退回用 `CurrentLayouter` 按字段偏移计算，遇到尾部 `@Contended` 等情况会偏小 |
| HotSpot Serviceability Agent | oop 大小、对象对齐、compressed oops / class pointers 是否开启及其 base 和 shift | 改用 MXBean 和实验推测；`details()` 打印 “guessed by the experiment” 警告，地址不可靠 |

两个构造器的差别体现在 `isAccurate` 字段上：带 `UniverseData` 的版本为 `true`，另一个为 `false`。

## Instrumentation 怎么拿到

`vm/InstrumentationSupport.java` 依次尝试三条路：

1. **已作为 agent 加载**：`premain` 把 `Instrumentation` 存进静态字段；或者 jar 的 manifest 声明了 `Launcher-Agent-Class: ...InstrumentationSupport$Installer`，`java -jar` 启动时 JVM 自动调用 `Installer.agentmain`。`jol-cli` 和 `jol-samples` 的 pom 都配置了这两个 manifest 属性。
2. **动态自我 attach**：用 `com.sun.tools.attach.VirtualMachine.attach(自己的 pid)`，把 `Installer` 类写进一个临时 `jolAgent*.jar`（manifest 只有 `Agent-Class`），`loadAgent` 之后再用反射从系统类加载器读回 `Installer.INSTRUMENTATION`，最后删除临时文件并 `detach`。
3. 都失败时抛出 `InstrumentationException`，消息就是[项目概览与用法](/projects/openjdk-jol/01/)例子里看到的 “Dynamic Attach failed. You may add this JAR as -javaagent manually, or supply -Djdk.attach.allowAttachSelf”。

JDK 9 起默认禁止进程 attach 自己，所以第 2 步需要 `-Djdk.attach.allowAttachSelf`。两步分别可以用 `-Djol.skipInstallAttach` 和 `-Djol.skipDynamicAttach` 关闭。

## Serviceability Agent 怎么用

SA 是 HotSpot 自带的调试接口（`jdk.hotspot.agent` 模块），能从外部读取一个 JVM 的内部结构。进程不能用 SA attach 自己，所以 `vm/sa/ServiceabilityAgentSupport.java` 会**启动一个子 JVM**：

- 用当前的 `java.home/bin/java` 和当前 classpath 启动 `AttachMain`；在 JDK 9+ 风格下追加 `--add-modules jdk.hotspot.agent` 和若干 `--add-exports`（`AgentStyle.JDK_9`），JDK 8 风格则把 `sa-jdi.jar` 加进 classpath。
- 先用 `SenseAccessMain` 探测哪种风格可用，再探测是否需要 `sudo`。
- 父进程把一个可序列化的 `Request`（pid、任务、超时）写到子进程的 stdin；子进程调用 `sun.jvm.hotspot.HotSpotAgent.attach(pid)`，执行任务，把 `Response` 序列化写回 stdout。超时常量是 5000 ms。
- 任务是 `vm/sa/UniverseTask.java`：通过反射调用 SA 的 `VM.getVM()`，读出 `getOopSize`、`getObjectAlignmentInBytes`、`getHeapOopSize`、`isCompressedOopsEnabled`、`isCompressedKlassPointersEnabled`，以及 `CompressedOops` / `CompressedKlassPointers` 的 `getBase`、`getShift`（JDK 13 之前回退到 `Universe` 上的同名方法）。

attach 失败时，异常消息会给出两种处理办法：`-Djol.tryWithSudo=true`，或把 `/proc/sys/kernel/yama/ptrace_scope` 设为 0。设置 `-Djol.skipHotspotSAAttach=true` 则直接跳过整套流程。

## 没有 SA 时的推测实验

`vm/Experiments.java` 定义了一组只为“被测量”而存在的小类，`HotspotUnsafe` 用它们推断 VM 参数：

| 要推断的值 | 方法 |
| --- | --- |
| 对象头大小 | `HeaderClass` 只有一个 `boolean b1`，它的 `objectFieldOffset` 就是头的长度 |
| 引用大小（oop size） | `CompressedOopsClass` 有两个 `Object` 字段，两者偏移之差即为 4 或 8 |
| 各基本类型字段大小 | `MyInts4`、`MyLongs4` 等类各有 4 个同类型字段，取偏移的最小差值 |
| 是否开启 compressed oops / class pointers、对齐 | 先通过 `HotSpotDiagnostic` MXBean 读 `UseCompressedOops`、`UseCompressedClassPointers`、`ObjectAlignmentInBytes`（`vm/VMOptions.java`） |
| 对齐（MXBean 不可用时） | 随机分配 10 万对不同大小的小对象，对每对对象的地址差求最大公约数 |
| 是否 Lilliput | 分配两个不同类的空对象，比较 mark word；Lilliput 把类信息编码进 mark word，所以会不同。重试 100 次都不同才判定为 Lilliput |

推测模式下 narrow oop 的 shift 取对齐的 log2，base 取 `addressOf(null)`，class pointer 的 base 直接设为 0。这些都是近似值，所以 `details()` 会打印警告。

## 偏移、地址与读取

字段偏移就是一次 `Unsafe` 调用：

```java
public long fieldOffset(Field field) {
    try {
        if (Modifier.isStatic(field.getModifiers())) {
            return U.staticFieldOffset(field);
        } else {
            return U.objectFieldOffset(field);
        }
    } catch (UnsupportedOperationException uoe) {
        if (MAGIC_FIELD_OFFSET) {
            return magicFieldOffset(field, uoe);
        } else {
            throw new RuntimeException("Cannot get the field offset, try with -D" + MAGIC_FIELD_OFFSET_OPTION + "=true", uoe);
        }
    }
}
```

公开的 `sun.misc.Unsafe.objectFieldOffset` 对 record 和 hidden class 会抛 `UnsupportedOperationException`（源码注释引用了 JDK-8247444）。开启 `jol.magicFieldOffset` 后，JOL 先通过对比 `setAccessible(true/false)` 两个 `Method` 对象的内存，找到 `AccessibleObject` 里 override 标志的偏移，再直接写这个字节，让内部的 `jdk.internal.misc.Unsafe.objectFieldOffset` 变得可调用。注释把这段称为 “YOLO Engineering” 和 “NAKED MEMORY STORE”，默认关闭。

对象地址的读法很巧妙：把对象放进一个线程本地的 `Object[1]`，再用 `Unsafe.getInt` 或 `getLong` 读出数组槽里的原始引用值，然后解码：

```java
private long toNativeAddress(long address) {
    if (compressedOopsEnabled) {
        return narrowOopBase + (address << narrowOopShift);
    } else {
        return isZGC ? ZGCAddress.uncolorize(address) : address;
    }
}
```

ZGC 的引用带颜色位，`vm/ZGCAddress.java` 按 x86_64 和 aarch64 的不同编码去掉颜色位；是否为分代 ZGC 通过是否存在名为 “ZGC Minor Cycles” 的 GC MXBean 判断。

## 从类到 ClassLayout

`info/ClassData.parse` 用反射沿继承链收集所有非静态字段（`getDeclaredFields`），记录类层次、是否带 `@Contended`；数组则只记录元素类型和长度。之后交给 `Layouter`：

- `layouters/CurrentLayouter`：对每个字段调用 `vm.fieldOffset(...)` 和 `vm.sizeOfField(...)`，放进按偏移排序的 `TreeSet`；实例大小取最后一个字段的末尾并按对齐取整。数组的大小是 `arrayBaseOffset + length × arrayIndexScale` 再对齐。源码里留有 TODO：存在尾部 `@Contended` 时这个计算不正确。
- `info/ClassLayout.create`：从对象头末尾开始扫描字段，累计字段之间的空洞为 internal 损失，实例大小与最后一个字段末尾之差为 external 损失；对真实布局还会检查不变量（字段按自身大小对齐、不重叠、不越界）。
- `toPrintable(instance)`：有实例时用 `vm.getLong(instance, 0)` 读 mark word，按低位解码：`01` 再看第 3 位区分无锁/可偏向，`00` 为 thin lock，`10` 为 fat lock，`11` 为 marked；无锁状态下 64 位 mark 的 `>>> 8` 部分就是 identity hash。最终的 `Instance size` 来自 `vm.sizeOf(instance)`，有 Instrumentation 时就是 JVM 的真实值。

## 模拟布局：DataModel 与 HotSpotLayouter

`datamodel/DataModel` 接口只描述几个数字：mark 头大小、class 头大小、数组长度槽大小、各类型大小、对齐和地址宽度。实现有 `Model32`、`Model64(compressedRefs, compressedClasses, align)`、`Model64_Lilliput(compRefs, align, version)`，以及把这些问题转发给 `VM.current()` 的 `ModelVM`。

`layouters/HotSpotLayouter(model, jdkVersion)` 在纯 Java 里重放 HotSpot 的字段分配：

- **JDK 15 及以后**：用一个 `BitSet` 表示已占用的字节，对象头部分预先占满；按类层次从父类到子类，每层先后处理引用字段和基本类型字段，按 8、4、2、1 的大小顺序，为每个字段找第一个能放下的对齐空位。所以小字段能填进父类或对象头留下的空洞。
- **JDK 25 及以后**：引用字段聚集在一起（注释引用 JDK-8353273），由上一层最后一个字段是否为引用决定这一层先放引用还是先放基本类型。
- **JDK 15 之前**：`oldLayouter` 按 `FieldAllocationType` 分组分配，并单独处理 `@Contended` 的填充（宽度取 `-DcontendedPaddingWidth`，默认 128）。
- **数组**：JDK 23 之前数组基址按 HeapWord 对齐，之后按 4 字节对齐（JDK-8139457）。

另有 `RawLayouter`，把字段紧挨着排、不考虑头和对齐，用来衡量“纯数据”有多少。CLI 的 `internals-estimates` 就是把一组 `DataModel` 和 JDK 版本组合依次交给 `HotSpotLayouter`，再把结果相同的组合归在一起。

## GraphLayout：对象图遍历

`info/GraphWalker.walk(roots...)` 是一个显式栈的深度优先遍历：

```java
while (!s.isEmpty()) {
    GraphPathRecord cGpr = s.pop();
    Object o = cGpr.obj();
    Class<?> cl = o.getClass();
    if (cl.isArray()) {
        if (cl.getComponentType().isPrimitive()) continue;
        // 逐个元素：非 null 且首次访问则记录 ArrayGraphPathRecord 并入栈
    } else {
        // 按类缓存 sizeOf 结果；逐个引用字段：非 null 且首次访问则记录 FieldGraphPathRecord 并入栈
    }
}
```

要点：

- **去重**：`SimpleIdentityHashSet` 按对象身份去重，共享对象只算一次，环也不会导致死循环。
- **只走引用字段**：`AbstractGraphWalker` 用 `ClassValue` 缓存每个类（含父类）的非静态、非基本类型字段，并提前 `setAccessible(true)`。静态字段不在遍历范围内。
- **读字段值**：`util/ObjectUtils.value` 先用普通反射，失败再 `setAccessible`，再失败就用 `vm.fieldOffset` 加 `vm.getObject` 直接读内存，所以能穿过模块封装。
- **大小**：普通对象的 `sizeOf` 按类缓存；数组大小随长度变化，由 `GraphPathRecord.size()` 首次访问时惰性计算。
- **路径**：每条记录保存父记录和字段名或数组下标，`toPrintable()` 里看到的 `.table[3].next.key` 这类 PATH 就是沿父链拼出来的。
- **地址**：`totalSize()` 等统计不需要地址；`toPrintable()`、`subtract()` 需要时才计算，并重复读取最多 10 轮，直到一轮内所有地址都没有变化，以应对 GC 搬移。

`GraphStatsWalker` 是同一套遍历去掉路径记录的版本，只累加个数和大小，适合大图。

## Heap dump 分析

CLI 的 `heapdump-*` 命令不需要目标进程在运行。`heap/HeapDumpReader` 单遍扫描 `.hprof`，从 class dump 记录中重建每个类的字段列表并沿父类合并，产出 `Multiset<ClassData>`（类结构 × 实例数）。之后每个 `DataModel` 都可以用 `HotSpotLayouter` 重新计算大小并汇总，这就是 `heapdump-estimates` 能回答“同一份堆换成另一种 VM 模式会多大”的原因。

## 设计取舍

- **真实优先，模拟兜底**：默认路径总是问当前 VM，模拟布局只用于 what-if，两者共用 `ClassLayout` 的输出格式，便于对照。
- **不确定就说出来**：推测出的参数会在 `details()` 里打印警告，`toPrintable()` 会注明地址是否稳定，CLI 实例化失败会说明退回了类级分析。
- **代价是依赖内部机制**：`Unsafe`、自我 attach、SA 子进程、可选的直接写内存，都可能随 JDK 收紧封装而失效。0.17 之后的提交里有专门的 “JDK 25 compatibility fixes”，说明这个库需要跟着 JDK 一起维护。
