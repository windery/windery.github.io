上一课说过，模型每一步都会得到“下一个 token”的概率分布。这一课回答两个问题：从分布里怎么选？生成什么时候结束？这两个问题对应着 API 里最常用的几个参数，也对应着最容易被忽略的返回字段 `stop_reason`。

## 采样：从概率分布中选一个 token

假设模型在“接口幂等性是指”之后，给出的分布是这样的：

| 候选 token | 概率 |
| --- | --- |
| 同一 | 0.62 |
| 多次 | 0.21 |
| 对 | 0.09 |
| 一个 | 0.05 |
| 其他所有 token | 0.03 |

最直接的策略是每次选概率最高的（贪心解码），但这样生成的文本容易重复、呆板。所以大多数模型默认会**按概率随机抽样**，并提供几个参数调整抽样方式：

- **temperature（温度）**：对分布做“拉伸”或“压平”。温度低于 1 时，高概率的选项更占优势，输出更保守、更一致；温度高于 1 时，分布变平，低概率的选项更容易被选中，输出更多样，也更容易跑偏。
- **top_p（核采样）**：只在累计概率达到 p 的那部分候选中抽样。比如 top_p = 0.9，上表只会在“同一”“多次”“对”里选（0.62 + 0.21 + 0.09 = 0.92）。
- **top_k**：只在概率最高的 k 个候选中抽样。

在很多模型和本地推理工具（比如第 24 课会讲的 Ollama）上，这些参数仍然是调节输出的主要手段，所以值得理解它们的原理。

## 一个常见误解：temperature = 0 不等于确定性

很多人把 temperature 设成 0，以为这样同样的输入就一定得到同样的输出，可以像普通函数一样测试。实际上并不保证：推理服务的批处理方式、浮点运算顺序、硬件差异都可能让结果略有不同，而自回归生成会把一个 token 的差异放大到整段输出。

正确的做法不是追求逐字一致，而是：

- 用**结构化输出**约束格式（第 6 课），让“格式”稳定；
- 用**评测集**检查“内容”是否满足要求（第 17 课），而不是比较字符串是否相同。

## Claude 新一代模型：用 effort 代替采样参数

在 Claude 的新一代模型上（Claude Opus 4.7 及之后的 Opus、Fable 系列等），`temperature`、`top_p`、`top_k` 已经不再被接受，请求里带上它们会直接返回 400 错误；Claude Sonnet 5 和 Sonnet 5.5 只接受默认值。官方的建议是通过 prompt 来引导输出风格，而不是调采样参数。

取而代之的控制手段是 **effort**，表示模型在一次回答中投入多少“思考”和输出：

| effort | 适合的场景 |
| --- | --- |
| `low` | 分类、简单抽取、闲聊、对延迟敏感的接口 |
| `medium` | 一般问答、常规代码任务 |
| `high` | 需要推理的问题、重要的生成任务 |
| `xhigh` | 复杂编码和长时间运行的 agent 任务 |
| `max` | 正确性比成本更重要的难题 |

effort 越高，模型思考得越充分，回答通常也更全面，但输出 token 更多、更贵、更慢。不同模型的默认值不同，比如 Claude Opus 5.5 默认是 `medium`，多数其他模型默认是 `high`。所以在代码里**显式写出 effort**，比依赖默认值更可靠。

请求中 effort 写在 `output_config` 里：

```json
{
  "model": "claude-opus-5-5",
  "max_tokens": 4096,
  "output_config": { "effort": "low" },
  "messages": [
    { "role": "user", "content": "把这条工单归类为：账单、物流、售后、其他。工单：快递三天没动了。" }
  ]
}
```

选择 effort 的方法和调 JVM 参数类似：先用默认值跑一组真实样例，再分别试高一档和低一档，比较质量、耗时和费用。不要凭感觉一律开到最高。

## max_tokens：输出的硬上限

`max_tokens` 是**必填参数**，表示这次回答最多生成多少 token（思考内容也算在内）。达到上限时，生成会被直接截断，哪怕一句话还没说完。

它和 effort 的区别是：

- effort 是模型**知道**的“预算倾向”，模型会据此调整回答的详略；
- `max_tokens` 是模型**不知道**的硬截断，到了就停。

所以 `max_tokens` 不宜设得太小。一个常见错误是为了省钱把它设成 200，结果模型的 JSON 输出被拦腰截断，解析失败后反复重试，反而更贵。控制长度应该靠 prompt 和 effort，`max_tokens` 只作为兜底。经验上，非流式请求可以设在一万多 token，流式请求可以更大；分类之类的短输出任务再相应调小。

## 停止条件：读懂 stop_reason

每次响应都有一个 `stop_reason` 字段，说明生成为什么结束。**处理响应时应该先看它，再读内容。**

| stop_reason | 含义 | 应用层该怎么做 |
| --- | --- | --- |
| `end_turn` | 模型自然结束 | 正常处理 |
| `max_tokens` | 达到 `max_tokens` 上限，输出被截断 | 不要直接当完整结果使用；调大上限或缩小任务 |
| `stop_sequence` | 遇到了你设置的停止序列 | 按约定处理 |
| `tool_use` | 模型想调用工具 | 执行工具并把结果发回（第 9 课） |
| `pause_turn` | 长任务暂停，可以继续 | 把响应原样发回让它继续 |
| `refusal` | 模型出于安全原因拒绝 | 查看 `stop_details`，给用户合适的提示 |
| `model_context_window_exceeded` | 上下文窗口用完 | 缩减输入，或做摘要压缩 |

这和处理 HTTP 状态码是一个道理：200 只说明请求成功，不说明业务成功。一个返回 200 但 `stop_reason` 是 `max_tokens` 的响应，内容很可能是残缺的。

`stop_sequences` 参数可以指定一组字符串，模型生成到其中任何一个时就停止。早期常用它截取格式化输出，现在更推荐使用结构化输出。

## 小结

- 采样参数（temperature、top_p、top_k）决定如何从概率分布中选 token，原理在各家模型中通用。
- temperature = 0 不保证输出完全一致，测试要靠结构化输出和评测集。
- Claude 新一代模型不再接受采样参数，改用 effort 控制投入程度；不同模型默认值不同，建议显式设置。
- `max_tokens` 是硬截断，不是长度控制手段。
- 先检查 `stop_reason`，再使用输出内容。
