第二部分你亲手写了一个编程 agent。从这一课开始，我们换到 Claude Code 上工作。它比 MiniAgent 成熟得多，但骨架是一样的：一个循环，一组工具，一份不断增长的上下文。

这一课不急着讲技巧，先做一件事：**把 Claude Code 当成一个可以观察的系统。** 你会用三种方法看到它每一步在做什么：`/context` 看上下文里装了什么，hooks 记录每一次工具调用，会话记录文件里有每一轮请求的 token 用量。之后几课讲的每一条实践，你都可以用这些方法去验证，而不是只能相信。

## 准备：练习项目 order-lab

第三部分的练习都在一个小项目里进行。它是一个极简的订单服务，只依赖 JDK 和 JUnit 5，结构和你熟悉的后端代码一样：

```sh
cd ~
curl -LO https://windery.github.io/courses/ai-dev/code/order-lab.zip
unzip order-lab.zip && cd order-lab
git init -q && git add -A && git commit -qm "initial"
mvn -q test          # 没有输出表示全部测试通过
```

源码也可以[在线浏览](/courses/ai-dev/code/order-lab/README.md)。主要的类：

| 类 | 作用 |
| --- | --- |
| `OrderService` | 下单、支付、发货、取消，计算应付金额 |
| `DiscountPolicy` | 满减规则：满 200 减 20，满 500 减 80 |
| `Order`、`OrderItem`、`OrderStatus` | 订单、商品行、订单状态 |
| `InMemoryOrderRepository` | 内存中的订单存储 |

项目里故意留了一些问题，后面几课会用到。现在先别急着找。

然后在项目目录里启动 Claude Code：

```sh
claude
```

第一次启动会引导你登录（Claude 订阅账号或 Console 的 API key 都可以），并询问是否信任这个目录。

## 部件对照

先把第二部分的 MiniAgent 和 Claude Code 放在一起看：

| MiniAgent（第 8–12 课） | Claude Code | 你在界面上看到的 |
| --- | --- | --- |
| `runAgentLoop` | 同样的 agent 循环 | 它连续读文件、跑命令，直到给出回答 |
| `list_files`、`grep`、`read_file` | Glob、Grep、Read | “Read 3 files”“Search…” |
| `edit_file`、`write_file` | Edit、Write | 带 `-` / `+` 的 diff |
| `run_command` | Bash | 命令和它的输出 |
| `buildSystemPrompt` | 内置的系统提示，加上环境信息、git 状态 | 看不到，但可以在 `/context` 里看到它的大小 |
| `AGENTS.md` | `CLAUDE.md`（没有 CLAUDE.md 时也会读 AGENTS.md） | 启动时加载 |
| `cacheControl` | 自动使用 prompt caching | 会话记录里的 `cache_read_input_tokens` |
| `compact`、`/compact`、`/clear` | 自动压缩、`/compact`、`/clear` | 上下文快满时自动整理 |
| `todo_write` | 任务清单 | 终端里的待办列表 |
| `task` 子 agent | 内置的 Explore、Plan 等子 agent，以及自定义子 agent | “Explore(…)” |
| `/mode`、allow/deny 规则 | 权限模式（Shift+Tab 切换）、`/permissions` | 状态栏的模式标识、确认提示 |

几乎每一行你都写过简化版。区别在于工程细节：Claude Code 的工具描述经过大量打磨，权限判断更精细，还有 MCP、skills、hooks 等扩展机制（第 18 课）。

还有一项是 MiniAgent 没有的：**检查点**。Claude Code 在编辑文件前会保存快照，按两次 `Esc` 或输入 `/rewind` 可以把对话和代码一起回退到之前的某一步。它只覆盖通过编辑工具做的修改，Bash 命令造成的改动不在其中，所以不能替代 git。

## 观察一：/context 看上下文里装了什么

在 Claude Code 里输入：

```text
/context
```

它会按类别列出当前上下文的占用：系统提示、工具定义、记忆文件（CLAUDE.md 等）、skills 列表、对话消息，以及剩余空间。

刚启动时，对话消息几乎为零，但上下文并不是空的：系统提示和工具定义已经占了一部分。这就是第 9、10 课讲的“每一轮的固定开销”。

现在问一个需要读代码的问题：

```text
OrderService 的 cancel 方法有什么问题？先不要修改代码。
```

回答之后再运行一次 `/context`，比较“消息”一类增加了多少。它读过的每个文件、跑过的每条命令输出，都在这里面。

## 观察二：用 hooks 记录每一次工具调用

hooks 是 Claude Code 在特定时机执行你的脚本的机制，第 18 课会系统地讲。这里先用它做一个“工具调用日志”：每次调用工具之前和之后，往一个文件里追加一行 JSON。

在 order-lab 里创建 `.claude/settings.local.json`（`.local` 结尾的设置文件只对你自己生效，不会提交到 git）：

```sh
mkdir -p .claude
cat > .claude/settings.local.json <<'EOF'
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "",
        "hooks": [{
          "type": "command",
          "command": "jq -c '{time: (now | todate), event: .hook_event_name, agent: .agent_type, tool: .tool_name, input: .tool_input}' >> \"$CLAUDE_PROJECT_DIR/.claude/tool-log.jsonl\""
        }]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "",
        "hooks": [{
          "type": "command",
          "command": "jq -c '{time: (now | todate), event: .hook_event_name, tool: .tool_name, result_chars: (.tool_response | tostring | length), ms: .duration_ms}' >> \"$CLAUDE_PROJECT_DIR/.claude/tool-log.jsonl\""
        }]
      }
    ]
  }
}
EOF
```

原理很简单：工具调用前后，Claude Code 把这次调用的信息以 JSON 的形式写到脚本的标准输入，`jq` 从中挑出几个字段追加到日志文件。`matcher` 为空表示匹配所有工具。

重启 Claude Code（或者输入 `/hooks` 确认它已经识别了这两个 hook），另开一个终端窗口跟踪日志：

```sh
cd ~/order-lab
tail -f .claude/tool-log.jsonl | jq -c '{event, agent, tool, input, result_chars}'
```

然后在 Claude Code 里提一个需要探索的问题：

```text
梳理一下订单状态是怎么流转的，每个状态转换由哪个方法负责、有什么前置条件。
```

日志里会出现一行行工具调用，和第 8 课 MiniAgent 打印的 `→ read_file …` 是同一回事。留意几件事：

- 它先用什么工具定位代码，是 Glob、Grep 还是直接 Read？
- 有没有出现 `Agent` 或类似的子 agent 调用？如果有，子 agent 内部的工具调用也会出现在日志里，`agent` 一列会显示子 agent 的类型（主对话里的调用这一列为 null）。
- `result_chars` 一列告诉你每个工具结果有多大，这些都进入了上下文。

## 观察三：会话记录里的 token 用量

Claude Code 把每个会话完整地保存在本地的一个 JSONL 文件里，位于 `~/.claude/projects/` 下以项目路径命名的目录中。找到最近的一个：

```sh
LOG=$(ls -t ~/.claude/projects/*/*.jsonl | head -1)
echo $LOG
```

统计这个会话里各个工具的调用次数：

```sh
jq -r 'select(.type == "assistant") | .message.content[] | select(.type == "tool_use") | .name' "$LOG" \
  | sort | uniq -c | sort -rn
```

再统计 token 用量。同一次模型回复可能被拆成多行记录，所以先按消息 id 去重：

```sh
jq -s '[.[] | select(.type == "assistant")] | unique_by(.message.id) | map(.message.usage) | {
  requests:    length,
  input:       (map(.input_tokens) | add),
  cache_write: (map(.cache_creation_input_tokens // 0) | add),
  cache_read:  (map(.cache_read_input_tokens // 0) | add),
  output:      (map(.output_tokens) | add)
}' "$LOG"
```

`requests` 是这个会话调用了多少次模型，也就是 agent 循环转了多少圈。`cache_read` 通常远大于其他几项，这就是第 10 课讲的 prompt caching 在起作用。举一个真实的例子：一个持续了几个小时、调用了 215 次模型的长会话，累计读取缓存约 4676 万 token，写入缓存约 60 万，未缓存的输入只有几百 token，输出约 24 万。如果没有缓存，这 4676 万 token 都要按全价计费。

这个文件的格式是 Claude Code 的内部实现，不是公开的接口，版本更新后字段可能变化。用它来观察和学习没有问题，不要在上面构建重要的工具。

## 动手

1. **完成上面三个观察。** 记下第一次 `/context` 时系统提示和工具定义占了多少 token。
2. **比较计划模式。** 按 `Shift+Tab` 切换到计划模式（状态栏显示 `plan mode on`），问同一个状态流转的问题。对比工具日志：计划模式下它用了哪些工具？有没有尝试编辑文件？
3. **观察检查点。** 让它“在 `OrderService` 顶部加一行注释，说明这个类的职责”。改完后按两次 `Esc`，选择回退到这次修改之前，用 `git diff` 确认文件已经恢复。
4. **找出子 agent。** 问一个范围更大的问题，比如“这个项目里所有抛出 `IllegalStateException` 的地方，分别是什么业务规则”。观察它是否把调研交给子 agent，以及主对话的上下文因此增加了多少。

## 小结

- Claude Code 的骨架和 MiniAgent 相同：循环、工具、上下文、权限。区别在工程细节和扩展机制。
- `/context` 按类别显示上下文的占用，是判断“会话是不是太长了”的依据。
- hooks 可以在每次工具调用前后执行脚本，最简单的用法是记录日志。
- 会话记录文件里有每一次请求的 token 用量，可以看到 prompt caching 的效果。
- 检查点可以回退编辑工具做的修改，但不能替代 git。

## 动手练习

1. 修改 PostToolUse 的 hook，只在 `result_chars` 超过 10000 时记录，找出你的会话里“最占上下文”的工具调用是哪些。
2. 用会话记录统计一次真实任务的成本：按第 2 课的价格表，分别计算未缓存输入、缓存写入（1.25 倍）、缓存读取（0.1 倍）和输出的费用。注意 Claude Code 可能使用 1 小时的缓存，写入价格更高，具体以官方文档为准。
3. 打开会话记录文件，找到一条 `tool_use` 和它对应的 `tool_result`（用 `tool_use_id` 对应）。对照第 7 课，说出这一来一回在 API 层面分别是哪个角色的消息。
