第 9 课给 MiniAgent 写了一套工具：列文件、搜索、读文件、精确编辑、写文件、执行命令。第 12 课加上了权限：模式、allow/deny 规则、敏感文件、沙箱。这一课看 opencode 怎么做同样的事。

和上一课一样，代码路径相对于 opencode 仓库根目录，主要在 `packages/opencode/src/tool/` 和 `packages/opencode/src/permission/` 下。实验用上一课下载的 opencode-lab，如果是之前下载的，请重新下载一次，这一课加了一个剧本：

```sh
cd ~ && rm -rf opencode-lab
curl -LO https://windery.github.io/courses/ai-dev/code/opencode-lab.zip
unzip opencode-lab.zip && cd opencode-lab
export OPENCODE_SRC=~/opencode
```

## 工具的定义

所有内置工具都用 `tool/tool.ts` 里的 `Tool.define` 定义。一个工具的定义（`Def`）有这几个字段：

```typescript
export interface Def<Parameters extends Schema.Decoder<unknown> = Schema.Decoder<unknown>, M extends Metadata = Metadata> {
  id: string
  description: string
  parameters: Parameters
  jsonSchema?: JSONSchema7
  execute(args: Schema.Schema.Type<Parameters>, ctx: Context): Effect.Effect<ExecuteResult<M>>
  formatValidationError?(error: unknown): string
}
```

和 MiniAgent 的 `AgentTool` 记录对照：

| MiniAgent（第 9 课） | opencode |
| --- | --- |
| `Tool definition`（名字、描述、JSON Schema） | `id`、`description`、`parameters`（Effect Schema，自动转成 JSON Schema） |
| `boolean readOnly` | 没有这个字段，读写的区别完全由权限规则表达 |
| `Handler handler` | `execute(args, ctx)`，`ctx` 里有会话 id、中断信号、`ask`（请求权限）等 |

**描述放在单独的文本文件里。** 每个工具都有一个同名的 `.txt` 文件，比如 `read.txt`、`edit.txt`，用 `import DESCRIPTION from "./read.txt"` 引入。上一课的实验里看到，`bash` 工具的描述有 4600 多个字符，`task` 有 3000 多个，几乎是一份小型的使用手册。第 9 课讲 ACI（agent 与计算机的接口）时说过，工具描述是写给模型看的文档，值得像写提示词一样认真写。opencode 把它们放在单独的文件里，方便修改和比较。

`bash` 工具的描述还是一个模板，里面的操作系统、默认超时、输出截断的上限，都在运行时填入实际的值。这样描述里写的数字和代码的实际行为永远一致。

**统一的参数校验和输出截断。** `Tool.define` 返回的工具会被包装一层（`tool.ts` 第 99 到 149 行）：先用 Schema 校验模型传来的参数，不合法时返回一条告诉模型“请按 schema 重写参数”的错误；执行完成后，如果工具自己没有截断输出，统一按上限截断。第 9 课 MiniAgent 的每个工具各自处理这些事，opencode 把它们集中到了一个地方。

### 注册与筛选

`tool/registry.ts` 把所有工具汇总起来。除了内置工具，还会加载：

- 配置目录下 `tool/` 或 `tools/` 里的 `.ts`、`.js` 文件（自定义工具）；
- 插件提供的工具（第 27 课）；
- MCP 服务器提供的工具（第 27 课）。

然后按模型筛选。一个有意思的例子：模型 id 里带 `gpt-` 的 OpenAI 模型（排除了 `gpt-4` 和开源的 `oss` 系列），`edit` 和 `write` 会被替换成 `apply_patch`，因为这些模型训练时更熟悉补丁格式。第 4 课讲过，不同模型的训练方式不同，对工具的偏好也不同；opencode 为每一类模型准备不同的系统提示（下一课）和不同的编辑工具。

最后按 agent 的权限筛选：如果一个工具在某个 agent 的权限规则里被整体禁止（规则是 `"*": "deny"`），这个工具就不会发给模型。模型看不到的工具，自然也不会去调用。

## 三个核心工具

### read：读文件

`tool/read.ts` 的几个上限：

```typescript
const DEFAULT_READ_LIMIT = 2000
const MAX_LINE_LENGTH = 2000
const MAX_LINE_SUFFIX = `... (line truncated to ${MAX_LINE_LENGTH} chars)`
const MAX_BYTES = 50 * 1024
```

默认读 2000 行，单行超过 2000 字符截断，总共不超过 50KB。上一课的实验里看到了它的输出格式：

```text
<path>/…/demo/hello.txt</path>
<type>file</type>
<content>
1: hello from the demo project

(End of file - total 1 lines)
</content>
```

每行前面加行号，末尾告诉模型“文件结束了，一共几行”；没读完时则提示“显示了第几到第几行，用 offset 继续”。这和第 9 课 MiniAgent 的 read_file 是同一个思路：**让模型知道自己看到的是全部还是一部分**。

还有几个 MiniAgent 没做的细节：

- **二进制文件**：按扩展名（`.zip`、`.class`、`.jar` 等）或内容（含有空字节，或超过 30% 的不可打印字符）识别，拒绝读取。
- **图片和 PDF**：作为附件发给模型，多模态模型可以直接“看”。
- **文件不存在**：给出最多 3 个名字相近的文件作为建议。模型拼错路径时，这比一句“文件不存在”有用得多。
- **读到子目录时附带该目录的 AGENTS.md**：下一课细讲。

### edit：精确编辑

`tool/edit.ts` 的参数和 MiniAgent 的 edit_file 一样：`filePath`、`oldString`、`newString`，外加一个 `replaceAll`。文件第一行注释写着，它的匹配策略参考了 Cline 和 gemini-cli 两个开源 agent。核心是 `replace` 函数：

```typescript
for (const replacer of [
  SimpleReplacer,
  LineTrimmedReplacer,
  BlockAnchorReplacer,
  WhitespaceNormalizedReplacer,
  IndentationFlexibleReplacer,
  EscapeNormalizedReplacer,
  TrimmedBoundaryReplacer,
  ContextAwareReplacer,
  MultiOccurrenceReplacer,
]) {
  for (const search of replacer(content, oldString)) {
    const index = content.indexOf(search)
    if (index === -1) continue
    notFound = false
    // ……匹配范围比 oldString 大得多时拒绝
    if (replaceAll) {
      return content.replaceAll(search, newString)
    }
    const lastIndex = content.lastIndexOf(search)
    if (index !== lastIndex) continue
    return content.substring(0, index) + newString + content.substring(index + search.length)
  }
}
```

第 9 课的 MiniAgent 只做精确匹配：`oldString` 必须在文件里出现且只出现一次。opencode 依次尝试 9 种匹配策略，从严格到宽松：

| 策略 | 容忍什么 |
| --- | --- |
| `SimpleReplacer` | 不容忍，精确匹配 |
| `LineTrimmedReplacer` | 每行首尾的空白不同 |
| `BlockAnchorReplacer` | 首尾两行对得上，中间部分足够相似（编辑距离相似度达到阈值） |
| `WhitespaceNormalizedReplacer` | 空白字符的数量和种类不同 |
| `IndentationFlexibleReplacer` | 整体缩进不同 |
| `EscapeNormalizedReplacer` | `\n`、`\t` 等转义写法不同 |
| `TrimmedBoundaryReplacer` | 整段首尾的空白不同 |
| `ContextAwareReplacer` | 用上下文行定位（至少 3 行） |
| `MultiOccurrenceReplacer` | 配合 `replaceAll` 处理多处出现 |

为什么要这么宽松？因为模型复制代码时经常出现细微偏差：缩进少了一级、行尾多了空格、把真正的换行写成了 `\n`。严格匹配会让这些编辑失败，模型只能重读文件再试，浪费步数和 token。宽松匹配则用更复杂的逻辑换来了更高的成功率。

宽松也有风险：可能匹配到错误的位置。opencode 用两道保护控制这个风险：每种策略找到的匹配仍然必须**唯一**（`index !== lastIndex` 时跳过）；匹配到的范围如果比 `oldString` 大得多，直接拒绝，并让模型重读文件。

编辑成功之后，opencode 还会做两件 MiniAgent 没做的事：如果配置了格式化工具，就格式化这个文件；如果启用了 LSP（语言服务器），就收集这个文件的诊断信息，有错误时附在工具结果后面：“LSP errors detected in this file, please fix”。这和第 18 课用 PostToolUse hook 在编辑后编译、把错误交给 Claude 是同一个思路，只是 opencode 把它内置了。这两项在 opencode 里默认都是关闭的，要在配置里打开。

**一个值得注意的细节。** `edit.txt` 里写着“如果没有先读文件就编辑，这个工具会报错”。但在这个版本的代码里，并没有检查“是否读过文件”的逻辑。描述和实现不一致，可能是重构时遗漏了。读开源代码时，**提示词、文档和代码说的不一定是同一件事，以代码为准**。后面讲权限时还会遇到一个类似的例子。

### bash：执行命令

`tool/shell.ts` 实现了执行命令的工具，为了兼容旧配置，工具名和权限名仍然叫 `bash`。

- **超时**：默认 2 分钟，模型可以通过 `timeout` 参数指定更长的时间。超时后先发终止信号，3 秒后强制结束，并在输出里提示模型“可以用更大的 timeout 重试”。
- **工作目录**：通过 `workdir` 参数指定，提示词明确要求模型不要写 `cd xxx && 命令`，而是用 `workdir`。这样权限检查看到的是真正要执行的命令。
- **输出截断**：上限是 2000 行或 50KB。超过时保留**最后**一段，前面加上 `...output truncated...` 和完整输出保存的文件路径。完整输出存在 opencode 数据目录下的 `tool-output/` 里，保留 7 天，模型需要时可以用 read 或 grep 去查。

第 9 课 MiniAgent 的 run_command 保留开头和结尾（`headAndTail`），opencode 只保留结尾。两种取舍各有道理：命令的错误信息和结果通常在最后，只保留结尾更省空间；而把完整输出存成文件，等于把“开头”也留给了模型，只是需要它主动去读。

## 权限

### 规则的格式

在 `opencode.json` 里配置：

```json
{
  "permission": {
    "edit": "ask",
    "bash": {
      "*": "ask",
      "git status *": "allow",
      "rm *": "deny"
    }
  }
}
```

每个工具对应一个权限名（`read`、`edit`、`bash`、`task`、`webfetch` 等），值可以是一个动作（`allow`、`ask`、`deny`），也可以是“模式到动作”的映射。`edit`、`write`、`apply_patch` 共用 `edit` 这个权限名。

### 匹配：最后一条匹配的规则生效

判断逻辑在 `permission/index.ts`，只有几行：

```typescript
export function evaluate(permission: string, pattern: string, ...rulesets: PermissionV1.Ruleset[]): PermissionV1.Rule {
  return (
    rulesets
      .flat()
      .findLast((rule) => Wildcard.match(permission, rule.permission) && Wildcard.match(pattern, rule.pattern)) ?? {
      action: "ask",
      permission,
      pattern: "*",
    }
  )
}
```

把所有规则排成一列，**从后往前找第一条匹配的**，找不到就是 `ask`。所以规则的顺序很重要：通配的 `"*"` 写在前面，具体的规则写在后面。规则的来源依次是：内置默认值、agent 自己的规则、用户配置、会话级别的规则，越靠后优先级越高。

这和第 12 课 MiniAgent 的设计不同。MiniAgent 是“deny 优先”：任何一条 deny 规则匹配，就直接拒绝，不管 allow 规则怎么写。Claude Code 也是 deny 优先（第 18 课）。opencode 是“最后匹配优先”，好处是表达力强，可以先禁止一大类、再放行其中几个；代价是顺序错了，后面一条宽泛的 allow 就可能覆盖掉前面的 deny。

通配符的规则在 `packages/core/src/util/wildcard.ts`：`*` 匹配任意字符（包括 `/`），`?` 匹配一个字符；模式以 `" *"` 结尾时，后面的参数是可选的，所以 `git status *` 也匹配不带参数的 `git status`。这和 Claude Code 的 `Bash(ls *)` 也匹配 `ls` 是一样的设计。

### 默认规则：几乎全部允许

这是 opencode 和 Claude Code 最大的区别之一。`agent/agent.ts` 里的默认规则是：

```typescript
const defaults = Permission.fromConfig({
  "*": "allow",
  doom_loop: "ask",
  external_directory: {
    "*": "ask",
    ...Object.fromEntries(whitelistedDirs.map((dir) => [dir, "allow"])),
  },
  question: "deny",
  plan_enter: "deny",
  plan_exit: "deny",
  read: {
    "*": "allow",
    "*.env": "ask",
    "*.env.*": "ask",
    "*.env.example": "allow",
  },
})
```

**默认所有操作都允许**，包括编辑文件和执行任意命令。只有三类情况会询问：读 `.env` 文件、访问项目目录之外的路径（`external_directory`）、疑似死循环（`doom_loop`，后面讲）。Claude Code 在 Manual 模式下，编辑文件和执行命令都要先问你；新版本默认的 auto 模式也不是直接放行，而是由一个分类器模型代替你审查每个操作（第 12 课）。如果你要在自己的机器上用 opencode，至少应该把 `edit` 和 `bash` 改成 `ask`，再逐步放行常用的命令。

这里又有一个文档和代码不一致的地方：官方文档（`packages/web/src/content/docs/permissions.mdx`）说 `.env` 文件默认是**拒绝**的，代码里却是**询问**。用实验验证一下：

```sh
./run.sh 06-env "看看 .env"
```

```text
! permission requested: read (.env); auto-rejecting
✗ Read …/demo/.env failed
Error: The user rejected permission to use this specific tool call.
```

是询问（`permission requested`），只是 `opencode run` 是非交互模式，没有人可以回答，所以自动拒绝了。交互模式下，你会看到一个让你选择的提示。

### bash 命令怎么检查

第 12 课的 MiniAgent 用字符串处理把复合命令按 `&&`、`||`、`;`、`|` 拆开，每一段分别检查。opencode 用的是 **tree-sitter**：一个真正的语法解析器，把命令解析成语法树，再找出树里的每一个命令节点。这样子 shell、`$(...)`、引号里的特殊字符都能正确处理，比字符串拆分可靠得多。

对每一段命令，opencode 生成两样东西：

- 用于检查的模式：命令的原文，比如 `rm hello.txt`；
- 用户选择“总是允许”时记住的模式：取命令的“有意义的前缀”再加 ` *`。哪些词算前缀，由 `permission/arity.ts` 里的一张表决定，比如 `git` 是 2 个词，`npm run` 是 3 个词，所以 `git checkout main` 记住的是 `git checkout *`，`npm run dev` 记住的是 `npm run dev *`。

`arity.ts` 里有一段注释很有意思：这张一百多个命令的表，是用一段提示词让模型生成的，提示词就保存在注释里。

运行实验包的第二个剧本：

```sh
./run.sh 02-deny "删掉 hello.txt"
```

```text
✗ ls && rm hello.txt failed
Error: The user has specified a rule which prevents you from using this specific tool call. Here are some of the relevant rules [{"permission":"*","action":"allow","pattern":"*"},{"permission":"bash","pattern":"*","action":"allow"},{"permission":"bash","pattern":"rm *","action":"deny"}]

$ ls | wc -l
3
删除被规则拒绝了，目录里还有这些文件。
```

实验包的 `opencode.json` 配置了 `"bash": { "*": "allow", "rm *": "deny" }`。`ls && rm hello.txt` 被拆成 `ls` 和 `rm hello.txt` 两段，`ls` 被允许，`rm hello.txt` 匹配了 deny 规则，**整条命令都被拒绝**，`ls` 也没有执行。拒绝的原因连同相关的规则作为工具结果返回给模型，模型可以据此换一种做法，循环继续。

注意两种“拒绝”的区别（`session/processor.ts` 的 `failToolCall`）：

- **规则拒绝**（deny）：工具结果是一条错误信息，循环继续，模型可以调整做法。
- **用户拒绝**（在询问时选择 Reject）：循环**停止**，等待用户的下一条消息。上面 `.env` 的例子就是这种情况。

这个区分很合理。规则拒绝是一个预期之内的约束，让模型自己绕开就好；用户拒绝说明 agent 的方向可能错了，应该停下来听用户的。

### 询问用户

需要询问时，`permission/index.ts` 的 `ask` 函数创建一个 `Deferred`（上一课讲过，相当于 `CompletableFuture`），发布一个 `permission.asked` 事件，然后等待。终端界面收到事件，显示三个选项：

- **Allow once**：只允许这一次；
- **Allow always**：允许，并把上面说的“前缀 + `*`”模式加入本会话的允许列表，同一会话里其他正在等待的、现在已经被允许的请求也会自动通过；
- **Reject**：拒绝，可以附带一段说明告诉模型为什么。同一会话里其他正在等待的请求也会一起被拒绝。

用户的回答通过 `POST /permission/{requestID}/reply` 发回服务端，完成那个 `Deferred`，工具继续执行或者失败。因为是客户端与服务端的结构，回答可以来自任何一个客户端：终端、网页，甚至是你用 SDK 写的程序。

### 项目目录之外

`tool/external-directory.ts` 检查路径是否在项目目录之内。read、edit 等工具访问项目之外的文件，bash 命令里的 `rm`、`cp`、`mv` 等文件命令的参数指向项目之外，都会触发 `external_directory` 权限，默认询问。第 12 课 MiniAgent 的 `resolve()` 也检查了路径是否越界，并且检查了符号链接的真实路径。

### 死循环检测

`session/processor.ts` 在处理每个 `tool-call` 事件时检查：当前这条助手消息的最后 3 个 part 是不是都在调用同一个工具，并且参数完全相同。如果是，触发 `doom_loop` 权限，默认询问用户。

```sh
./run.sh 05-doom-loop "反复读 hello.txt"
```

```text
! permission requested: doom_loop (read); auto-rejecting
Error: The user rejected permission to use this specific tool call.
```

剧本让模型在一次回复里三次调用完全相同的 read。检查的范围是一条助手消息内部，而每一步模型调用都会创建一条新的助手消息，所以这个检测只能发现“一次回复里的重复调用”，发现不了“连续几步都在做同一件事”。后者要靠步数上限和用户的观察。

### 计划模式

opencode 的计划模式是一个叫 `plan` 的 agent，在终端界面里按 Tab 切换。它的权限规则是：

```typescript
edit: {
  "*": "deny",
  ".opencode/plans/*.md": "allow",
  // ……以及数据目录下的 plans/*.md
},
```

除了计划文件，所有编辑都被拒绝。但是 `bash` 没有被限制，`sed -i`、`echo >` 这类命令理论上仍然可以修改文件。对此 opencode 依靠提示词：进入计划模式时，往用户消息里追加一段提醒，“CRITICAL: Plan mode ACTIVE - you are in READ-ONLY phase…”，明确禁止用 sed、tee、echo 等修改文件（`session/prompt/plan.txt`）。

第 11、12 课的 MiniAgent 在计划模式下同时用了两层保护：提示词告诉模型只读，代码在执行时拦截所有写操作和非只读命令。opencode 对编辑工具用了代码拦截，对 bash 只用了提示词。第 3 课讲过，提示词是“建议”，代码才是“保证”。

### 沙箱

在这个版本的 opencode 里，没有找到容器或系统级的沙箱。安全边界就是权限规则和项目目录检查。第 12 课给 MiniAgent 加了 Docker 沙箱；Claude Code 也提供了沙箱功能。如果你要让 opencode 在无人值守的情况下运行（比如 CI），要自己把它放进容器里。

## 三方对照

## 动手

1. **改规则顺序。** 把实验包根目录下 `opencode.json` 里的 bash 规则改成 `{ "rm *": "deny", "*": "allow" }`（顺序反过来），再运行 `./run.sh 02-deny "删掉 hello.txt"`。结果有什么不同？为什么？（`run.sh` 每次运行都会把它复制到 `demo/` 下。做完后把规则改回来，并删掉 `demo/` 目录，下次运行会重新创建。）
2. **收紧默认权限。** 在 `opencode.json` 里加上 `"edit": "ask"`，写一个剧本让模型调用 `write` 工具创建一个文件，看看非交互模式下会发生什么。
3. **读匹配策略。** 打开 `tool/edit.ts`，读 `LineTrimmedReplacer` 和 `BlockAnchorReplacer` 的实现。写一个 `oldString` 例子，它会被 `BlockAnchorReplacer` 匹配上，但不会被前两种匹配上。
4. **查前缀表。** 打开 `permission/arity.ts`，找到 `mvn`、`gradle`、`docker` 各是几个词。对 `mvn -q test`，“总是允许”会记住什么模式？

## 小结

- opencode 的工具由 `Tool.define` 定义，参数用 Effect Schema 描述，长描述放在单独的文本文件里；注册时按模型和 agent 的权限筛选，模型看不到被整体禁止的工具。
- read 有行数、行长和字节数三重上限，并告诉模型是否读完；edit 依次尝试 9 种匹配策略，用“必须唯一”和“匹配范围不能过大”控制风险；bash 保留输出的结尾，完整输出存成文件。
- 权限规则是“最后匹配的生效”，默认几乎全部允许；bash 命令用 tree-sitter 解析，任何一段被拒绝，整条命令都不执行。
- 规则拒绝时模型可以调整做法、循环继续；用户拒绝时循环停止。
- 提示词、文档和代码不一定一致，以代码为准，并且用实验验证。
