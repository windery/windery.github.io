前几课的实践，有不少需要你每次在提示词里重复：怎么跑测试、金额用 BigDecimal、修 bug 要先写失败的测试。这一课把它们沉淀成项目配置，提交到 git，整个团队都能用。

Claude Code 的扩展机制有好几种，第一次接触容易混淆。用第二部分的视角看，它们其实就是在回答同一个问题：**什么内容、在什么时候、以什么方式进入上下文，或者在上下文之外强制执行。**

## 先选对机制

| 机制 | 什么时候进入上下文 | 适合放什么 | 对应第二部分 |
| --- | --- | --- | --- |
| CLAUDE.md | 每个会话启动时，全部加载 | 每次都需要的约定：构建命令、代码风格、项目陷阱 | 第 10 课的 AGENTS.md |
| `.claude/rules/` | 启动时加载；带 `paths` 的规则在读到匹配文件时才加载 | 按主题或按目录拆分的约定 | 第 10 课 |
| Skills | 启动时只加载名字和描述，用到时才加载全文 | 某类任务的工作流程、领域知识 | 新机制 |
| 子 agent | 在独立的上下文中运行，只返回结果 | 需要读很多文件的调研、独立的审查 | 第 11 课的 `task` |
| MCP | 工具名称先进入上下文，定义按需加载 | 接入外部系统：issue、数据库、文档 | 第 7 课的工具 |
| Hooks | 不进入上下文，在特定时机执行脚本 | 必须每次执行、不能有例外的规则 | 第 12 课的拦截、第 16 课的关卡 |
| 权限设置 | 不进入上下文，由程序判断 | 哪些操作自动放行、哪些禁止 | 第 12 课的 allow/deny |

选择的原则来自第 10 课的上下文成本和第 11 课的“提示词引导、代码保证”：

- **每次都要用的** → CLAUDE.md。但它每轮都占上下文，要短。
- **有时才用的** → skills 或带 `paths` 的 rules，用到时再加载。
- **会读很多东西、但只需要结论的** → 子 agent。
- **不能有例外的** → hooks 或权限设置。CLAUDE.md 里的规则是建议，hooks 是强制。

## CLAUDE.md：只写模型猜不到的

在项目里运行 `/init`，Claude Code 会分析项目结构，生成一份初始的 CLAUDE.md。这是个不错的起点，但生成的内容往往偏多，需要删减。

官方最佳实践给了一个检验每一行的问题：**删掉这一行，Claude 会因此犯错吗？** 如果不会，就删掉。

| 应该写 | 不应该写 |
| --- | --- |
| 它猜不到的命令（比如只跑单个测试的写法） | 读代码就能知道的东西 |
| 和通常做法不同的代码风格 | 语言的标准约定 |
| 测试的要求和偏好的测试方式 | 详细的 API 文档（给链接即可） |
| 分支命名、提交信息等仓库约定 | 经常变化的信息 |
| 项目特有的架构决定 | 长篇的解释和教程 |
| 开发环境的特殊之处（必需的环境变量等） | 逐个文件的说明 |
| 不明显的陷阱 | “写干净的代码”这类空话 |

CLAUDE.md 写得太长，重要的规则反而会被淹没，这和第 5 课讲的长上下文问题是同一个道理。如果它一直不遵守某条规则，先检查文件是不是太长了。

order-lab 的 CLAUDE.md 可以这样写：

```markdown
# order-lab

## 命令
- 全部测试：`mvn -q test`（成功时没有输出）
- 单个测试：`mvn -q -Dtest=OrderServiceTest#方法名 test`

## 约定
- 金额一律用 BigDecimal，计算结果保留两位小数，HALF_UP。
- 时间通过注入的 Clock 获取，测试中用 Clock.fixed，不要直接调用 Instant.now()。
- 业务规则变化时，同步更新 README.md 里的规则说明。

## 工作方式
- 修 bug：先写能复现问题的失败测试，确认失败后再修复，不修改这个测试。
- 不要修改已有测试的断言来让测试通过；如果认为测试本身有误，先说明理由。

## Compact Instructions
压缩时保留：修改过的文件列表、测试命令、用户做出的业务决定。
```

几个相关的细节：

- **位置和作用范围**：`~/.claude/CLAUDE.md` 对你的所有项目生效；项目根目录的 `CLAUDE.md` 提交到 git，团队共享；`CLAUDE.local.md` 放个人在这个项目里的偏好，记得加进 `.gitignore`。
- **导入其他文件**：在 CLAUDE.md 里写 `@docs/architecture.md`，这个文件会在启动时一起加载。
- **AGENTS.md**：如果项目已经有给其他 agent 用的 AGENTS.md、又没有 CLAUDE.md，Claude Code 会读 AGENTS.md。两者都有时默认只读 CLAUDE.md，可以在 CLAUDE.md 里用 `@AGENTS.md` 导入它。
- **运行 `/context` 或 `/memory`** 可以确认哪些记忆文件被加载了。

### 按路径加载的规则

只和某些文件有关的约定，放进 `.claude/rules/`，用 `paths` 限定范围。比如测试代码的规范：

```markdown
---
paths:
  - "src/test/**/*.java"
---
# 测试规范
- 测试方法名用英文描述行为，例如 cancelShippedOrderIsRejected。
- 每个测试只验证一个行为。
- 不使用 Mockito，order-lab 的依赖都可以直接构造。
```

保存为 `.claude/rules/testing.md`。只有当 Claude 读取或编辑匹配的测试文件时，这份规则才会进入上下文。

## Skills：按需加载的工作流程

Skill 是一个目录，里面有一个 `SKILL.md`：开头的 YAML 写名字和描述，正文写具体的做法。会话启动时只有描述进入上下文，Claude 判断用得上时，或者你用 `/名字` 调用时，才加载全文。这正是第 10 课“只放每次都需要的内容”的延伸：把有时才用的知识从 CLAUDE.md 里挪出来。

给 order-lab 写一个“新增业务规则”的流程，保存为 `.claude/skills/add-rule/SKILL.md`：

```markdown
---
name: add-rule
description: 为订单服务新增或修改一条业务规则（折扣、状态流转、校验等）的标准流程。
disable-model-invocation: true
---
为订单服务实现这条业务规则：$ARGUMENTS

按以下步骤进行，每一步完成后简要汇报：
1. 用自己的话复述规则，列出边界情况。有歧义的地方先问我，不要自行假设。
2. 先写测试：每条规则和每个边界情况各一个测试。运行 `mvn -q test`，确认新测试失败。
3. 实现规则，直到 `mvn -q test` 全部通过。
4. 更新 README.md 中的规则说明。
5. 贴出最后一次 `mvn -q test` 的输出和 `git diff --stat`。
```

- `$ARGUMENTS` 会被替换成调用时的参数：`/add-rule 订单创建超过 30 分钟未支付不能再支付`。
- `disable-model-invocation: true` 表示只能由你手动调用，Claude 不会自己触发它。有副作用的流程适合这样设置。
- 不设置它的 skill，Claude 会根据描述自动判断何时使用。所以**描述要写清楚“什么时候用”**，这和第 9 课写工具描述是一回事。

Skill 也可以放在 `~/.claude/skills/` 下，对你的所有项目生效。本站的 [mattpocock/skills 项目解读](/projects/mattpocock-skills/01/) 介绍了一套现成的 skills，其中的 grill 系列就是第 14 课“让 agent 采访你”的一种成熟写法。

## 子 agent：独立上下文里的专门角色

第 11 课的 `task` 工具是一个固定的调研子 agent。Claude Code 允许你在 `.claude/agents/` 下定义自己的子 agent，每个都有自己的系统提示和工具范围。比如一个只读的测试审查员，保存为 `.claude/agents/test-reviewer.md`：

```markdown
---
name: test-reviewer
description: 审查测试是否覆盖了改动涉及的业务规则。在实现完成、提交之前使用。
tools: Read, Grep, Glob, Bash
---
你是一名严格的测试审查员。阅读 git diff 和相关的测试代码，回答：
1. 改动涉及的每一条业务规则，是否都有测试覆盖？列出没有覆盖的。
2. 有没有测试被修改了断言？如果有，修改是否合理？
3. 边界值（0、负数、刚好等于门槛、四舍五入）是否被测试到？
只报告问题，不要修改任何文件。
```

使用时直接说：“用 test-reviewer 子 agent 审查当前的改动。”`tools` 字段限制了它能用的工具，即使它想修改文件也做不到。这是第 11 课 EXPLORER 配置的完整版。

## MCP：接入外部系统

MCP（Model Context Protocol）是一个开放协议，让外部程序以标准的方式向 agent 提供工具。回想第 7 课：工具就是名字、描述和参数 schema，加上一段执行逻辑。MCP 把“执行逻辑”放到了另一个进程甚至另一台服务器上，agent 通过协议调用它。这样，同一个 MCP server 可以同时给 Claude Code、opencode 和其他支持 MCP 的工具使用。

添加一个远程的 MCP server：

```sh
claude mcp add --transport http <名字> <URL>
# 例如官方文档中的示例：
claude mcp add --transport http notion https://mcp.notion.com/mcp
```

添加一个在本地运行的 MCP server（`--` 之后是启动它的命令）：

```sh
claude mcp add --transport stdio <名字> -- <启动命令> [参数...]
```

默认只对你在当前项目中生效；加上 `--scope project` 会写入项目根目录的 `.mcp.json`，可以提交给团队。`claude mcp list` 查看已配置的 server，会话中输入 `/mcp` 查看连接状态。

两个使用建议：

- **能用命令行工具就用命令行工具。** 官方最佳实践指出，`gh`、`aws` 这类 CLI 是和外部服务交互最节省上下文的方式。比如操作 GitHub，装好 `gh` 并登录，Claude 就会用它来查 issue、开 PR。
- **MCP 的工具定义也占上下文。** Claude Code 默认只把 MCP 工具的名字放进上下文，用到时再加载完整定义，但 server 和工具多了仍然会有开销。只添加你真正需要的。

## Hooks：必须执行的规则

第 13 课用 hooks 记录日志，第 16 课用 Stop hook 做测试关卡。这里再加一个常用的：**每次修改 Java 文件后立即编译**，把编译错误马上反馈给 Claude，而不是等到最后跑测试才发现。

`.claude/hooks/compile.sh`：

```bash
#!/bin/bash
# PostToolUse hook：每次改完 .java 文件就编译一次，编译失败时把错误交给 Claude。
FILE=$(jq -r '.tool_input.file_path // empty')
[[ "$FILE" == *.java ]] || exit 0

cd "$CLAUDE_PROJECT_DIR" || exit 0
if ! OUTPUT=$(mvn -q test-compile 2>&1); then
  echo "编译失败（mvn -q test-compile）：" >&2
  echo "$OUTPUT" | grep -E '\.java:\[|symbol|location' | awk '!seen[$0]++' | head -20 >&2
  exit 2
fi
exit 0
```

`PostToolUse` 发生在工具执行之后，退出码 2 不能阻止已经完成的编辑，但会把标准错误输出交给 Claude，它会接着修复编译错误。

把它和第 16 课的 Stop hook 一起注册到 `.claude/settings.json`，同时加上团队共享的权限规则：

```json
{
  "permissions": {
    "allow": [
      "Bash(mvn -q test *)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "deny": [
      "Bash(git push *)",
      "Read(./.env)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/compile.sh" }]
      }
    ],
    "Stop": [
      {
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/verify.sh" }]
      }
    ]
  }
}
```

权限规则的写法和第 12 课的 MiniAgent 很像：`Bash(mvn -q test *)` 允许 `mvn -q test` 本身以及在它后面加参数的命令；deny 规则在任何权限模式下都生效。和 MiniAgent 一样，Claude Code 也会识别 `&&`、`;` 这类复合命令，不会因为开头匹配就放行整条命令。

hook 脚本会以你的身份、在你的机器上执行任意命令，所以**不要随便运行别人仓库里的 hooks**。Claude Code 在你第一次信任一个目录时会提示这一点。

## 哪些文件提交到 git

| 提交，团队共享 | 不提交，只给自己用 |
| --- | --- |
| `CLAUDE.md` | `CLAUDE.local.md` |
| `.claude/settings.json` | `.claude/settings.local.json` |
| `.claude/rules/`、`.claude/skills/`、`.claude/agents/`、`.claude/hooks/` | `~/.claude/` 下的个人配置 |
| `.mcp.json` | |

把这些配置当成代码对待：通过 PR 修改，出了问题回头检查。官方的建议是，Claude 一直不遵守某条规则时，检查 CLAUDE.md 是不是太长了；它总问 CLAUDE.md 里已经写了的问题时，检查措辞是不是有歧义。

## 动手

在 order-lab 里：

1. **CLAUDE.md。** 先运行 `/init`，看它生成了什么；然后对照本课的表格删改，或者直接使用上面的示例。开一个新会话，运行 `/context` 确认它被加载了。
2. **规则和 skill。** 创建 `.claude/rules/testing.md` 和 `.claude/skills/add-rule/SKILL.md`，然后运行：

   ```text
   /add-rule 订单创建超过 30 分钟仍未支付的，不能再支付
   ```

   观察它是否按 skill 的步骤进行，是否先问你“30 分钟整算不算超时”这类边界问题。
3. **hooks。** 安装 `compile.sh` 和第 16 课的 `verify.sh`，写好 `.claude/settings.json`。让它做一个修改，故意在提示词里要求“调用 `Order` 的 `getTotal()` 方法”（这个方法不存在），观察编译 hook 的反馈如何让它修正。
4. **子 agent。** 创建 `test-reviewer`，在第 2 步完成后让它审查改动。
5. **提交配置。** 把应该共享的文件提交到 git，用 `git status` 确认个人文件没有被提交。

## 小结

- 每种扩展机制回答的是：什么内容、在什么时候进入上下文，或者在上下文之外强制执行。
- CLAUDE.md 每次都加载，只写模型猜不到、删了会出错的内容；有时才用的知识放进 skills 或带 `paths` 的 rules。
- 子 agent 有独立的上下文和工具范围，适合调研和审查。
- MCP 让外部系统以标准方式提供工具；能用 CLI 时优先用 CLI。
- 不能有例外的规则用 hooks 和权限设置实现，CLAUDE.md 里的规则只是建议。

## 动手练习

1. 完成五个实验，把 order-lab 的 `.claude/` 目录结构画出来，标出每个文件属于哪种机制。
2. 检查你自己项目的 CLAUDE.md（如果没有，用 `/init` 生成一份），用“删掉会出错吗”逐行检验，看能删掉多少。
3. 把你在工作中经常重复的一个流程（比如“新增一个 REST 接口”“排查一次慢 SQL”）写成一个 skill。想一想它应该允许 Claude 自动调用，还是只能手动调用。
