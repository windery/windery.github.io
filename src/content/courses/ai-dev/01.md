这门课写给已经能独立交付后端服务的 Java 工程师。目标不是训练模型，而是把大模型当成一种新的基础能力，接进真实的业务系统，并让它像其他服务一样可靠、可测、可控。

## AI 开发工程师到底做什么

“做 AI”在招聘里至少指三种岗位，它们需要的知识差别很大：

| 岗位 | 主要工作 | 核心技能 |
| --- | --- | --- |
| 算法 / 研究工程师 | 设计和训练模型 | 数学、深度学习框架、实验方法 |
| ML 平台工程师 | 训练与推理基础设施 | GPU 集群、分布式训练、模型服务 |
| **AI 应用开发工程师** | 用现成模型构建产品功能 | API 集成、Prompt、工具调用、RAG、评测、工程化 |

这门课针对第三种。它的日常工作看起来是这样的：

- 把“自动回复客服工单”这样的需求，拆成模型能稳定完成的步骤。
- 设计发给模型的指令和上下文，让输出能被程序解析。
- 让模型调用内部接口（查订单、建工单），并控制它能做什么、不能做什么。
- 把公司文档接入检索系统，让回答有依据。
- 建立评测集，在换模型、改 prompt 之后知道效果是变好还是变差。
- 处理限流、超时、成本和安全问题，让功能能上线并持续运行。

可以看到，后半部分全是后端工程问题。模型本身是买来的，真正的工作量在模型之外。

## 哪些后端经验可以直接迁移

转型最常见的误区是以为要从头学起。实际上，你已经掌握的东西大部分仍然有用：

| 你已经会的 | 在 AI 开发中的对应 |
| --- | --- |
| 调用第三方 HTTP 服务 | 模型就是一个按 token 计费的远程服务 |
| 接口契约、DTO、JSON 序列化 | 结构化输出、工具的参数 schema |
| 超时、重试、熔断、限流 | 模型调用会慢、会 429、会过载，同样需要这些 |
| 日志、链路追踪、指标 | 记录每次调用的输入输出、token 用量和耗时 |
| 单元测试、集成测试 | Eval：用一组样例给模型输出打分，防止回归 |
| 权限控制、输入校验 | 防 prompt injection，限制工具权限 |
| 数据库与搜索（MySQL、ES） | RAG 的检索层，向量库只是多了一种索引 |

真正需要新建立的直觉只有几条：

1. **输出是概率性的。** 同样的输入可能得到不同的输出，不能像普通函数那样只写一个断言。
2. **上下文就是全部状态。** 模型不记得上一次调用，你发什么，它就只知道什么。
3. **自然语言也是接口。** Prompt 的措辞会改变系统行为，需要像代码一样版本管理和测试。
4. **成本按用量计算。** 每次调用的费用取决于输入和输出的 token 数量，设计时就要考虑。

## 课程结构

课程分六个部分，前一部分是后一部分的基础：

1. **从后端视角认识大模型**：模型怎么工作，API 长什么样，第一次调用。
2. **Prompt 与结构化输出**：让输出稳定、可解析，控制成本和延迟。
3. **工具调用与 Agent**：让模型调用你的代码，理解 agent 循环和 MCP。
4. **RAG 与知识接入**：embedding、检索、向量存储和质量问题。
5. **评估与生产化**：eval、可观测性、安全和上线。
6. **Java 生态与实战**：Spring AI、LangChain4j，以及一个综合项目。

前五部分直接使用模型厂商的 API 和官方 SDK，先看清协议本身；第六部分再介绍框架。这样当框架帮你隐藏了细节时，你知道它隐藏的是什么。

## 课程用到的工具

- **Java 17 或更高版本**，Maven 或 Gradle。示例以 Java 为主，必要时用 curl 展示原始 HTTP 请求。
- **Claude API**：示例使用 Anthropic 的 Messages API 和官方 Java SDK（`com.anthropic:anthropic-java`）。概念在其他厂商的 API 上基本通用，差异处会单独说明。
- **一个 API key**：在 [Claude Console](https://platform.claude.com/) 创建，放在环境变量 `ANTHROPIC_API_KEY` 里，不要写进代码或提交到仓库。

涉及的开源项目会在本站“项目解读”中单独介绍，第一个是 [Anthropic Java SDK](/projects/anthropics-anthropic-sdk-java/01/)，第 4 课会用到它。

## 怎样学这门课

- **每课都动手。** 每课末尾有练习。读懂和写出来是两回事，尤其是 prompt，必须实际运行才知道效果。
- **记录成本。** 从第一次调用开始就看 `usage` 字段，建立“一次请求大概多少钱”的直觉。
- **用评测代替感觉。** 从第二部分开始，任何“好像变好了”的判断都尽量用几条固定样例验证。
- **保留后端工程师的怀疑精神。** 模型的回答听起来很自信，并不代表正确。对它的输出，要像对待外部系统的返回值一样校验。

## 练习

1. 列出你现在负责的系统里，三个可能用大模型改进的功能。对每个功能写一句话：输入是什么，期望输出是什么，出错的代价有多大。
2. 在 Claude Console 创建一个 API key，设置到环境变量中，并确认 `echo $ANTHROPIC_API_KEY` 能读到（注意不要把输出贴到任何公开的地方）。
3. 对照上面的“经验迁移”表格，标出你最熟悉和最陌生的两项。后续课程中，可以优先关注陌生的部分。
