第 8 课说过，agent 的循环本身很简单，表现好不好几乎全看每一轮送进去的上下文。这一课就来设计这份上下文。业界把这件事叫作**上下文工程**（context engineering）：在有限的窗口里，决定放什么、按什么顺序放、什么时候清理。

先回顾一次请求里都有什么：

```text
┌─ tools      工具定义（第 7、9 课）
├─ system     系统提示：身份、工作方式、环境、项目约定
└─ messages   对话历史：用户任务、模型回复、工具调用与结果……
```

这一课给 MiniAgent 加上四样东西，每一样都对应 Claude Code 里的一个功能：

| 本课新增 | 解决什么问题 | Claude Code 中的对应 |
| --- | --- | --- |
| 结构化的系统提示 | 让 agent 有稳定的工作习惯，知道自己所处的环境 | 内置的系统提示 |
| 项目记忆 AGENTS.md | 每次都要重复交代的项目约定 | CLAUDE.md |
| prompt caching | 每一轮都重发全部历史，成本太高 | 自动使用缓存 |
| 上下文压缩 | 长任务把上下文窗口撑满 | 自动压缩和 `/compact` |

完整代码：[MiniAgent.java（第 10 课版本）](/courses/ai-dev/code/10/MiniAgent.java)，在第 9 课版本的基础上修改。

## 系统提示：agent 的工作习惯从哪里来

第 3 课讲过，指令微调让模型特别重视系统提示。第 8 课的实验 3 也验证了：删掉“修改之后运行测试验证”这一句，agent 就不再主动验证。系统提示是塑造 agent 行为最直接的地方。

这一版把系统提示拆成几个部分，由程序在启动时拼出来：

```java
static String buildSystemPrompt() {
    StringBuilder prompt = new StringBuilder("""
            你是一个编程助手，在用户的项目目录中工作，通过工具读取和修改代码、执行命令。

            # 工作方式
            - 先用 list_files 和 grep 定位相关代码，再用 read_file 读取需要的部分，不要猜测文件内容。
            - 修改已有文件用 edit_file，只有创建新文件时才用 write_file。
            - 遵循项目现有的代码风格和约定，不做任务之外的修改。
            - 修改之后，运行构建或测试来验证，并根据输出继续修正。
            - 没有实际运行过的验证，不要说“已通过”。
            - 完成后，用中文简要说明改了哪些文件、怎么验证的。
            """);
    prompt.append("""

            # 环境
            - 项目根目录：%s
            - 操作系统：%s
            - Java 版本：%s
            - 今天的日期：%s
            """.formatted(ROOT, System.getProperty("os.name"), System.getProperty("java.version"), LocalDate.now()));
    String memory = loadProjectMemory();
    if (memory != null) {
        prompt.append("\n# 项目约定（来自 AGENTS.md，必须遵守）\n").append(memory);
    }
    return prompt.toString();
}
```

几个写法上的考虑：

- **写行为，不写空话。** “你是一个优秀的工程师”对行为几乎没有影响；“没有实际运行过的验证，不要说已通过”针对的是第 3 课讲过的一个具体倾向。
- **给出环境信息。** 操作系统决定了命令怎么写（macOS 的 `sed -i` 和 Linux 的不一样）；Java 版本决定了能用哪些语法；日期能让模型知道它的训练数据可能已经过时。
- **约束要有理由，范围要清楚。** “不做任务之外的修改”能防止 agent 顺手“优化”你没让它动的代码。

Claude Code 的系统提示要长得多，覆盖了语气、工具使用规范、git 操作、安全规则等方方面面，但思路是一样的：把希望 agent 稳定遵守的工作方式写下来。

## 项目记忆：AGENTS.md

每个项目都有一些“新人入职时要交代”的东西：怎么构建、怎么跑测试、金额用什么类型、哪些目录不要碰。如果每次都在任务里重复这些，既麻烦又容易漏。

做法很简单：在项目根目录放一个 Markdown 文件，agent 启动时读进来，拼到系统提示后面：

```java
/** 项目记忆：根目录下的 AGENTS.md，没有的话再找 CLAUDE.md。 */
static String loadProjectMemory() {
    for (String name : List.of("AGENTS.md", "CLAUDE.md")) {
        Path file = ROOT.resolve(name);
        try {
            if (Files.isRegularFile(file)) {
                System.out.println("已加载项目记忆：" + name);
                return Files.readString(file);
            }
        } catch (IOException e) {
            System.out.println("读取 " + name + " 失败：" + e);
        }
    }
    return null;
}
```

文件名用了 `AGENTS.md`，这是 opencode 等多个开源 agent 共同支持的约定；找不到时再读 Claude Code 使用的 `CLAUDE.md`。第五部分读 opencode 源码时你会看到，它的查找顺序和这里几乎一样，只是多了用户全局目录和逐级向上查找。

记忆文件“生效”的原理就是这么朴素：**它被原样放进了每一次请求的系统提示。** 这带来两个推论：

- **它占用每一轮的上下文。** 一个 5000 token 的记忆文件，在一次 40 轮的任务里会被发送 40 次。所以要写得精炼，只放每次都需要的信息。
- **写在里面的指令会被认真对待。** 系统提示有特殊地位，这也是为什么“必须遵守”的约定放在这里，比在任务里口头说一句更可靠。

一份好的项目记忆通常包括：构建和测试命令、代码风格中工具检查不出来的部分、项目特有的约定和陷阱。第 18 课会结合 Claude Code 详细讲怎么写。

## Prompt caching：不再为重复的前缀付全价

第 2 课算过一笔账：模型无状态，第 20 轮请求要重新为前 19 轮付输入费用。agent 的情况更严重，一次任务几十轮，每轮都要重发系统提示、工具定义和越来越长的历史。

Prompt caching 解决的就是这个问题。服务端会缓存请求的**前缀**，下一次请求如果以完全相同的内容开头，这部分就直接从缓存读取：

| 计费项 | 价格（相对于正常输入价格） |
| --- | --- |
| 写入缓存（默认 5 分钟有效） | 1.25 倍 |
| 从缓存读取 | 0.1 倍 |
| 未命中缓存的输入 | 1 倍 |

agent 的请求天然适合缓存：每一轮请求都是上一轮请求加上新的几条消息，前缀几乎完全相同。在 SDK 里开启自动缓存只需要一行：

```java
static MessageCreateParams.Builder newConversation() {
    MessageCreateParams.Builder conversation = MessageCreateParams.builder()
            .model("claude-opus-5-5")
            .maxTokens(16_000L)
            .system(buildSystemPrompt())
            // 自动缓存：在请求的最后一个块上打缓存标记，下一轮请求可以复用整个前缀
            .cacheControl(CacheControlEphemeral.builder().build());
    TOOLS.values().forEach(t -> conversation.addTool(t.definition()));
    return conversation;
}
```

`cacheControl` 放在请求的顶层时，API 会自动在最后一个可缓存的块上打缓存标记。下一轮请求时，到上一轮末尾为止的全部内容都能命中缓存。

要让缓存有效，必须理解**前缀匹配**：请求按 tools → system → messages 的顺序拼接，任何一处改动都会让它后面的缓存全部失效。所以：

- 不要在系统提示里放每次都变的内容，比如精确到秒的时间戳。这一版只放了日期。
- 不要在对话中途增删工具。工具定义在最前面，一改全部失效。
- 不要修改历史消息。压缩会改写历史，所以压缩之后第一轮会重新写入缓存，这是有意识的取舍。

开启缓存后，`usage` 里的 `input_tokens` 只表示**未命中缓存**的部分，上下文的总量要把三项加起来。这一版每一步都会打印这三项：

```java
Usage usage = response.usage();
long cacheRead = usage.cacheReadInputTokens().orElse(0L);
long cacheWrite = usage.cacheCreationInputTokens().orElse(0L);
// 开启缓存后，input_tokens 只是未命中缓存的部分，上下文总量要把三者加起来
long context = usage.inputTokens() + cacheRead + cacheWrite;
System.out.printf("[第 %d 步] stop_reason=%s 上下文=%d（缓存命中 %d，写入缓存 %d，未缓存 %d） 输出=%d%n",
        step, reason, context, cacheRead, cacheWrite, usage.inputTokens(), usage.outputTokens());
```

太短的前缀不会被缓存，具体门槛和各模型的缓存价格以官方文档为准。

## 上下文压缩：窗口快满的时候

即使有缓存，上下文也有上限。第 5 课讲过，上下文越长，模型越容易忽略中间的信息，所以即使窗口还没满，过长的历史也会让效果变差。一个持续几小时的任务，读过的文件、跑过的测试输出会把窗口塞满，其中大部分已经没有用了。

压缩（compaction）的思路是：**让模型把到目前为止的工作写成一份摘要，然后用摘要替换全部历史。**

```java
static final String COMPACT_PROMPT = """
        上下文即将用完。请为接手这项工作的人写一份摘要，之后的工作将只依据这份摘要继续，原始对话会被丢弃。
        按以下标题组织，信息要具体（文件路径、类名、命令、报错原文）：
        1. 用户的目标和明确提出的要求
        2. 已完成的工作：修改了哪些文件，每处改了什么
        3. 重要发现：项目结构、约定、踩过的坑、失败过的尝试
        4. 当前状态：最近一次构建或测试的结果
        5. 下一步要做什么
        只输出摘要本身。
        """;

/**
 * 让模型把目前的对话总结成一份摘要，然后用这份摘要替换全部历史。
 * pending 是还没发给模型的工具结果，它们会和压缩指令放在同一条 user 消息里。
 */
static void compact(AnthropicClient client, MessageCreateParams.Builder conversation,
                    List<ContentBlockParam> pending) {
    List<ContentBlockParam> last = new ArrayList<>(pending);
    last.add(ContentBlockParam.ofText(COMPACT_PROMPT));
    MessageCreateParams request = conversation.build().toBuilder()
            .addUserMessageOfBlockParams(last)
            .toolChoice(ToolChoiceNone.builder().build()) // 只写摘要，不调用工具
            .build();
    Message response = client.messages().create(request);
    String summary = response.content().stream()
            .flatMap(block -> block.text().stream())
            .map(text -> text.text())
            .reduce("", String::concat);
    conversation.messages(List.of());
    conversation.addUserMessage("""
            这是一段长时间工作的延续。之前的对话已压缩为下面的摘要：

            %s

            请在此基础上继续工作。如果需要文件的细节，重新读取即可。
            """.formatted(summary));
    System.out.printf("（上下文已压缩：摘要 %d 个字符）%n", summary.length());
}
```

几个细节：

- **摘要的结构决定了压缩的质量。** 提示词列出了接手工作需要的五类信息，并要求写具体的路径、命令和报错原文。“改了一些文件”这样的摘要，会让 agent 在压缩后重复已经做过的事，甚至推翻已经确认的决定。
- **压缩用的是同一个对话。** 摘要请求带着完整的历史，再加上一条“请写摘要”的指令，所以模型能看到全部细节。`toolChoice` 设为 `none`，让它只写文字、不调用工具。
- **在合适的时机压缩。** 在循环里，压缩发生在“工具结果已经拿到、还没发给模型”的时候。这批结果会和压缩指令放在同一条消息里，所以摘要会包含最新的进展。

触发条件写在循环里：

```java
if (!results.isEmpty()) {
    if (context > COMPACT_AT) {
        // 工具结果还没发给模型，把它们一起交给压缩，摘要里会包含这些结果
        compact(client, conversation, results);
    } else {
        conversation.addUserMessageOfBlockParams(results);
    }
    continue;
}
```

另外，MiniAgent 现在支持两个命令：`/compact` 立即压缩，`/clear` 清空对话从头开始。Claude Code 里也有同名的命令，第 17 课讲会话管理时会讨论什么时候该用哪个。

压缩是有损的。摘要漏掉的信息就真的丢了，比如“用户说过不要改那个接口”。这也是项目记忆的价值所在：写在 AGENTS.md 里的约定在系统提示中，压缩不会影响它。

## 动手

**1. 写一份项目记忆。** 在第 8 课的 `~/agent-lab` 里创建 `AGENTS.md`：

```sh
cd ~/agent-lab
cat > AGENTS.md <<'EOF'
# agent-lab

- 运行方式：java PriceCalculator.java，输出 ALL PASSED 表示全部检查通过。
- 金额计算一律使用 BigDecimal，不要使用 double。
- 每新增一条业务规则，都要在 main 里补充对应的 check。
EOF
```

启动 agent，确认第一行输出了“已加载项目记忆：AGENTS.md”，然后给它一个任务：

```text
> 增加一条规则：周末下单额外打 95 折（在会员折扣之后计算）。日期作为 finalPrice 的新参数传入。
```

观察它是否在没有被提醒的情况下，把金额计算改成了 BigDecimal，并补充了检查。再删掉 AGENTS.md 重做一次（先恢复文件），比较两次的结果。

**2. 观察缓存。** 在上面的任务中，看每一步打印的三项数字。第 1 步应该全部是“写入缓存”或“未缓存”；从第 2 步开始，大部分 token 应该出现在“缓存命中”里。用第 2 课的价格表，分别按有缓存和无缓存估算这次任务的输入成本。

**3. 触发压缩。** 用一个很小的阈值启动，让压缩尽早发生：

```sh
COMPACT_AT=20000 mvn -q -f ~/mini-agent/pom.xml compile exec:java -Dexec.mainClass=demo.MiniAgent
```

给它一个需要多步完成的任务（比如在你的真实项目里“找出所有直接使用 double 表示金额的地方，列出文件和行号，不要修改”）。压缩发生后，往历史里加一句：

```text
> 你刚才的摘要里记录了哪些信息？之前检查过哪些文件？
```

它的回答只能来自摘要。对照压缩前的过程，看看丢了什么。

## 小结

- 上下文工程决定每一轮送进模型的内容：工具定义、系统提示、对话历史。
- 系统提示塑造 agent 的工作习惯，要写具体的行为和必要的环境信息。
- 项目记忆文件的原理是被原样拼进系统提示，所以要精炼，并且会被认真遵守。
- Prompt caching 按前缀匹配，agent 的请求天然适合缓存；不要改动前缀中的内容。
- 压缩用摘要替换历史，摘要的结构决定质量；压缩是有损的，长期有效的约定应写进项目记忆。

## 动手练习

1. 完成“动手”中的三个实验，记录第 2 步有缓存和无缓存两种情况下的估算成本。
2. 在 `buildSystemPrompt` 的环境部分加上当前的 git 分支（可以执行 `git rev-parse --abbrev-ref HEAD` 获取）。想一想：如果改成加上“当前时间，精确到秒”，对缓存会有什么影响？
3. 让 `loadProjectMemory` 同时读取用户目录下的 `~/.mini-agent/AGENTS.md`（放你的个人偏好，比如“回答使用中文”），并把它放在项目记忆之前。这就是 Claude Code 里用户级和项目级 CLAUDE.md 的区别。
