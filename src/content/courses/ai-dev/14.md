“给订单加个会员折扣。”这句话对一个在项目里待了两年的同事可能够用了，对 agent 却远远不够。它会去读代码，然后**补全**所有你没说的部分：几个会员等级、各打几折、和满减谁先谁后、会员等级从哪来。第 3 课讲过，模型会按“最常见的做法”补全，而且补全时语气笃定。补得合理，你可能根本不会注意到它替你做了业务决定；补得不合理，你要到 review 时才发现，然后返工。

这一课讲怎么把需求交代清楚：哪些必须你来说，哪些交给 agent 自己找，以及怎么让 agent 反过来追问你。

## 什么必须你给，什么让它自己找

agent 能用工具读代码，所以**代码里有的东西不用你说**；代码里没有的东西，它只能猜。

| 必须由你给 | 可以让 agent 自己找 |
| --- | --- |
| 为什么要做（背景、动机） | 相关代码在哪些文件里 |
| 业务规则，尤其是边界值和优先级 | 项目现有的写法和模式 |
| 约束：哪些接口不能改、哪些依赖不能加 | 依赖了哪些库、什么版本 |
| 范围之外：明确不做什么 | 怎么构建、怎么跑测试（写在 CLAUDE.md 里时） |
| 验收标准：怎样算做完，用什么命令验证 | |

左边一列的共同点是：**它们是决定，不是事实。** 事实可以从代码里查到，决定只能由人来做。一份好的需求，就是把所有需要人做的决定都提前做好。

还有一类介于两者之间：你知道答案、而且代码里也有，但藏得很深。这时直接指出来能省很多探索：“参考 `DiscountPolicy` 的写法”“问题可能在 `cancel` 方法的状态检查里”。官方最佳实践里的说法是：限定范围、指出来源、引用现有模式、描述症状。

## 第 3 课的倾向，在写需求时怎么应对

| 训练带来的倾向 | 写需求时的应对 |
| --- | --- |
| 按最常见的做法补全没说的部分 | 把业务规则和范围写全；不确定的地方让它先问 |
| 顺着你的说法走 | 用中性的方式描述问题，不预设原因：说“已发货的订单还能取消”，不说“cancel 方法少了一个判断” |
| 倾向于呈现“已完成” | 写明验收标准和验证命令，要求它给出命令的实际输出 |
| 知识可能过时 | 写明版本，或让它先读 `pom.xml` |

预设原因的问题在于：如果你猜错了，模型很可能顺着你的猜测去“修”一个不存在的问题。描述症状，让它自己定位。

## 一份写给 agent 的 spec

需求复杂时，与其在对话里一句句补充，不如写成一个文件。下面是一个适合 agent 的结构：

```markdown
# 会员折扣

## 背景
运营要上线会员体系，会员在满减之后再享受折扣。

## 业务规则
- 会员等级：NORMAL（无折扣）、SILVER（98 折）、GOLD（95 折）。
- 计算顺序：商品总额 → 减去满减 → 乘以会员折扣 → 四舍五入保留两位小数（HALF_UP）。
- 满减门槛按商品总额判断，不受会员折扣影响。

## 改动范围
- 新增 `MemberLevel` 枚举和一个按 customerId 查询会员等级的接口 `MemberLevelProvider`。
- `OrderService` 通过构造函数注入 `MemberLevelProvider`。
- `payableAmount(String orderId)` 的签名不变。

## 不做
- 不做会员等级的存储和升级逻辑，测试中用一个简单的实现代替。
- 不修改 `DiscountPolicy` 的满减规则。

## 验收标准
- 新增单元测试覆盖：三个等级各一例；满减和会员折扣同时生效的一例；
  四舍五入的边界一例（比如 GOLD 会员、满减后 199.99 元）。
- `mvn -q test` 全部通过，贴出命令输出。

## 参考
- 金额计算的写法参考 `DiscountPolicy` 和 `OrderService.payableAmount`。
```

几个要点：

- **每一条业务规则都可以直接变成一个测试用例。** 这不是巧合，第 16 课会讲为什么测试是 agent 最重要的反馈回路。
- **“不做”这一节很重要。** 没有它，agent 很可能顺手把会员等级的存储也实现了，多出一堆你没打算要、却需要你 review 的代码。
- **验收标准写成可以运行的命令。** “测试通过”不如“`mvn -q test` 全部通过，贴出输出”。

## 让 agent 先追问你

写 spec 本身也可以交给 agent。你只给一句话，让它来**采访你**：

```text
我想给订单加上会员折扣。请先用 AskUserQuestion 工具详细地问我，
覆盖业务规则、边界情况、和现有代码的关系、取舍。不要问显而易见的问题，
重点问我可能没想到的难点。问完之后，把完整的 spec 写到 SPEC.md。
```

`AskUserQuestion` 是 Claude Code 内置的工具，会以选择题的形式向你提问。这个做法来自 Claude Code 的官方最佳实践，它有两个好处：

- agent 已经读过代码，它问的问题是基于代码的，比如“现在 `OrderService` 拿不到会员等级，要新增依赖还是改方法签名”。这类问题你自己写需求时很容易漏掉。
- 每个问题都逼你做一个决定，而不是让它替你决定。

spec 写好之后，**开一个新会话去实现它**（`/clear` 或者重新启动 `claude`）。采访过程中的讨论、被否决的方案都不再占用上下文，新会话只看到一份干净的 spec。

## 把具体材料直接给它

除了文字描述，还有几种更直接的方式提供上下文：

- **用 `@` 引用文件**：`参考 @src/main/java/com/example/order/DiscountPolicy.java 的写法`。被引用的文件会直接读进来，省去搜索。
- **贴报错原文**：完整的异常栈比“启动报错了”有用得多。
- **用管道传入数据**：`cat build.log | claude -p "解释这个构建失败的原因"`。
- **让它自己去取**：“用 `git log -p -- src/main/java/com/example/order/OrderService.java` 看看 cancel 方法是怎么演变成现在这样的。”

## 动手

以下都在 order-lab 里做，每个实验开始前确认 `git status` 是干净的。

**1. 一句话需求。** 在 Claude Code 里输入：

```text
给订单加个会员折扣。
```

让它做完（如果它先问你问题，就回答“你决定”）。然后看 `git diff`，列出它替你做了哪些决定：几个等级、各打几折、顺序、会员等级从哪来、有没有改方法签名、写了哪些测试。看完后撤销改动：

```sh
git checkout -- . && git clean -fd
```

**2. 让它采访你。** 输入 `/clear`，然后用上一节的提示词让它采访你，最后生成 SPEC.md。把它问到的、而你在第 1 步里没有想到的问题记下来。

**3. 中性描述和预设原因。** 输入 `/clear`，分别用下面两种说法提出同一个问题（每次之后都撤销改动）：

```text
用户反馈：已经发货的订单还能被取消。请定位原因并说明，先不要修改代码。
```

```text
DiscountPolicy 的满减计算有 bug，导致已发货的订单还能被取消，帮我找出来。
```

第二种说法故意把原因指向了一个无关的类。观察模型是否顺着你的错误判断去 `DiscountPolicy` 里“找问题”，还是指出了真正的原因。

**4.** 保留第 2 步生成的 SPEC.md，下一课会用它来实现功能。

## 小结

- 代码里有的事实让 agent 自己找；代码里没有的决定必须由你给出。
- 一份好的 spec 包括背景、业务规则、改动范围、不做什么、可运行的验收标准和参考实现。
- 描述症状而不是预设原因，避免模型顺着错误的判断走。
- 复杂需求可以让 agent 先采访你，再把结论写成 spec，然后在新会话里实现。
- 用 `@` 引用文件、贴报错原文、用管道传入数据，都比文字描述更直接。
