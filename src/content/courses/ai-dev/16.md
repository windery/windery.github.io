Claude Code 的官方最佳实践把这一条放在了第一位：**给 Claude 一个它能自己运行的检查。** 原文的说法是，这决定了一个会话是需要你盯着的，还是你可以走开的。

原因要从 agent 什么时候停下来说起。第 8 课的循环里，模型不再请求工具，循环就结束了。也就是说，**agent 在“看起来做完了”的时候停下来。** 如果它没有任何办法检验结果，“看起来做完了”就是它唯一的信号，而你就成了那个检验者：每一个错误都要等你发现。

反过来，如果有一个能返回通过或失败的检查，循环就能自己闭合：做事、跑检查、读结果、继续改，直到检查通过。第 3 课讲过，新一代模型在“结果可以自动检验”的任务上经过大量强化学习，这正是它最擅长的工作方式。

## 检查的层次

对 Java 项目来说，常见的检查从快到慢依次是：

| 检查 | 命令示例 | 能发现什么 |
| --- | --- | --- |
| 编译 | `mvn -q compile` | 调用了不存在的方法、类型错误（第 3 课说的“编造 API”） |
| 单个测试 | `mvn -q -Dtest=OrderServiceTest test` | 当前改动涉及的行为 |
| 全部单元测试 | `mvn -q test` | 改动有没有破坏其他功能 |
| 静态检查和格式 | Checkstyle、SpotBugs、Spotless 等 | 风格和常见缺陷 |
| 集成测试 | `mvn -q verify` | 和数据库、外部服务的交互 |
| 运行起来看 | 启动应用，调接口 | 端到端的行为 |

越快的检查越适合在每一步之后运行，越慢的检查越适合放在最后。把这些命令写进 CLAUDE.md（第 18 课），agent 就不用每次猜该怎么验证。

## 修 bug：先写一个会失败的测试

修 bug 时最有效的一个习惯是：**先写一个能复现问题的测试，确认它失败，再去修。**

```text
用户反馈：已经发货的订单还能被取消。
1. 先写一个能复现这个问题的单元测试，运行它，确认它失败，贴出失败的输出；
2. 然后修复代码，不要修改这个新测试；
3. 运行全部测试，贴出输出。
```

这样做有三个好处：

- **证明问题确实存在。** 测试失败，说明你们对问题的理解一致；如果它写出的测试直接通过了，说明问题不在它以为的地方。
- **修完有据可查。** 同一个测试从失败变成通过，比“我已经修好了”可信得多。
- **防止“改测试来让测试通过”。** 第 3 课讲过，模型学到的是“让检验通过”。先写好测试、再明确要求不修改它，就把检验标准固定了下来。

对新功能也一样：上一课的 spec 里，每一条业务规则都可以先写成测试，再写实现。

## 让验证命令快速且可复现

agent 会运行很多次验证，每一次的输出都会进入上下文，所以验证命令本身也要设计：

- **快。** 一次要跑十分钟的测试套件，agent 不会愿意频繁运行，或者会超时。提供只跑相关测试的方法：`mvn -q -Dtest=OrderServiceTest#cancelShippedOrder test`。
- **输出精简。** `mvn -q` 只输出错误；成功时没有输出。第 9 课讲过，几千行的构建日志会挤占上下文，而有用的只有最后的失败汇总。
- **结果确定。** 依赖当前时间、随机数、外部网络的测试，时好时坏，会让 agent 陷入反复修改。order-lab 的测试用 `Clock.fixed` 固定了时间，就是这个原因。
- **一条命令。** 需要先启动数据库、再设置三个环境变量才能跑的测试，agent 很难自己跑起来。用 Testcontainers 或脚本把它封装成一条命令。

## 要证据，不要结论

在提示词里要求它**贴出命令和输出**，而不是只说“测试通过”。审阅证据比自己重新验证快，而且即使你没有一直盯着会话，事后也能确认它做了什么。

如果它说“测试通过”却没有贴输出，最简单的回应就是：“贴出 `mvn -q test` 的完整输出。”

## 硬性关卡：Stop hook

提示词里的要求是“建议”，模型大多数时候会遵守，但不保证。如果你希望**每次结束前都必须通过测试**，可以用 hooks 把它变成确定性的规则。

`Stop` 事件在 Claude 准备结束回合时触发。hook 脚本如果输出 `{"decision": "block", "reason": "…"}`，Claude Code 就不会结束回合，而是把 `reason` 交给 Claude，让它继续工作。

在 order-lab 里创建 `.claude/hooks/verify.sh`：

```bash
#!/bin/bash
# Stop hook：Claude 准备结束回合时运行测试，失败就让它继续修。
cd "$CLAUDE_PROJECT_DIR" || exit 0

# 这一回合没有改动 src 下的文件（比如只是回答问题），就不跑测试
if [ -z "$(git status --porcelain -- src)" ]; then
  exit 0
fi

if OUTPUT=$(mvn -q test 2>&1); then
  exit 0
fi

# 测试失败：输出 decision=block，Claude 会收到 reason 并继续工作
jq -n --arg out "$(echo "$OUTPUT" | tail -40)" '{
  decision: "block",
  reason: ("mvn -q test 没有通过，请根据下面的输出修复后再结束：\n" + $out)
}'
```

```sh
chmod +x .claude/hooks/verify.sh
```

然后在 `.claude/settings.json` 里注册它（这个文件可以提交到 git，团队共享）：

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/verify.sh" }
        ]
      }
    ]
  }
}
```

如果第 13 课的 `.claude/settings.local.json` 还在，两个文件里的 hooks 会同时生效。

几个细节：

- 脚本先检查 `src` 下有没有未提交的改动。只是回答问题的回合不需要跑测试，否则每次对话都要等一次构建。
- 只把最后 40 行输出交给 Claude：失败的测试和断言信息通常在最后。
- 为了防止无限循环，Claude Code 对连续的 Stop 阻止次数设了上限（目前是连续 8 次），达到上限后会强制结束回合。如果测试本身有问题（比如依赖网络），它不会一直卡住。

这就是第 11 课“用提示词引导行为，用代码保证底线”在 Claude Code 里的样子：提示词让它主动跑测试，Stop hook 保证没跑通就不会停。

## 第二意见

还有一种检查不是命令，而是**另一个模型的审视**。写代码的 agent 倾向于认为自己写对了（第 3 课的偏好训练），一个没有参与编写的新会话或子 agent，更容易发现问题：

```text
用一个子 agent 审查刚才的改动：只看 git diff 和相关的测试，
找出没有被测试覆盖的业务规则和可能的边界问题。不要修改代码。
```

第 19 课会专门讲审查。

## 动手

1. **测试先行修 bug。** 在 order-lab 里，用“修 bug”一节的提示词修复“已发货的订单还能取消”。确认它先贴出了失败的测试输出，再贴出修复后的通过输出。用 `git diff` 检查它没有修改新测试以外的已有测试。
2. **安装 Stop hook。** 按上一节创建脚本和配置，重启 Claude Code，输入 `/hooks` 确认 Stop hook 已加载。
3. **验证关卡。** 手动把 `DiscountPolicy` 里的 `80.00` 改成 `70.00`（模拟一个引入回归的改动），然后让 Claude 做一个无关的小修改，比如“给 `InMemoryOrderRepository` 加一个 `count()` 方法”。它准备结束时，Stop hook 会发现测试失败，它会被要求继续修复。观察它是把 `70.00` 改回去，还是去改测试？不论哪种，最后都用 `git diff` 确认结果。

## 小结

- agent 在“看起来做完了”时停下。给它一个能自己运行的检查，循环才能自己闭合。
- 修 bug 先写失败的测试，确认失败，再修复，并要求不修改这个测试。
- 验证命令要快、输出精简、结果确定、一条命令就能跑。
- 要求贴出命令和输出，审阅证据而不是相信结论。
- Stop hook 可以把“测试必须通过”变成确定性的规则。

## 动手练习

1. 完成三个实验。在第 3 个实验里，如果它改了测试而不是代码，你会怎样修改提示词或 hook 来防止这种情况？
2. 写一个 `PreToolUse` hook，在修 bug 的任务中阻止修改 `src/test` 下**已经存在**的文件（新建测试文件仍然允许）。提示：hook 的输入里 `tool_input.file_path` 是文件路径；可以用 `git ls-files --error-unmatch` 判断文件是否已被 git 跟踪；退出码 2 表示阻止，标准错误输出会作为原因交给 Claude。
3. 在你自己的项目里，写出“让 agent 只运行一个测试类”的命令，并测一测它需要多长时间。如果超过一分钟，想想怎么让它更快。
