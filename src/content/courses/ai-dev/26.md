## 系统提示是怎么拼出来的

先运行第 24 课的第一个剧本，这次连同系统提示一起看：

```sh
./run.sh 01-read "读一下 hello.txt"
python3 show.py logs/01-read.jsonl --system
```

主请求的系统提示有上万个字符（具体长度取决于你装了哪些 skills，第 27 课会讲为什么 `~/.claude/skills` 里的 skills 也会出现在这里）。它由 `session/prompt.ts` 的 `runLoop` 和 `session/llm/request.ts` 的 `prepare` 两处拼出来，**每一步都重新拼一次**：

```typescript
// session/prompt.ts：runLoop 里，每一步调用模型之前
const [skills, env, instructions, mcpInstructions, modelMsgs] = yield* Effect.all([
  sys.skills(agent),
  sys.environment(model),
  instruction.system().pipe(Effect.orDie),
  sys.mcp(agent, session.permission),
  MessageV2.toModelMessagesEffect(msgs, model),
])
const system = [
  ...env,
  ...instructions,
  ...(mcpInstructions ? [mcpInstructions] : []),
  ...(skills ? [skills] : []),
]

// session/llm/request.ts：prepare 里，把开头的提示词放在最前面，拼成一个字符串
const system = [
  [
    ...(input.agent.prompt ? [input.agent.prompt] : SystemPrompt.provider(input.model)),
    ...input.system,
    ...(input.user.system ? [input.user.system] : []),
  ]
    .filter((x) => x)
    .join("\n"),
]
```

按顺序，系统提示由这几段组成：

| 段落 | 来源 | 在实验里看到的内容 |
| --- | --- | --- |
| 开头的提示词 | agent 自己的 `prompt`；没有的话按模型选一份 | `You are OpenCode, the best coding agent on the planet.` 开头的长提示 |
| 环境信息 | `system.ts` 的 `environment` | 模型名，`<env>` 里的工作目录、仓库根目录、是否 git 仓库、平台、日期 |
| 项目说明 | `instruction.ts` 的 `system` | `Instructions from: …/demo/AGENTS.md` 加文件内容 |
| MCP 服务端的说明 | `system.ts` 的 `mcp` | 实验里没有配置 MCP，这一段为空 |
| skills 列表 | `system.ts` 的 `skills` | `<available_skills>` 里每个 skill 的名字、描述和路径 |

“按模型选一份”是 `system.ts` 里的 `provider` 函数，靠模型 ID 里的关键字判断：

```typescript
export function provider(model: Provider.Model) {
  // ……
  if (model.api.id.includes("gpt-4") || model.api.id.includes("o1") || model.api.id.includes("o3"))
    return [PROMPT_BEAST]
  if (model.api.id.includes("gpt")) {
    if (model.api.id.includes("gpt-6")) return [PROMPT_ASTRA]
    if (model.api.id.includes("codex")) return [PROMPT_CODEX]
    return [PROMPT_GPT]
  }
  if (model.api.id.includes("gemini-")) return [PROMPT_GEMINI]
  if (model.api.id.includes("claude")) return [PROMPT_ANTHROPIC]
  // ……kimi、trinity 等
  return [PROMPT_DEFAULT]
}
```

这些提示词都在 `session/prompt/` 下，是普通的文本文件。值得花十分钟对比一下 `anthropic.txt` 和 `gpt.txt`：同一个 agent，给不同模型的工作习惯说明并不一样。第 10 课说“系统提示是 agent 的工作习惯”，这里能看到 opencode 认为不同模型需要不同的说法。

和 MiniAgent 相比，有两点不同：

- **每一步都重新拼。** MiniAgent 在启动时读一次 AGENTS.md，opencode 每一步都重新读。好处是你在会话中途改了 AGENTS.md，下一步就生效；代价是系统提示一变，缓存就失效（后面讲缓存时再说）。
- **整个系统提示是一个字符串。** 它在请求里是 `system` 数组的一个元素。插件可以通过 `experimental.chat.system.transform` 往里加内容，`prepare` 会把加进来的部分合并成第二个元素，保证第一个元素不变。原因同样和缓存有关。

## 项目说明：AGENTS.md 怎么查找

`instruction.ts` 的 `systemPaths` 决定哪些文件进入系统提示：

```typescript
const globalFiles = [
  path.join(global.config, "AGENTS.md"),                         // ~/.config/opencode/AGENTS.md
  ...(!flags.disableClaudeCodePrompt ? [path.join(global.home, ".claude", "CLAUDE.md")] : []),
]
const instructionFiles = [
  "AGENTS.md",
  ...(!flags.disableClaudeCodePrompt ? ["CLAUDE.md"] : []),
  "CONTEXT.md", // deprecated
]
```

规则是：

1. **全局只取一个。** 先找 `~/.config/opencode/AGENTS.md`，没有再找 `~/.claude/CLAUDE.md`，找到第一个就停。
2. **项目里按文件名逐个找，第一个有结果的文件名胜出。** 对 `AGENTS.md`，从当前目录向上一直找到仓库根目录（`findUp`），沿途每一级的 `AGENTS.md` 都会加进来。只要找到了任何一个 `AGENTS.md`，就不再找 `CLAUDE.md`。源码注释写得很清楚：不要把每一级的 AGENTS.md 和 CLAUDE.md 叠在一起。
3. **配置里的 `instructions`。** `opencode.json` 可以写 `"instructions": ["docs/style.md", "~/notes/*.md"]`，支持 glob，也支持 http 地址（会去下载）。

第 2 条意味着：如果你的项目同时用 opencode 和 Claude Code，最省事的做法是只维护一份 `AGENTS.md`，再让 `CLAUDE.md` 引用它（Claude Code 支持在 CLAUDE.md 里用 `@AGENTS.md` 导入）。两份都写的话，opencode 只读 AGENTS.md。

和第 10 课的 `loadProjectMemory` 对照：MiniAgent 只看根目录、AGENTS.md 优先、找不到再读 CLAUDE.md，这一条和 opencode 一样；opencode 多了全局文件、向上查找和配置项。

### 子目录里的 AGENTS.md

上面这些都是启动时就放进系统提示的。子目录里的说明文件是另一套机制：**读到那个目录下的文件时，才附加到工具结果里。** 运行这一课新加的第一个剧本：

```sh
./run.sh 07-nested "看看 docs/notes.txt"
python3 show.py logs/07-nested.jsonl
```

演示项目里有 `docs/AGENTS.md`，内容是“这个目录下的文档用英文写”。模型调用 read 读 `docs/notes.txt`，返回的 tool_result 是：

```text
<path>…/demo/docs/notes.txt</path>
<type>file</type>
<content>
1: release notes draft

(End of file - total 1 lines)
</content>

<system-reminder>
Instructions from: …/demo/docs/AGENTS.md
# docs 目录

这个目录下的文档用英文写。

</system-reminder>
```

实现在 `instruction.ts` 的 `resolve`：从被读文件所在的目录开始向上走，一直走到项目根目录（不含根目录，根目录的已经在系统提示里了），每一级找一个说明文件。已经在系统提示里的、这个会话里已经附加过的，都跳过：

```typescript
// Walk upward from the file being read and attach nearby instruction files once per message.
while (current.startsWith(root) && current !== root) {
  const found = yield* find(current)
  if (!found || found === target || sys.has(found) || already.has(found)) {
    current = path.dirname(current)
    continue
  }
  // ……记录下来，读出内容
}
```

这个设计的好处是按需加载：一个大仓库里几十个模块各有说明，只有 agent 真正碰到的那几个才占用上下文。代价是它们进入的是对话历史，不是系统提示。第 17 课讲过 Claude Code 的同类行为：子目录的 CLAUDE.md 读到相关文件时才加载，会随对话一起被压缩掉。opencode 也一样，下面讲压缩时会看到原因。

## 缓存标记打在哪里

`show.py` 的输出里，有些内容块前面有 `[cache]`。这是 `provider/transform.ts` 的 `applyCaching` 打的标记：

```typescript
function applyCaching(msgs: ModelMessage[], model: Provider.Model): ModelMessage[] {
  const system = msgs.filter((msg) => msg.role === "system").slice(0, 2)
  const final = msgs.filter((msg) => msg.role !== "system").slice(-2)
  // ……给这些消息加上 cacheControl: { type: "ephemeral" }（不同服务商的写法不同）
}
```

**前两条系统消息，加上最后两条非系统消息。** 第 10 课讲过，缓存按前缀匹配，标记表示“到这里为止的内容请缓存”。打在系统提示上，系统提示和工具定义就能被所有请求共用；打在最后两条消息上，下一步请求时，到上一步为止的整段历史都能命中缓存。Anthropic 的 API 一个请求最多四个标记，这里正好用满。

再看上一节提到的两个细节，就明白它们为什么重要了：

- **插件加的内容合并成第二个元素，第一个元素保持不变。** 插件每次加的内容如果不一样，至少第一个元素（占了绝大部分长度）还能命中缓存。
- **系统提示每一步都重新拼。** 只要其中任何一个字符变了，整个前缀的缓存就失效。会话中途改 AGENTS.md、装了新的 skill、过了午夜日期变了，下一步都要重新写入缓存。第 22 课算过，缓存读取的价格是写入的十几分之一，所以这不是小事。opencode 的 V2 重写专门处理了这个问题，本课最后会讲。

MiniAgent 用的是请求级别的自动缓存（`cacheControl` 放在请求上，由 API 决定标记位置），效果接近“最后一条消息打标记”。opencode 显式地控制标记的位置，因为它要支持很多家服务商，每家的写法都不同。

## 什么时候压缩

判断条件在 `session/overflow.ts`，只有三十多行：

```typescript
const COMPACTION_BUFFER = 20_000

export function usable(input: { cfg: ConfigV1.Info; model: Provider.Model; outputTokenMax?: number }) {
  const context = input.model.limit.context
  if (context === 0) return 0

  const reserved =
    input.cfg.compaction?.reserved ??
    Math.min(COMPACTION_BUFFER, ProviderTransform.maxOutputTokens(input.model, input.outputTokenMax))
  return input.model.limit.input
    ? Math.max(0, input.model.limit.input - reserved)
    : Math.max(0, context - ProviderTransform.maxOutputTokens(input.model, input.outputTokenMax))
}

export function isOverflow(input: { /* … */ }) {
  if (input.cfg.compaction?.auto === false) return false
  if (input.model.limit.context === 0) return false

  const count =
    input.tokens.total || input.tokens.input + input.tokens.output + input.tokens.cache.read + input.tokens.cache.write
  return count >= usable(input)
}
```

“可用空间”的算法：如果模型单独声明了输入上限，就用输入上限减去预留量；否则用上下文窗口减去最大输出长度。最大输出长度取模型声明值和 32000 中较小的一个。

代入两个例子：

| 模型 | 上下文 | 最大输出 | 可用空间 |
| --- | --- | --- | --- |
| 实验用的小模型（`models-small.json`） | 30000 | 4000 | 30000 − 4000 = 26000 |
| 一个 200K 上下文、64K 输出的模型 | 200000 | min(64000, 32000) = 32000 | 200000 − 32000 = 168000 |

“用了多少”看的是上一步模型返回的 token 用量，输入、输出、缓存读写都算上。

检查发生在两个地方：

- **每一步结束时。** processor 处理 `step-finish` 事件时算一次，超了就设置 `needsCompaction`，流随即停止，`process` 返回 `"compact"`。
- **服务商报错“上下文超长”时。** 同样设置 `needsCompaction`。这种情况下压缩完还会把最后一条用户消息重放一遍（附件换成一行文字说明），因为那条消息本身可能就是超长的原因。

返回 `"compact"` 后，`runLoop` 并不直接压缩，而是**往会话里写一条带 `compaction` part 的用户消息**，然后进入下一轮循环。下一轮发现最后一条用户消息是压缩任务，才调用 `SessionCompaction.process`。手动压缩（TUI 里的 `/compact`，服务端的 `POST /session/{id}/summarize`）也是写这样一条消息。压缩成了会话里一个看得见、存得下的事件，而不是循环里的一次函数调用。

和 MiniAgent 对照：第 10 课用一个固定阈值 `COMPACT_AT`，在“工具结果已拿到、还没发给模型”时压缩，结果和压缩指令放在同一条消息里。opencode 的阈值按模型算，压缩发生在一步结束之后。

## 压缩成什么样

运行压缩剧本。它用上下文只有 30000 的小模型，模拟的服务端在第一步报告用了 27000 个输入 token，超过了 26000：

```sh
./run.sh 04-compact "读一下 hello.txt"
python3 show.py logs/04-compact.jsonl
```

一共四个请求：

```text
===== 请求 1：1 条消息，工具 无
system（2096 字符）：You are a title generator. ……
===== 请求 2：1 条消息，工具 ['bash', 'edit', 'glob', ……]
system（18062 字符）：You are OpenCode, the best coding agent on the planet. ……
===== 请求 3：1 条消息，工具 无
system（630 字符）：You are a context summarization agent. ……
  user      text        [cache] "Here is the conversation so far:\n\n<conversation>\n[User]: \"读一下 hello.txt\"……
===== 请求 4：3 条消息，工具 ['bash', 'edit', 'glob', ……]
system（18062 字符）：You are OpenCode, the best coding agent on the planet. ……
  user      text        "What did we do so far?"
  assistant text        [cache] "## Objective\n- 查看目录内容\n\n## Work State\n### Completed\n- 已运行 ls"
  user      text        [cache] "Continue if you have next steps, or stop and ask for clarification if you are unsure how to proceed."
```

### 请求 3：压缩请求

压缩用的是一个隐藏的 `compaction` agent，系统提示只有几句：

```text
You are a context summarization agent. You are given a conversation between a user and an agent. Your goal is to produce a structured summary matching the format specified so another coding agent can continue the work.
……
Do not continue the conversation. Do not respond to any questions in the conversation. Only output the structured summary in the exact format requested by the user prompt. Respond in the same language as the conversation.
```

注意它**不带工具，也不带原来的系统提示**，对话历史被转成纯文本放进一条用户消息：

```text
Here is the conversation so far:

<conversation>
[User]: "读一下 hello.txt"

[Assistant tool call]: bash({"command":"ls","description":"List files"})
[Tool result]: AGENTS.md
docs
hello.txt
opencode.json

</conversation>

Create a new anchored summary from the conversation history in the <conversation> tags above so another coding agent can continue the work.

Output exactly the Markdown structure shown inside <template> and keep the section order unchanged. ……
<template>
## Objective
## Important Details
## Work State
### Completed
### Active
### Blocked
## Next Move
## Relevant Files
</template>
```

（模板里每一节下面还有一行说明，这里省略了。）转换时每个工具结果最多保留 2000 个字符，超出的部分换成 `[truncated]`。

和 MiniAgent 的做法正好相反。第 10 课的压缩请求“带着完整的历史，再加一条请写摘要的指令”，好处是请求前缀和平时一样，能命中缓存，模型也能看到原始格式的全部内容。opencode 把历史转成文本、换了系统提示，缓存一定用不上，但换来两点：压缩请求不受工具定义和长系统提示的干扰，以及工具结果被截断后，压缩请求本身不容易超长。两种做法各有道理，没有哪个绝对更好。

如果之前已经压缩过，压缩提示里还会带上 `<prior-summary>`，要求模型把旧摘要和新对话合并：旧摘要里的目标、约束、决定要保留，冲突时以新对话为准，已完成的从 Active 移到 Completed。这样连续压缩多次，早期的关键信息也不会丢。

### 请求 4：压缩之后的历史

压缩后的历史是三条消息：

1. 用户：`What did we do so far?`（这是那条压缩任务消息在发给模型时的样子）
2. 助手：摘要
3. 用户：`Continue if you have next steps, or stop and ask for clarification if you are unsure how to proceed.`

第 3 条只在自动压缩时才加，手动 `/compact` 之后不会自动继续。最初的“读一下 hello.txt”这条消息不见了，为什么？

### 保留最近的几轮

`compaction.ts` 的 `select` 会把历史按“轮”（从一条用户消息到下一条用户消息）切开，从最近的一轮往前数，在预算之内的几轮**原样保留**，不进摘要：

```typescript
function preserveRecentBudget(input: { cfg: ConfigV1.Info; model: Provider.Model }) {
  return (
    input.cfg.compaction?.preserve_recent_tokens ??
    Math.min(MAX_PRESERVE_RECENT_TOKENS, Math.max(MIN_PRESERVE_RECENT_TOKENS, Math.floor(usable(input) * 0.25)))
  )
}
```

预算是可用空间的四分之一，最少 2000，最多 15000 token。最近的一轮如果超出预算，还会尝试只保留这一轮的后半段。

但有一个条件：如果能保留的部分从第一条消息就开始（`keep.start === 0`），说明整个历史都在预算之内，保留下来就等于没压缩，于是全部进摘要。实验里的会话很短，所以没有保留任何原始消息。在真实的长会话里，压缩后的历史是“摘要 + 最近几轮的原文 + 继续”。

保留多少可以配置：`compaction.preserve_recent_tokens` 改预算，`compaction.tail_turns` 限制最多保留几轮。

### 原始消息并没有删除

查一下数据库：

```sh
./db.sh
```

```text
role       type         detail
user       text         "读一下 hello.txt"
assistant  step-start
assistant  tool         bash
assistant  step-finish  tool-calls
user       compaction
assistant  step-start
assistant  text         ## Objective
assistant  step-finish  stop
user       text         Continue if you have next step
assistant  step-start
assistant  text         压缩后继续：目录里有三个文件。
assistant  step-finish  stop
```

压缩前的消息都还在。每一步从数据库加载历史时，`message-v2.ts` 的 `filterCompacted` 从最新的消息往前读，遇到一次已完成的压缩就停下，只保留它之后的部分（加上保留下来的那几轮）。**压缩改变的是“发给模型什么”，不是“存了什么”。** 所以导出会话时，压缩前的对话也是完整的。

这也解释了上一节的问题：子目录的 AGENTS.md 是附加在某个工具结果里的，那个工具结果被压缩进摘要后，说明就不在了，除非模型再次读到那个目录的文件。而 `resolve` 判断“已经附加过”时看的正是压缩后的历史，所以再次读到时会重新附加。

### 修剪：只清掉旧的工具输出

除了压缩，还有一个更轻的手段，叫 prune（修剪）。它默认关闭，在配置里打开：

```json
{ "compaction": { "prune": true } }
```

每次循环结束后，`prune` 在后台从最新的消息往前数：跳过最近两轮，跳过 skill 工具的输出，累计超过 40000 token 之后更早的工具输出都标记为“已清理”。只有可清理的总量超过 20000 token 才真正动手。被清理的工具结果在以后的请求里显示为：

```text
[Old tool result content cleared]
```

这和第 10 课提到的“清理旧工具结果”是同一个思路：工具调用本身（读了哪个文件、跑了什么命令）还在，只是输出没了。模型知道自己做过什么，需要细节时可以重新读。它比摘要便宜得多，不需要额外调用模型。

## 会话存在哪里

opencode 的会话存在一个 SQLite 数据库里，正常安装时在 `~/.local/share/opencode/opencode.db`（从源码运行时文件名是 `opencode-local.db`，实验包的在 `.home/data/opencode/` 下）。主要的表有四张：`session`、`message`、`part`、`todo`。

```sh
./db.sh "select id, parent_id, project_id, title from session"
./db.sh "select id, worktree from project"
```

`project_id` 是什么？对比一下：

```sh
cd demo && git rev-list --max-parents=0 HEAD && cd ..
```

它就是仓库第一个提交的哈希。同一个仓库不管克隆到哪个目录，都被认为是同一个项目，会话列表也是按项目区分的。

和会话有关的命令：

| 操作 | opencode | Claude Code（第 17 课） |
| --- | --- | --- |
| 开始新会话 | `/new`（别名 `/clear`） | `/clear` |
| 压缩 | `/compact`（别名 `/summarize`），不能指定重点 | `/compact <重点>` |
| 回退 | `/undo`、`/redo` | `/rewind` |
| 分支 | TUI 里的 `/fork`；`opencode run --continue --fork` | `/branch`、`--fork-session` |
| 恢复会话 | `/sessions`；`opencode run --continue` 或 `--session <id>` | `/resume`、`claude --continue` |
| 不进历史的旁支问题 | 没有 | `/btw` |
| 导出和导入 | `opencode export <id>`、`opencode import <文件>` | 会话文件本身就是 JSONL |

opencode 的 `/compact` 不接受参数。想影响压缩的内容，可以写插件，用 `experimental.session.compacting` 钩子往压缩提示里加内容，或者整个替换掉压缩提示，第 27 课讲插件时会看到。

## 快照与撤销

第 17 课说过，Claude Code 的检查点只记录编辑工具的修改，Bash 命令的改动记不住。opencode 用的是另一种办法：**给整个工作目录拍 git 快照。**

运行这一课新加的第二个剧本，模型用 write 工具创建一个文件：

```sh
./run.sh 08-write "建一个 todo.md"
./db.sh "select json_extract(data, '$.type') as type, json_extract(data, '$.snapshot') as snapshot,
         json_extract(data, '$.hash') as hash, json_extract(data, '$.files') as files
  from part where session_id = (select id from session order by time_created desc limit 1)
    and json_extract(data, '$.type') in ('step-start', 'step-finish', 'patch') order by id"
```

```text
type         snapshot                                  hash                                      files
step-start   a90aacc5556851e58f6364e35249559cb779a517
step-finish  d755b95ac3fde2544570d40706603c337f2594ea
patch                                                  a90aacc5556851e58f6364e35249559cb779a517  [".../demo/todo.md"]
step-start   d755b95ac3fde2544570d40706603c337f2594ea
step-finish  d755b95ac3fde2544570d40706603c337f2594ea
```

（你的哈希会不一样。）每一步开始时，processor 调用 `snapshot.track()` 记下工作目录的状态；结束时再记一次，比较两次之间哪些文件变了，变了就写一个 `patch` part，`hash` 是这一步开始前的快照。

快照存在哪里？`snapshot/index.ts` 里：

```typescript
gitdir: path.join(Global.Path.data, "snapshot", ctx.project.id, Hash.fast(ctx.worktree)),
```

一个独立的 git 目录，和你项目自己的 `.git` 无关，不会产生提交，也不会碰你的暂存区。`track` 的做法是 `git add` 加 `git write-tree`，快照就是一个 tree 对象的哈希。可以直接用 git 看：

```sh
G=$(ls -d .home/data/opencode/snapshot/*/* | head -1)
git --git-dir "$G" ls-tree <step-start 那一行的快照哈希>
git --git-dir "$G" diff --stat <第一个快照> <第二个快照>
```

```text
 todo.md | 1 +
 1 file changed, 1 insertion(+)
```

因为是给整个目录拍快照，**bash 命令造成的文件改动也会被记录**，这一点比 Claude Code 的检查点强。限制也来自 git：项目必须是 git 仓库，`.gitignore` 里的文件不在快照里，数据库之类目录外的改动当然也回不去。

`/undo` 调用的是 `session/revert.ts` 的 `revert`：找到要回退的那条消息，收集它之后所有的 `patch` part，用快照把这些文件恢复回去（`git read-tree` 加 `git checkout-index`）。有意思的是，**消息并不马上删除**。会话上只是记下“回退到了哪里”，等你发下一条消息时，`cleanup` 才真正删掉那些消息。在那之前，`/redo` 可以把文件和对话都恢复回来。

## 待办清单

第 11 课的 `todo_write` 只是把清单打印出来再返回给模型。opencode 的 `todowrite` 做的事一样，区别是清单存进了 `todo` 表，TUI 可以随时显示，会话恢复后也还在。提醒模型用清单的规则写在系统提示里（`anthropic.txt` 里有好几段专门讲 todowrite），循环本身不会主动把清单插回上下文。

## V2 在改什么

第 24 课提到，`packages/core` 是一个还没完成的重写。它的设计文档 `specs/v2/session.md` 里有一段专门针对本课讲的问题，叫 Context Epoch：

> V2 Sessions persist the exact privileged System Context shown to the model. A Context Epoch stores one immutable provider-cache baseline …… Changed context becomes one durable chronological System message ……

翻译过来就是：会话开始时把系统提示（环境信息、日期、AGENTS.md、skills 说明）存下来，作为不再改变的缓存基线。之后这些来源有变化，不再改写系统提示，而是在对话的当前位置追加一条系统消息，说明什么变了。

对照前面讲的 V1 行为，这正好解决了“系统提示每一步重新拼、任何变化都让整个缓存失效”的问题，同时还让模型看到的上下文变得可以完整回放：数据库里存的就是模型真正看到的。读一个项目的设计文档，常常能看到作者自己认为现在哪里不够好。

## 三方对照

| | MiniAgent（第 10、11 课） | opencode | Claude Code |
| --- | --- | --- | --- |
| 系统提示 | 启动时拼一次 | 每一步重新拼；按模型选不同的提示词 | 不公开 |
| 项目说明 | 根目录的 AGENTS.md 或 CLAUDE.md | 全局一个；项目里向上查找，AGENTS.md 优先；配置可加文件和网址 | CLAUDE.md，多级加载，可用 `@` 导入 |
| 子目录说明 | 无 | 读到文件时附加到工具结果 | 读到文件时加载 |
| 缓存 | 请求级自动缓存 | 前两条系统消息和最后两条消息打标记 | 自动 |
| 压缩时机 | 固定阈值 | 按模型算可用空间，超过即压缩 | 接近上限时自动 |
| 压缩请求 | 原历史加一条指令 | 历史转成文本，专用系统提示，无工具 | 不公开 |
| 摘要格式 | 五类信息 | 固定模板，支持和旧摘要合并 | 可用 CLAUDE.md 补充压缩说明 |
| 压缩后保留 | 只有摘要 | 摘要加最近几轮原文 | 摘要，并重新注入根目录 CLAUDE.md 等 |
| 清理旧工具结果 | 无 | prune，默认关闭 | 不公开 |
| 会话存储 | 内存，不保存 | SQLite | 本地 JSONL 文件 |
| 文件回退 | 无 | git 快照，包括 bash 的改动 | 检查点，只含编辑工具的改动 |

## 动手

1. **看提示词的差别。** 打开 `session/prompt/anthropic.txt` 和 `session/prompt/gpt.txt`，各找出三条对方没有的要求。你觉得这些差别是针对模型的什么特点？
2. **加一个全局说明。** 在实验包的 `.home/config/opencode/` 下建一个 `AGENTS.md`，写一句“回答时先说结论”，重新运行 `01-read`，用 `show.py --system` 找到它在系统提示里的位置。
3. **两级子目录。** 在 `demo/docs/` 下再建一个 `api/` 目录，放一个 `AGENTS.md` 和一个文件，仿照 `07-nested.json` 写一个剧本去读这个文件。tool_result 里会附加几份说明，顺序是什么？
4. **算一个阈值。** 实验包 `models.json` 里的模型就是表格第二行那种：上下文 200000，输出 64000。如果给它加上 `"input": 150000`，可用空间变成多少？为什么这时预留量是 20000，而不是 32000？
5. **让压缩保留原文。** 在实验包根目录的 `opencode.json` 里加上 `"compaction": { "tail_turns": 1 }`，先运行 `./run.sh 01-read "读一下 hello.txt"`，再用 `./run.sh 04-compact "再看看目录" --continue` 接着同一个会话发第二条消息。用 `show.py` 看压缩后的请求：第二轮的原文是否保留了？压缩请求的 `<conversation>` 里还有第二轮吗？去掉这个配置再做一次（先删掉 `demo/` 和 `.home/`），结果有什么不同？
6. **撤销 bash 的改动。** 在你自己安装的 opencode 里（不是实验包），让它用 bash 删除一个文件，然后 `/undo`，看文件是否回来。在 Claude Code 里做同样的事，用 `/rewind` 对比。

## 小结

- 系统提示每一步重新拼：按模型选的提示词、环境信息、AGENTS.md、MCP 说明、skills 列表。好处是改动立即生效，代价是任何变化都会让缓存失效。
- AGENTS.md 全局取一个，项目里向上查找并且 AGENTS.md 优先；子目录的说明在读到文件时附加到工具结果里，会随压缩消失。
- 缓存标记打在前两条系统消息和最后两条消息上，一个请求正好四个。
- 压缩的阈值按模型算；压缩请求把历史转成文本，用固定模板生成摘要，保留最近几轮原文；原始消息仍在数据库里，只是不再发给模型。
- 会话存在 SQLite 里，按仓库的第一个提交区分项目；文件回退用独立的 git 快照，连 bash 的改动也能撤销。
