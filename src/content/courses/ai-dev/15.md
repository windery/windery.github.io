有了 spec，下一步就是让 agent 去实现。最省事的做法是把 spec 丢给它，然后等结果。这样做的问题在第 11 课讲过：agent 可能读了几个文件就开始改，方向错了要到最后才发现，而那时它已经改了十几个文件。

这一课讲一次任务的节奏：**探索、计划、实现、提交**，以及你在每一步该看什么。这四步来自 Claude Code 的官方最佳实践，背后的原理你在第 11 课已经亲手实现过：先写下的计划会约束后续的生成，计划阶段也是纠错成本最低的时候。

## 什么时候需要这套流程

先说什么时候**不需要**。计划本身有成本：多几轮对话，多一些 token，多一次你的审阅。如果改动能用一句话描述清楚，比如改一个拼写错误、加一行日志、重命名一个变量，直接让它做就好。

下面几种情况，值得先计划：

- 你不确定应该怎么做；
- 改动会涉及多个文件；
- 你不熟悉要修改的这部分代码；
- 改错的代价比较大，比如涉及数据迁移、对外接口。

## 第一步：探索

按 `Shift+Tab` 切换到计划模式，直到状态栏显示 `plan mode on`；也可以用 `claude --permission-mode plan` 直接以计划模式启动。在这个模式下，Claude Code 只读代码、回答问题，不会修改你的源文件。

探索阶段的提示词，重点是**让它说出它的理解**：

```text
读一下 @SPEC.md，然后阅读 OrderService 及相关的类，弄清楚：
1. 应付金额现在是怎么计算的，调用链是什么；
2. 实现这个 spec 需要改动哪些地方；
3. 现有测试是怎么组织的。
先不要给出计划，只说明你的理解。
```

**这一步你要检查：**

- 它读的文件对不对？（可以看界面上的工具调用，或者用第 13 课的 hook 日志。）
- 它描述的现状和你知道的一致吗？如果它对现有代码的理解就错了，后面的计划不可能对。
- 它有没有发现你没想到的东西？比如“`OrderService` 的构造函数在测试里被直接调用，新增依赖会影响所有测试”。

探索范围较大时，可以明确要求它用子 agent：“用子 agent 调研……，只把结论告诉我。”调研中读过的文件就不会留在主对话的上下文里（第 11 课）。

## 第二步：计划

理解对了，再让它出计划：

```text
现在给出实施计划：要修改和新增哪些文件，每个文件改什么，按什么顺序做，
每一步怎么验证。列出你看到的风险和需要我决定的问题。
```

Claude Code 会把计划展示出来，等你批准。按 `Ctrl+G` 可以在你的文本编辑器里直接修改计划。

**审计划时，看这几样：**

| 检查项 | 典型问题 |
| --- | --- |
| 范围 | 计划里有没有 spec 的“不做”一节明确排除的内容？ |
| 改动点 | 有没有改动它不该改的接口或公共方法签名？ |
| 顺序 | 是否先写或先改测试，让每一步都可以验证？ |
| 测试 | 测试用例是否覆盖了 spec 里的每一条业务规则和边界？ |
| 待决问题 | 它提出的问题，你是否都给了明确答复？ |

有问题就直接说，比如“不要修改 `Order` 的构造函数，会员等级只在计算金额时查询”。在计划阶段改一句话，比在实现之后改十个文件便宜得多。

## 第三步：实现

批准计划，或者按 `Shift+Tab` 离开计划模式，让它开始实现：

```text
按计划实现。先写测试，再写实现。每完成一步运行 mvn -q test，
全部完成后贴出最后一次测试的输出。
```

实现阶段你不需要盯着每一步，但要知道怎么及时干预：

- **看任务清单。** 它会把计划拆成待办项，逐项打勾。如果清单开始偏离计划，比如多出了一项你没批准的“顺便重构”，立刻纠正。
- **按 `Esc` 中断。** 当前的工具调用会被取消，上下文保留，你可以给出新的指示。
- **直接输入纠正。** 不按 `Esc` 也可以直接输入消息并回车，它会在当前的工具调用结束后读到你的消息，再调整下一步。
- **发现方向错了，就回退。** 按两次 `Esc` 或 `/rewind`，把代码和对话一起退回到出错之前，然后换个说法重来。

## 第四步：审查与提交

它说完成之后，不要直接提交：

1. **看证据。** 它有没有贴出测试的实际输出？如果只说“测试已通过”，让它贴出来，或者自己跑一次 `mvn -q test`。
2. **看 diff。** 用 `git diff` 逐个文件看一遍，对照计划，看有没有计划外的改动。第 19 课会给出完整的审查清单。
3. **提交。** 让它写提交信息：

```text
提交这些改动，提交信息用中文，说明做了什么和为什么。
```

## 动手：实现会员折扣

在 order-lab 里，用上一课生成的 SPEC.md（如果没有，可以使用上一课正文中的 spec 示例，保存为 SPEC.md），完整地走一遍四个步骤：

```sh
cd ~/order-lab
git status                         # 确认工作区干净（SPEC.md 可以先提交）
claude --permission-mode plan
```

1. 用“探索”一节的提示词让它说明理解。对照代码，找出它理解中的错误或遗漏（如果有）。
2. 让它出计划。按 `Ctrl+G` 打开计划，至少改一处：比如补一个它漏掉的边界测试，或者删掉一项超出范围的改动。
3. 批准计划，让它实现。实现过程中，故意插一句话：“`MemberLevelProvider` 改名为 `MemberDirectory`。”观察它如何调整。
4. 自己运行 `mvn -q test`，看 `git diff`，然后让它提交。

做完后回顾一下：四个步骤里，你在哪一步纠正它的次数最多？纠正发生得越早，代价就越小。

## 小结

- 能用一句话说清的改动直接做；不确定、涉及多个文件或不熟悉的代码，先计划。
- 探索：让它说出对现有代码的理解，先确认理解正确。
- 计划：检查范围、改动点、顺序、测试和待决问题，用 `Ctrl+G` 直接编辑。
- 实现：看任务清单，用 `Esc` 中断、直接输入纠正、用 `/rewind` 回退。
- 提交之前：看证据，看 diff，再提交。

## 动手练习

1. 完成“实现会员折扣”的四个步骤，记录每一步你纠正了它什么。
2. 找一个改动能用一句话描述的小任务（比如给 `OrderService` 的某个异常信息加上订单 id），分别用“直接做”和“先计划”两种方式完成。用第 13 课的方法比较两次消耗的 token。
3. 在你自己的项目里，挑一个涉及多个文件的小需求，用计划模式完成探索和计划两步（不必实现）。把它的计划和你自己会怎么做进行对比。
