做应用开发不需要推导反向传播，但需要一个足够准确的心智模型：它能解释为什么模型会“忘事”、为什么长输入更贵、为什么它会一本正经地编造。这一课只讲对写代码有影响的部分。

## 一句话版本：预测下一个 token

大语言模型（LLM）做的事情可以概括为：**给定前面的文本，预测下一个 token 的概率分布，从中选一个，接到文本后面，再重复。**

```text
输入： 接口幂等性是指
第 1 步：预测 → "同一"（概率最高）      文本变为：接口幂等性是指同一
第 2 步：预测 → "请求"                  文本变为：接口幂等性是指同一请求
第 3 步：预测 → "执行"                  ……
……直到生成结束标记，或达到长度上限
```

这个过程叫**自回归生成**。几个直接推论：

- **输出是一个一个吐出来的。** 这就是流式输出（streaming）能实现的原因，也是生成长回答耗时更长的原因。
- **每一步都基于之前的全部内容。** 模型前面写错了一个前提，后面会顺着错的前提继续写下去。
- **“回答”只是一种续写。** 模型经过大量对话数据和人类反馈的训练，学会了把“用户提问”续写成“有帮助的回答”，但底层机制仍然是预测。

模型内部是 Transformer 结构。对应用开发者来说，记住它的一个特点就够了：生成每个 token 时，模型会通过**注意力机制**查看上下文中的所有 token，判断哪些和当前位置相关。所以上下文越长，计算量越大，费用和延迟也越高。

## Token：模型的计量单位

模型不直接处理字符，而是处理 **token**。分词器（tokenizer）把文本切成模型词表中的片段：常见的英文单词往往是一个 token，不常见的词会被拆成几段；中文通常一到几个汉字一个 token，具体取决于分词器。

token 对开发者重要，是因为几乎所有限制都按 token 计算：

| 用 token 计算的东西 | 影响 |
| --- | --- |
| 上下文窗口 | 一次请求最多能放多少内容 |
| `max_tokens` | 一次回答最多生成多少 |
| 价格 | 输入和输出分别按百万 token 计价 |
| 限流 | 每分钟可用的输入、输出 token 数 |

不要用字符数去估算 token。不同模型的分词器不同，同一段文字在不同模型上的 token 数也会不同。需要精确数字时，直接问 API：Messages API 有专门的 token 计数接口（`POST /v1/messages/count_tokens`），每次响应的 `usage` 字段也会返回实际用量（下面是节选）：

```json
"usage": {
  "input_tokens": 52,
  "output_tokens": 187
}
```

## 上下文窗口：一次请求能“看到”的全部

**上下文窗口**是一次请求中输入和输出加起来的 token 上限。模型只能基于窗口里的内容工作，窗口外的东西对它来说不存在。

以 2026 年 10 月的 Claude 模型为例（以官方文档为准）：

| 模型 | 上下文窗口 | 输入价格（每百万 token） | 输出价格（每百万 token） |
| --- | --- | --- | --- |
| Claude Opus 5.5 | 1M | $4 | $20 |
| Claude Sonnet 5.5 | 1M | $2 | $10 |
| Claude Haiku 4.5 | 200K | $1 | $5 |

两点值得注意：

- **输出比输入贵得多**，通常是五倍。让模型“写少一点”是有效的省钱方式。
- **窗口大不等于应该塞满。** 窗口能放下整个代码库，但放进去的每个 token 都要付费，也会增加延迟。无关内容还可能干扰模型对重点的判断。后面讲 RAG 时会回到这个问题：只放相关的内容。

## 无状态：模型不记得上一次调用

这一点对后端工程师最容易理解，也最容易在实践中忘记：**模型 API 是无状态的。**

你在聊天产品里看到的“它记得我刚才说的话”，是因为客户端每次请求都把完整的对话历史重新发了一遍：

```text
第 1 次请求：[用户：我叫小王]
第 2 次请求：[用户：我叫小王] [助手：你好小王] [用户：我叫什么？]
第 3 次请求：[用户：我叫小王] [助手：你好小王] [用户：我叫什么？] [助手：你叫小王] [用户：……]
```

后果是：

- **对话越长，每次请求越贵。** 第 20 轮对话会重新为前 19 轮付输入费用。这也是第 8 课要讲 prompt caching 的原因。
- **“记忆”是你的责任。** 存什么、存多久、超长时怎么截断或摘要，都是应用层的设计，和你设计 session 存储没有本质区别。
- **每个请求都可以独立重放。** 这对调试很有用：把出问题的那次请求原样保存下来，就能复现。

## 模型知道什么，不知道什么

模型的知识来自训练数据，有一个**知识截止时间**。它不知道截止时间之后发生的事，也不知道你公司的内部文档、数据库里的订单、昨天的线上事故。

如果你问它不知道的东西，它不一定会说“不知道”。因为它的工作方式是生成**看起来合理的续写**，在缺少依据时，它可能编造出格式正确、内容错误的答案。这就是常说的**幻觉**（hallucination）。

应对思路贯穿整门课：

| 问题 | 做法 | 对应课程 |
| --- | --- | --- |
| 不知道私有数据 | 把相关资料放进上下文 | 第四部分 RAG |
| 不知道实时信息 | 让模型调用工具去查 | 第三部分工具调用 |
| 可能编造 | 要求引用来源，并在程序里校验 | 第 16 课 |
| 输出格式不稳 | 用 schema 约束输出 | 第 6 课 |

## 推理模型与 thinking

较新的模型在给出最终回答之前，可以先生成一段“思考”内容（Claude API 里称为 thinking），把问题拆开、检查中间步骤，再输出答案。这对数学、代码和多步骤任务的准确率帮助很大，代价是更多的输出 token 和更长的耗时。

在 Claude 的新一代模型上，思考是默认开启的，由模型根据问题难度自己决定想多少（adaptive thinking）。你能调节的是**投入程度**（effort），下一课会具体讲。

## 小结

- LLM 一次预测一个 token，输出是逐步生成的。
- token 是计量单位：上下文、输出上限、价格和限流都按它算。
- 上下文窗口是模型能看到的全部，窗口外的内容对它不存在。
- API 无状态，对话历史需要每次重新发送，记忆是应用层的事。
- 模型不知道私有和实时数据，缺少依据时可能编造。

## 练习

1. 假设一个客服对话平均 10 轮，每轮用户输入 100 token、模型回答 300 token，系统提示 1,000 token。在不使用缓存的情况下，估算第 10 轮请求的输入 token 数，以及整段对话累计的输入和输出 token 数。用 Sonnet 5.5 的价格算出总费用。
2. 用自己的话解释：为什么聊天产品里说“忘掉刚才的话”，在 API 层面其实就是“下次请求不发那段历史”？
3. 想一个你业务中模型一定不知道的问题（比如某个内部接口的错误码含义）。思考：要让模型正确回答，需要在请求里提供什么？
