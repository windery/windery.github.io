agent 写代码很快，审查就成了整个流程的瓶颈。更麻烦的是，AI 写的代码**看起来总是很像样**：命名规范、注释齐全、测试也通过了。人写的烂代码往往一眼就能看出来，AI 写的问题代码却藏在像样的外表下面。

这一课整理 AI 代码最常见的错误模式，它们大多能追溯到第 3 课讲的训练过程。然后给出一个审查流程和一份清单，最后用一个故意埋了问题的补丁练手。

## 典型的错误模式

| 错误模式 | 表现 | 来源 |
| --- | --- | --- |
| 过度实现 | 加了没要求的功能、配置项、抽象层，“顺便”重构了无关代码 | 模型倾向于给出“更完整”的回答 |
| 假装通过的测试 | 断言没有意义（`assertNotNull`）；测试名说的和测的不一致；测试只是把实现再算一遍 | 训练中“让检验通过”的目标 |
| 放宽已有的测试 | 改了期望值、加大了误差、注释掉断言、加 `@Disabled` | 同上，这是最需要警惕的一类 |
| 悄悄放宽约束 | 删掉了校验；`catch (Exception e)` 吞掉异常；加 `-DskipTests`；把类型从具体改为宽泛 | 为了让代码“能跑” |
| 编造或过时的 API | 不存在的方法、旧版本的用法 | 预训练的模式补全、知识截止 |
| 违背项目约定 | 用 double 算钱、直接调 `Instant.now()`、不用项目已有的工具类 | 没读到或没遵守项目记忆 |
| 边界与并发 | 门槛值的 `>` 和 `>=`、空集合、四舍五入、共享的可变状态 | 常见代码里这些细节本来就容易错 |
| 残留物 | `System.out.println`、调试代码、和实现不一致的注释 | 迭代过程中留下的 |

编造的 API 通常会被编译器发现（第 16 课）。但写在字符串里的东西编译器检查不到：配置项的 key、SQL、反射调用的方法名、日志格式。这些地方要多看一眼。

## 审查的顺序

面对一个几百行的 diff，从第一个文件读到最后一个文件效率很低。推荐的顺序是：

1. **先看需求和计划。** 重新读一遍 spec 和批准过的计划，带着“应该改什么”去看“实际改了什么”。
2. **再看范围。** `git diff --stat`：改了哪些文件？有没有计划之外的文件？改动量和需求的大小是否匹配？
3. **先看测试，再看实现。** 测试说明了它认为的需求是什么。先确认测试测的是对的东西，再看实现是否满足测试。**已有测试的任何改动都要逐行看。**
4. **再看实现。** 对照上面的错误模式，重点看校验、异常处理、边界条件和约定。
5. **自己运行一次。** `mvn -q test`，必要时启动应用调一次接口。不要只相信它贴出的输出。

有疑问时可以直接问 agent，但注意第 3 课说的“顺着你说”：问“为什么在这里 catch Exception”，而不是“这里 catch Exception 是不是有问题”。前一种问法得到的是解释，后一种问法得到的很可能是认错，哪怕原来的写法其实是对的。

## 让另一个会话来审查

写代码的会话天然倾向于认为自己写的是对的。官方最佳实践推荐“写和审分开”：一个会话写，另一个**全新的会话**审。新会话没有参与编写，不会受之前讨论的影响。

Claude Code 提供了几种方式：

- **`/review`**：审查当前的改动（也可以指定分支或 PR），找出其中的问题。
- **`/security-review`**：专门检查当前分支相对于默认分支的安全问题，比如注入、认证问题、敏感数据泄露。
- **自定义审查子 agent**：上一课的 `test-reviewer` 就是一个例子，可以按你们团队的关注点定制。
- **开一个新会话**：用 `/clear` 或在另一个终端里启动 `claude`，让它“审查 `git diff` 中的改动，只报告问题，不要修改”。

AI 审查能发现很多问题，但不能代替你的判断。它不知道这个需求背后的业务背景，也不会为线上事故负责。把它当作第一轮筛查，最后的判断由人来做。

## 审查清单

把下面这份清单保存到项目里（比如 `docs/ai-review-checklist.md`），每次审查 AI 代码时过一遍：

```markdown
# AI 代码审查清单

## 范围
- [ ] 改动的文件都在计划之内，没有“顺便”的重构或新功能
- [ ] 没有新增未经同意的依赖、配置项、公共 API

## 测试
- [ ] 已有测试的修改逐行检查过：期望值、误差、断言、@Disabled
- [ ] 新测试的名字和它实际验证的内容一致
- [ ] 每个断言都有意义（不是 assertNotNull / assertTrue(true) 之类）
- [ ] spec 中的每条业务规则和边界情况都有对应的测试
- [ ] 我自己运行过测试

## 实现
- [ ] 没有删除或放宽已有的校验
- [ ] 没有吞掉异常（catch 之后只打印或什么都不做）
- [ ] 门槛值、空值、空集合、四舍五入的处理正确
- [ ] 遵守项目约定（金额类型、时间获取方式、已有工具类）
- [ ] 没有共享的可变状态，或者已经考虑了并发
- [ ] 字符串里的配置 key、SQL、类名是存在且正确的

## 收尾
- [ ] 没有调试输出、临时代码、和实现不一致的注释
- [ ] 没有密钥、内部地址等敏感信息
```

## 动手：审查一个有问题的补丁

下面这个补丁实现了“下单超过 30 分钟未支付，就不能再支付”的需求。它能编译，测试也全部通过。请找出其中的问题。

在 order-lab 的一个干净工作区里应用它：

```sh
cd ~/order-lab
git status                                     # 确认工作区干净
git switch -c review-exercise
curl -LO https://windery.github.io/courses/ai-dev/code/review-exercise.patch
git apply review-exercise.patch
mvn -q test                                    # 测试会通过
git diff
```

也可以[直接在浏览器里查看补丁](/courses/ai-dev/code/review-exercise.patch)。

1. **先自己审。** 对照清单，把你发现的问题写下来。
2. **再让 AI 审。** 开一个新会话，运行 `/review`，或者输入“审查当前 `git diff` 中的改动，只报告问题，不要修改”。比较它找到的和你找到的。
3. **对照答案。** 下面列出了埋在补丁里的问题，看看你们各漏掉了几个。

<details>
<summary>参考答案（先自己找，再展开）</summary>

1. **用了 `Instant.now()`**，而不是注入的 `Clock`。违反项目约定，而且时间相关的逻辑因此无法被测试固定。
2. **`try/catch` 吞掉了自己抛出的异常。** `isPaymentExpired` 为真时抛出的 `IllegalStateException` 被下面的 `catch (Exception e)` 捕获，只打印一行日志，然后照样把订单改成已支付。**这条业务规则实际上完全没有生效。**
3. **过度实现：`adminOverride`。** 需求里没有“管理员跳过检查”。而且它是 `OrderService` 上的一个可变字段，一旦设置，对之后所有订单都生效，在多线程下也不安全。
4. **假装通过的测试：`payExpiredOrder`。** 名字说的是“支付过期订单”，断言却是 `assertNotNull(order.getStatus())`，无论结果如何都会通过。正确的测试应该断言抛出异常，并且用 `Clock` 控制时间。
5. **放宽了已有的测试。** `payableAmountWithLevel2Discount` 的断言被改成了 `double` 比较，误差是 1.0 元。原来精确的金额断言被悄悄削弱了，而这个改动和需求毫无关系。
6. **边界值没有确认。** `compareTo(PAYMENT_TIMEOUT) > 0` 意味着恰好 30 分钟时仍可支付。这可能是对的，但需求里的“超过 30 分钟”需要和产品确认，并且应该有一个恰好 30 分钟的测试。
7. **残留的 `System.out.println`。**

第 2 和第 5 条最危险：测试全部通过，业务规则却没有生效，原有的保护也被削弱了。只看“测试通过”的审查，这两条都会漏掉。

</details>

审查完成后，你可以让 Claude 根据审查意见修复，修复后再审一轮；或者直接丢弃这个分支：

```sh
git checkout -- . && git switch - && git branch -D review-exercise
```

## 小结

- AI 写的代码看起来总是很像样，问题藏在细节里，很多能追溯到训练带来的倾向。
- 重点警惕：过度实现、假装通过的测试、被放宽的已有测试、被吞掉的异常、违背项目约定。
- 审查顺序：需求和计划 → 改动范围 → 测试 → 实现 → 自己运行。
- 用中性的方式向 agent 提问；用新会话或审查子 agent 做第一轮筛查，最后的判断由人来做。

## 动手练习

1. 完成“审查一个有问题的补丁”，记录你自己找到了几个问题，AI 审查找到了几个，各漏掉了哪些。
2. 根据你们团队的技术栈，给审查清单加三条：比如 Spring 项目可以加“事务边界是否正确”“是否在循环里查询数据库”。
3. 把审查清单改写成一个审查子 agent（参考上一课的 `test-reviewer`），用它审查你最近一次让 AI 写的代码。
