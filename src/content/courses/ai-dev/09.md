第 8 课的 MiniAgent 修好了一个 20 行的类。把它放进一个有几百个文件的 Spring Boot 项目，问题马上就会出现：

- **找不到代码。** 它只能用 `run_command` 跑 `grep -r`，每次都要你确认，输出还会把 `target/` 里的编译产物一起搜出来。
- **读得太多。** `read_file` 一次读入整个文件。一个 2000 行的 Service 类，可能就占掉两万多个 token，而且之后每一轮都要重新发送。
- **改得太贵。** `write_file` 每次都要把整个文件重新输出一遍。输出 token 的单价是输入的五倍，改一行代码要重写三百行。模型重写时还可能顺手漏掉或改动其他代码。
- **输出太长。** 一次 `mvn test` 的输出可能有几千行，真正有用的报错在最后，而第 8 课的截断恰好只保留开头。

这一课给 MiniAgent 换一套工具箱。你会发现，这套工具和 Claude Code 内置的工具几乎一一对应，因为它们要解决的是同样的问题。

## 工具设计就是接口设计

普林斯顿大学的 SWE-agent 论文（2024）提出了一个说法：**agent-computer interface（ACI）**。人用 IDE 写代码，IDE 的界面是为人设计的；agent 也需要一套为它设计的“界面”，就是工具。论文的实验显示，只改工具的设计，不换模型，同一个模型解决真实 GitHub issue 的成功率就有明显差别。Anthropic 在《Building effective agents》一文中也给出了同样的建议：花在工具设计上的精力，应该和花在 prompt 上的一样多。

对后端工程师来说，这套原则一点都不陌生，它就是好的 API 设计：

| 原则 | 在工具上的体现 |
| --- | --- |
| 粒度合适 | 先搜索、再定位、再读局部，而不是一次读入整个项目 |
| 返回值为调用方设计 | 读文件时带行号；搜索结果是“路径:行号: 内容”；截断时说明还剩多少 |
| 错误信息可操作 | 报错里写清楚哪里不对、下一步该怎么做 |
| 防呆 | 路径一律相对项目根目录；编辑时要求被替换的文本唯一 |

第三条值得多说一句：**工具的错误信息是写给模型看的提示词。** “替换失败”只会让模型盲目重试；“old_string 出现了 2 次，请包含更多上下文”则直接告诉它怎么改。

## 新的工具箱

| 工具 | 作用 | 只读 | Claude Code 中对应的工具 |
| --- | --- | --- | --- |
| `list_files` | 按 glob 模式列出文件 | 是 | Glob |
| `grep` | 按正则搜索文件内容 | 是 | Grep |
| `read_file` | 带行号读取，支持分段 | 是 | Read |
| `edit_file` | 精确替换一段文本 | 否 | Edit |
| `write_file` | 创建新文件 | 否 | Write |
| `run_command` | 执行命令，支持超时，输出保留首尾 | 否 | Bash |

“只读”这一列决定是否需要确认：只读工具直接执行，其余的先问你。这样 agent 在探索代码时不会每一步都打断你，第 12 课会把这个开关扩展成完整的权限模式。

完整代码约 400 行：[MiniAgent.java（第 9 课版本）](/courses/ai-dev/code/09/MiniAgent.java)。把它覆盖到第 7 课创建的 `mini-agent/src/main/java/demo/MiniAgent.java`，运行方式和第 8 课相同。下面逐块讲改动。

## 改动一：工具注册表

工具多了以后，第 8 课里的 `switch` 会越来越长。先把每个工具的定义、是否只读、执行逻辑放在一起：

```java
interface Handler {
    String run(ToolUseBlock call) throws Exception;
}

/** readOnly 的工具直接执行；会改变文件或执行命令的工具，执行前要用户确认。 */
record AgentTool(Tool definition, boolean readOnly, Handler handler) {}
```

注册一个工具就是一次 `register(tool(...))` 调用，比如 `grep`：

```java
register(tool("grep",
        "在项目文件中按正则表达式搜索，返回“路径:行号: 内容”。可以用 glob 限定文件范围，例如 **/*.java。",
        true,
        Map.of("pattern", Map.of("type", "string", "description", "Java 正则表达式"),
               "glob", Map.of("type", "string", "description", "可选，只搜索匹配的文件")),
        List.of("pattern"), MiniAgent::grep));
```

执行时查表，只读的直接运行，其他的先确认：

```java
static ToolResultBlockParam execute(ToolUseBlock call) {
    AgentTool tool = TOOLS.get(call.name());
    if (tool == null) return error(call, "未知工具：" + call.name());
    System.out.println("  → " + call.name() + " " + brief(call));
    try {
        if (call.name().equals("edit_file")) checkEdit(call); // 先校验，免得用户确认了一个注定失败的修改
        if (!tool.readOnly() && !confirm(call)) return error(call, "用户拒绝了这个操作。");
        return ToolResultBlockParam.builder().toolUseId(call.id()).content(truncate(tool.handler().run(call))).build();
    } catch (IllegalArgumentException e) {
        return error(call, e.getMessage());
    } catch (Exception e) {
        return error(call, e.toString());
    }
}
```

## 改动二：搜索

`list_files` 和 `grep` 都基于同一个文件遍历，它会跳过 `.git`、`target`、`node_modules` 这些目录。这些目录里的内容对理解代码没有帮助，却会让搜索结果膨胀几十倍：

```java
/** 项目中的所有文件（相对路径），跳过 SKIP_DIRS。 */
static List<Path> projectFiles() throws IOException {
    List<Path> files = new ArrayList<>();
    Files.walkFileTree(ROOT, new SimpleFileVisitor<>() {
        @Override
        public FileVisitResult preVisitDirectory(Path dir, BasicFileAttributes attrs) {
            return !dir.equals(ROOT) && SKIP_DIRS.contains(dir.getFileName().toString())
                    ? FileVisitResult.SKIP_SUBTREE : FileVisitResult.CONTINUE;
        }

        @Override
        public FileVisitResult visitFile(Path file, BasicFileAttributes attrs) {
            if (attrs.isRegularFile()) files.add(ROOT.relativize(file));
            return FileVisitResult.CONTINUE;
        }
    });
    files.sort(null);
    return files;
}
```

`grep` 的输出格式是 `路径:行号: 内容`，和你在终端里用 `grep -n` 看到的一样。模型对这种格式很熟悉，拿到行号后可以直接用 `read_file` 的 `offset` 跳过去。注意它在超过 100 处匹配时停下，并告诉模型“请缩小范围”，而不是把几千行结果一股脑塞进上下文：

```java
static String grep(ToolUseBlock call) throws IOException {
    Pattern regex = Pattern.compile(arg(call, "pattern"));
    String glob = optArg(call, "glob");
    List<String> hits = new ArrayList<>();
    int limit = 100;
    for (Path file : projectFiles()) {
        if (glob != null && !globMatches(glob, file)) continue;
        Path absolute = ROOT.resolve(file);
        if (Files.size(absolute) > 1_000_000) continue;
        List<String> lines;
        try {
            lines = Files.readAllLines(absolute);
        } catch (IOException notText) {
            continue; // 二进制或非 UTF-8 文件
        }
        for (int i = 0; i < lines.size(); i++) {
            Matcher m = regex.matcher(lines.get(i));
            if (!m.find()) continue;
            if (hits.size() == limit) {
                return String.join("\n", hits) + "\n……匹配超过 " + limit + " 处，请用更具体的模式或 glob 缩小范围。";
            }
            String line = lines.get(i).strip();
            hits.add(file + ":" + (i + 1) + ": " + (line.length() > 200 ? line.substring(0, 200) + "…" : line));
        }
    }
    return hits.isEmpty() ? "没有匹配。" : String.join("\n", hits);
}
```

为什么不直接让模型用 `run_command` 执行 `grep -r`？有三个原因：一条 shell 命令是否只读，程序很难可靠判断（第 12 课会讲），所以只能每次都请你确认；`grep -r` 不会跳过构建目录；它的输出长度也没有上限。专门的工具把这三件事都解决了。

## 改动三：带行号、可分段的读取

```java
static String readFile(ToolUseBlock call) throws IOException {
    List<String> lines = Files.readAllLines(resolve(arg(call, "path")));
    int offset = Math.max(1, intArg(call, "offset", 1));
    int limit = Math.max(1, intArg(call, "limit", 400));
    int end = Math.min(lines.size(), offset - 1 + limit);
    StringBuilder out = new StringBuilder();
    for (int i = offset - 1; i < end; i++) {
        out.append(String.format("%6d\t%s%n", i + 1, lines.get(i)));
    }
    if (offset > 1 || end < lines.size()) {
        out.append("（文件共 ").append(lines.size()).append(" 行，以上是第 ").append(offset)
           .append("–").append(end).append(" 行。）");
    }
    return out.toString();
}
```

行号有两个用处：模型和你沟通时可以说“第 42 行”；和 `grep` 的结果配合，可以只读相关的那几十行。工具描述里特意写了“行号不是文件内容”，否则模型在编辑时可能把行号也抄进要替换的文本里。

## 改动四：精确替换代替整文件重写

`edit_file` 只需要模型给出两段文本：要替换的原文和新内容。

```java
static String editFile(ToolUseBlock call) throws IOException {
    Path file = checkEdit(call);
    String content = Files.readString(file);
    Files.writeString(file, content.replace(arg(call, "old_string"), arg(call, "new_string")));
    return "已修改 " + arg(call, "path");
}

/** old_string 必须恰好出现一次。错误信息写给模型看，告诉它下一步该怎么做。 */
static Path checkEdit(ToolUseBlock call) throws IOException {
    Path file = resolve(arg(call, "path"));
    int count = countOccurrences(Files.readString(file), arg(call, "old_string"));
    if (count == 0) {
        throw new IllegalArgumentException("文件中没有找到 old_string。请先用 read_file 查看当前内容，"
                + "注意缩进和空白要完全一致，且不要包含行号。");
    }
    if (count > 1) {
        throw new IllegalArgumentException("old_string 在文件中出现了 " + count + " 次。请包含更多上下文，使它只出现一次。");
    }
    return file;
}
```

这个设计有几个好处：

- **省输出 token。** 改一行代码，模型只需输出这一行和必要的上下文，而不是整个文件。
- **改动可审查。** 确认时，终端里会打印出 `-` 和 `+` 两段文本，就像一个小 diff。整文件重写时你很难看出它到底改了什么。
- **不会误伤其他代码。** 没有出现在 `old_string` 里的部分，一个字符都不会动。

“必须唯一”是防呆设计：如果 `old_string` 出现了多次，程序不猜测要改哪一处，而是让模型补充上下文。工具描述里还写了“修改前应先用 read_file 读过该文件”，因为模型只有看过文件的当前内容，才能写出逐字一致的原文。Claude Code 的 Edit 工具遵循同样的规则：要求先读文件，且被替换的文本必须唯一。

`execute` 在请求确认之前先调用了 `checkEdit`。这样，一个注定失败的修改不会先让你按一次 `y`。

## 改动五：命令输出保留首尾

```java
/** 命令输出过长时保留开头和结尾：开头有命令的上下文，结尾通常是错误和汇总。 */
static String headAndTail(String s, int head, int tail) {
    if (s.length() <= head + tail) return s;
    return s.substring(0, head)
            + "\n……（省略中间 " + (s.length() - head - tail) + " 个字符）……\n"
            + s.substring(s.length() - tail);
}
```

构建和测试工具的输出有个规律：开头是在做什么，结尾是结果和错误汇总。Maven 的 `BUILD FAILURE` 和失败的测试列表都在最后。所以截断时保留开头 4000 个字符和结尾 12000 个字符，中间告诉模型省略了多少。

`run_command` 还多了一个可选参数 `timeout_seconds`。跑一个完整的集成测试可能需要几分钟，模型可以按需要放宽超时。

## 动手

**1. 让它读一个真实的项目。** 进入你自己的一个 Spring Boot 项目，启动 agent：

```sh
cd ~/your-spring-boot-project
mvn -q -f ~/mini-agent/pom.xml compile exec:java -Dexec.mainClass=demo.MiniAgent
```

```text
> 找到处理“创建订单”的接口（换成你项目里的一个真实功能），说明从 Controller 到数据库的调用链，标出每一层的文件和行号。不要修改任何文件。
```

这个任务只用到只读工具，整个过程不需要你确认。观察它的工具调用顺序：通常是 `grep` 找到入口，再 `read_file` 带着 `offset` 读局部，然后顺着方法调用继续 `grep`。对照每一步的 `input_tokens`，和第 8 课一次读整个文件的方式比较。

**2. 让它做一个修改。** 回到第 8 课的 `~/agent-lab`：

```text
> 给 PriceCalculator 增加一条规则：满 300 元（含 300）减 60，与满 100 减 20 不叠加。在 main 里加两条对应的检查，然后运行验证。
```

确认 `edit_file` 时，读一读终端里打印的 `-` 和 `+` 两段文本。这就是你在 Claude Code 里看到的 diff 确认的原型。

**3. 比较两种编辑方式的成本。** 在 `static { ... }` 里把注册 `edit_file` 的那一行注释掉，重新做第 2 步（先用 `git checkout` 或手动恢复 PriceCalculator.java）。这时模型只能用 `write_file` 重写整个文件。比较两次运行中，修改那一步的 `output_tokens`。

## 小结

- 工具是 agent 的“界面”，工具设计的好坏直接影响 agent 的表现，原则和 API 设计相同。
- 搜索工具让 agent 只读需要的代码；带行号的分段读取让定位更精确。
- 精确替换比整文件重写更省 token、更容易审查，也不会误改其他代码。“必须唯一”是防呆设计。
- 工具的错误信息是写给模型的提示词，要写清楚下一步怎么做。
- 命令输出保留首尾，因为错误和汇总通常在最后。

## 动手练习

1. 完成“动手”中的三个任务，记录第 3 步两种方式的 `output_tokens`。
2. 故意制造一次编辑失败：在 agent 读过 PriceCalculator.java 之后，你自己在编辑器里改动其中一行，再让它修改这一行附近的代码。观察它收到“没有找到 old_string”后怎么处理。
3. 给 `read_file` 增加一个检查：如果文件超过 200 KB，返回错误，提示模型先用 `grep` 定位、再用 `offset` 和 `limit` 读取需要的部分。写好错误信息后，找一个大文件试试，看模型是否照着提示做。
