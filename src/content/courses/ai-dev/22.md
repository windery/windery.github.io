上一课完整地交付了一个功能。这一课回头算账：这样做到底划不划算？什么时候不该用 agent？花了多少钱？如果要在团队里推广，该怎么做？

这些问题没有统一的答案，它们取决于你的项目、你的团队和你自己。这一课给出思考的框架和统计的方法，答案要用你自己的数据来得出。

## 先看自己的记录

如果你在上一课按建议记了 NOTES.md，先回答这几个问题：

1. 八个步骤里，你自己花的时间（写需求、审计划、审代码、验证）和等待 agent 的时间，各占多少？
2. 你纠正了它几次？每次纠正的原因是什么：需求没说清楚、它没遵守约定、还是它的能力不够？
3. 如果完全自己写，你估计要多久？
4. 最终的代码，你有没有完全理解？如果明天线上出了问题，你能不能直接定位？

第 4 个问题经常被忽略，却最重要。**你不理解的代码，不能算交付了。** agent 写得再快，如果审查时你只是“看起来没问题”就合并，节省的时间会在之后排查问题时加倍还回去。

## 什么时候用 agent 不划算

使用 agent 的收益，可以粗略地这样估算：

```text
收益 = 自己写需要的时间 −（写需求 + 审计划 + 审代码 + 返工 + 等待中无法做别的事的时间）
```

括号里的每一项都不是零。把这个式子套到不同类型的任务上，就能看出哪些不划算：

| 任务类型 | 为什么容易不划算 | 更好的做法 |
| --- | --- | --- |
| 很小的改动，比如改一个常量 | 写提示词、等它、看 diff 的时间，比自己改还长 | 自己改 |
| 需求本身还没想清楚 | agent 会替你做决定，而且做得很像样，你很难发现它决定了什么 | 先自己想清楚，或者只让它采访你（第 14 课） |
| 依赖大量隐性知识，比如“这个字段在下游某系统里有特殊含义” | 它读不到这些知识，你要花大量篇幅解释 | 先把知识写进文档或 CLAUDE.md，再决定是否交给它 |
| 没有测试的遗留代码上的大重构 | 没有反馈闭环，它不知道自己改坏了什么，你也不知道 | 先让它补测试（这本身是很好的 agent 任务），再重构 |
| 性能调优 | 需要真实的测量数据和环境，它只能凭经验猜 | 你来测量和定位，它帮你写基准测试或实现已经确定的优化 |
| 涉及资金、权限、安全的核心逻辑 | 可以用，但审查成本很高，每一行都要细看 | 只让它做有明确 spec 和充分测试的部分 |

反过来，最划算的任务通常有这些特征：需求清楚、有可以运行的检查（测试、编译、lint）、改动的影响范围清楚、你能快速判断结果对不对。补测试、写脚本、按已有模式加接口、解释陌生代码、排查有明确报错的问题，都属于这一类。

## 失败的信号：什么时候该停下来

和人合作一样，问题越早发现越好处理。下面这些信号出现时，不要继续推它，而是停下来：

| 信号 | 说明 | 怎么办 |
| --- | --- | --- |
| 同一个问题纠正了两次以上 | 上下文里塞满了失败的尝试（第 17 课） | 让它写下进展，`/clear`，换一个更具体的提示词 |
| 它开始改测试或放宽检查 | 它在“让检查通过”，而不是“让功能正确”（第 3、19 课） | 立即停止，`/rewind` 回去，在提示词里明确禁止 |
| diff 越来越大，超出了计划 | 它在“顺便”做别的事 | 回到计划，让它只做计划内的改动 |
| 你开始看不懂它写的代码 | 你已经失去了对这段代码的掌控 | 停下来，要它解释，或者回退到你能看懂的地方 |
| 它反复说“现在应该可以了” | 它没有真正的反馈来源，只是在猜 | 补上能运行的检查（第 16 课），没有检查就不要继续 |

失败本身并不可怕，可怕的是在一个已经变差的会话里越陷越深。**回退和重来的成本，几乎总是比继续纠缠更低。** 第 17 课的检查点和 `/clear` 就是为此设计的。

## 算清成本：钱

### 订阅和 API 是两种账

使用 Claude Code 有两种付费方式。用 Pro、Max 这类订阅，费用是固定的月费，用量受限额约束，不按 token 计费；用 API key，按实际消耗的 token 付费。官方文档给出的参考数据是：企业部署中，平均每个开发者每个活跃日大约 13 美元，每月 150 到 250 美元，90% 的用户每个活跃日低于 30 美元。

不管用哪种方式，弄清楚一次任务实际消耗了多少 token 都是有意义的：订阅用户可以知道自己离限额有多远，API 用户可以知道花了多少钱。

### 在 Claude Code 里看

- `/usage`：当前会话的 token 用量和按 API 价格估算的费用，还有 prompt cache 的命中情况。订阅用户还能看到套餐用量。
- `/insights`：分析你最近的会话，生成一份 HTML 报告，内容包括你常做什么类型的工作、哪些地方有摩擦（比如误解了需求、写出了有问题的代码），以及改进建议。
- `claude -p --output-format json` 的结果里有 `total_cost_usd`（第 20 课）。

### 从会话记录里算

第 13 课用 jq 统计过会话记录里的 token 用量。这里把它扩展成一个按模型、按缓存类型计算费用的脚本，子 agent 的用量也算进去（子 agent 的记录在会话目录下的 `subagents/` 里）：

```bash
#!/bin/bash
# 估算一个 Claude Code 会话按 API 价格计算的费用（含它的子 agent）。
# 用法：./session-cost.sh [会话记录.jsonl]，不传参数时取最近修改的会话。
# 价格是每百万 token 的美元价格 [输入, 输出]，来自第 2 课的价格表，以官方价格页为准。
PRICES='{"claude-opus-5-5": [4, 20], "claude-sonnet-5-5": [2, 10], "claude-haiku-4-5": [1, 5]}'

LOG=${1:-$(ls -t ~/.claude/projects/*/*.jsonl | head -1)}
FILES=("$LOG")
for f in "${LOG%.jsonl}"/subagents/*.jsonl; do
  [ -e "$f" ] && FILES+=("$f")
done
echo "会话：$LOG（另有 $((${#FILES[@]} - 1)) 个子 agent 记录）"

cat "${FILES[@]}" | jq -s --argjson prices "$PRICES" '
  [.[] | select(.type == "assistant" and .message.usage != null)]
  | unique_by(.message.id)
  | group_by(.message.model)
  | map(
      .[0].message.model as $model
      | ($prices | to_entries | map(select(.key as $k | $model | startswith($k))) | .[0].value) as $p
      | map(.message.usage) as $u
      | {
          model:     $model,
          requests:  ($u | length),
          input:     ($u | map(.input_tokens) | add),
          write_5m:  ($u | map(.cache_creation.ephemeral_5m_input_tokens // .cache_creation_input_tokens // 0) | add),
          write_1h:  ($u | map(.cache_creation.ephemeral_1h_input_tokens // 0) | add),
          read:      ($u | map(.cache_read_input_tokens // 0) | add),
          output:    ($u | map(.output_tokens) | add)
        }
      | . + {
          usd: (if $p == null then "未知价格" else
                 ((.input + .write_5m * 1.25 + .write_1h * 2 + .read * 0.1) * $p[0] + .output * $p[1]) / 1e6
                 | . * 100 | round / 100
               end)
        }
    )'
```

下载并运行：

```sh
curl -LO https://windery.github.io/courses/ai-dev/code/session-cost.sh
chmod +x session-cost.sh
./session-cost.sh                                   # 最近的会话
./session-cost.sh ~/.claude/projects/<项目目录>/<会话 id>.jsonl
```

计费规则沿用第 10 课：5 分钟缓存的写入按输入价格的 1.25 倍计算，缓存读取按 0.1 倍计算。Claude Code 常用的 1 小时缓存，写入按输入价格的 2 倍计算。和第 13 课一样，会话记录是 Claude Code 的内部格式，字段可能随版本变化，算出来的数字只是估算。

举一个真实的例子：编写这门课的过程中，有一个持续了几个小时的长会话，用这个脚本统计的结果是：

```json
{
  "model": "claude-opus-5-5",
  "requests": 275,
  "input": 549,
  "write_5m": 0,
  "write_1h": 754472,
  "read": 58384238,
  "output": 334466,
  "usd": 36.08
}
```

拆开来看，读取缓存约 23.4 美元，写入缓存约 6.0 美元，输出约 6.7 美元。**最大的一项是缓存读取**：每一轮请求都要把整段对话重新读一遍，即使按 0.1 倍计价，5800 多万 token 加起来仍然是大头。这从成本的角度说明了第 17 课的结论：会话越长，每一轮都越贵，不相关的任务要及时 `/clear`。

### 降低成本的几个有效做法

按官方文档的建议，效果最明显的几项是：

- **不相关的任务之间 `/clear`。** 原因就是上面的例子。
- **按任务选模型。** 大多数编码任务 Sonnet 就能做好，复杂的架构决策和多步推理再用 Opus。用 `/model` 切换，子 agent 也可以单独指定模型。
- **调低 effort。** 思考的 token 按输出计价。简单任务可以用 `/effort` 降低推理强度。
- **写具体的提示词。** “改进这个代码库”会触发大范围的读取，“给 `OrderService.create` 加上参数校验”只需要读几个文件。
- **让 hooks 和子 agent 处理冗长的输出。** 比如用 hook 过滤测试输出只留失败的部分，或者让子 agent 去读日志，只把结论带回主对话。

## 算清成本：时间

钱通常不是最大的成本，你的时间才是。一个功能 agent 花了 5 美元，而你审查它花了两个小时，这两个小时才是主要的成本。

时间成本只能靠你自己记录。建议在一段时间内（比如两周），对每个用 agent 完成的任务记一行：

| 日期 | 任务 | 类型 | 自己写的估计时间 | 实际总时间 | 其中审查时间 | 返工次数 | 费用 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 10-03 | 限量优惠券 | 新功能 | | | | | |

两周后再看：哪些类型的任务省了时间，哪些反而更慢了。这份数据比任何文章的观点都更适合指导你自己的选择。

## 在团队里落地

一个人用好 agent 和一个团队用好 agent 是两回事。团队里会多出几个问题：配置怎么共享、代码质量怎么保证、新人怎么上手、怎么判断它真的有用。

### 从共享的配置开始

第 18 课的配置文件，就是团队落地最好的起点：

- **CLAUDE.md**：团队约定、常用命令、踩过的坑。所有人的 agent 都按同一套规则工作。
- **`.claude/settings.json`**：共享的权限规则，尤其是 deny 规则，比如禁止读 `.env`、禁止 `git push`。
- **`.claude/skills/`、`.claude/agents/`、`.claude/hooks/`**：团队沉淀下来的工作流程、审查角色和自动检查。

这些文件和代码一样通过 PR 修改。每次有人发现 agent 犯了一个“只要告诉它就不会再犯”的错误，就提一个 PR 把它写进 CLAUDE.md。时间长了，这份文件就是团队的经验库。也要定期清理：第 10 课说过，项目记忆越长，每一条被遵守的可能性越低。

组织层面还可以用**托管设置**（managed settings）统一下发配置，比如强制的权限规则，个人和项目的设置都无法覆盖它。这通常由管理员通过设备管理工具或 `managed-settings.json` 部署。

### 规则：AI 写的代码没有特权

最重要的一条规则是：**提交代码的人对代码负责，不管是谁写的。** 由此推出几条具体做法：

- AI 写的代码走和人写的代码完全相同的审查流程，不因为“是 AI 写的”而降低或提高标准。
- 作者必须能解释代码的每一部分。审查者问“为什么这样写”，回答“AI 写的”是不可以的。
- 审查者重点关注第 19 课的错误模式：被放宽的测试、被吞掉的异常、超出需求的改动。
- 大的改动先提交计划或 spec，在写代码之前达成一致。这对人写的代码同样有益，agent 只是让它变得更必要。

### 分阶段推广

不要一开始就让所有人用 agent 写所有代码。按风险从低到高分阶段推进：

1. **只读任务**：解释陌生代码、回答“这个功能在哪里实现”、分析报错。不改代码，风险最低，也最容易让人建立信心。
2. **测试和工具**：补单元测试、写脚本、写数据迁移的校验工具。这些代码有明确的对错标准。
3. **有 spec 的功能开发**：按上一课的流程，在有测试保护的模块里开发新功能。
4. **自动化**：在 CI 里做自动审查、自动解释失败原因（第 20 课），最后才考虑让它自动开 PR。

每个阶段都留出时间，让团队成员分享自己的经验和踩过的坑，并把共性的问题沉淀到配置里。

### 度量：看结果，不看产量

“AI 写了百分之多少的代码”是一个诱人但没有意义的指标。代码行数从来不是好的产出指标，AI 生成的代码行数更不是。值得看的是团队原本就在乎的结果：

- **交付周期**：从开始做到上线的时间有没有缩短。
- **返工率**：PR 审查中被要求修改的比例、合并后很快被修复或回滚的比例。
- **线上缺陷**：上线后发现的问题有没有增加。
- **开发者的反馈**：大家觉得哪些任务省了时间，哪些反而更麻烦。

如果交付更快了，缺陷没有增加，那就是有用的。如果交付更快了，但缺陷和返工也增加了，节省的时间可能只是被转移到了后面。

## 课程回顾

到这里，这门课的主线就走完了。回顾一下四个部分是怎么连起来的：

| 部分 | 你学到了什么 | 它解释了什么 |
| --- | --- | --- |
| 第一部分：大模型原理 | token、上下文、训练过程、提示词 | agent 为什么会“顺着你说”、为什么会编造、为什么上下文越长越不准 |
| 第二部分：手写 agent | agent 循环、工具、上下文工程、计划、子 agent、权限 | Claude Code 每个功能背后的机制，它为什么那样设计 |
| 第三部分：Claude Code 实践 | 需求、计划、反馈闭环、会话管理、配置、审查、并行 | 怎样把原理转化成日常的工作方法 |
| 第四部分：Spring Boot 实战 | 完整交付一个功能，算清成本 | 方法在真实项目里如何组合，什么时候值得用 |

这门课的目标是“用好编程 agent”，而用好它的核心，是理解它为什么会这样做。工具会变，Claude Code 的命令和参数明年可能就不一样了，但 agent 循环、上下文的限制、训练带来的倾向、反馈闭环的价值，这些原理会长期有效。

第五部分是进阶内容：通读一个开源编程 agent，opencode 的源码，把第二部分的手写版、opencode 和 Claude Code 三者对照起来看。

## 小结

- 判断是否用 agent，要把写需求、审查、返工和等待的时间都算进去。需求清楚、有可运行的检查、结果容易判断的任务最划算。
- 同一问题纠正两次以上、它开始改测试、diff 失控、你看不懂代码，都是该停下来的信号。
- 用 `/usage`、`/insights` 和会话记录了解成本。长会话里最大的开销往往是缓存读取，及时 `/clear` 是最有效的省钱方式。
- 时间成本只能靠自己记录，用两周的数据来指导你的选择。
- 团队落地从共享的配置开始；AI 写的代码没有特权；按风险分阶段推广；度量看交付结果，不看代码产量。

## 动手练习

1. 用 `session-cost.sh` 统计上一课的会话，算出整个功能的费用，以及每个步骤（如果你分了多个会话）各花了多少。哪一步最贵？为什么？
2. 运行 `/insights`，读一读报告里的“摩擦点”。它指出的问题，和你在 NOTES.md 里记录的一致吗？
3. 按“时间成本”一节的表格，记录接下来两周用 agent 完成的任务。两周后总结：哪类任务你会继续交给 agent，哪类你决定自己做。
4. 假设你要在你们团队推广 Claude Code。写一页推广方案：第一阶段做哪些任务、共享哪些配置、团队规则是什么、用什么指标判断效果。
