用熟了 Claude Code 之后，你会发现自己经常在等：等它读代码、等它跑测试、等它改完。自然的想法是：让几个会话同时干活。

这一课讲两件事：**并行**，同时推进多个任务；**自动化**，让 agent 在没有人盯着的地方运行，比如脚本和 CI。两者都让你的产出不再受限于“一次只能看着一个会话”，但也都有各自的陷阱。

## 并行之前先想清楚：瓶颈在你

开三个会话，并不会让你的产出变成三倍。每个会话都需要你写需求、审计划、审代码（第 14、15、19 课），这些都是你的时间。并行真正节省的，是**等待的时间**：一个会话在跑测试，你可以去审另一个会话的计划。

所以适合并行的，是彼此独立、各自边界清晰的任务；不适合的，是需要你持续关注、频繁决策的任务。

## 用 worktree 隔离会话

两个会话在同一个目录里同时改代码，一定会互相覆盖。git worktree 可以让同一个仓库同时检出多个分支，每个分支在自己的目录里，互不干扰。

Claude Code 直接支持这个用法：

```sh
cd ~/order-lab
claude --worktree coupon
```

它会在仓库根目录下创建 `.claude/worktrees/coupon/`，检出一个新分支 `worktree-coupon`，然后在这个目录里启动会话。另开一个终端：

```sh
cd ~/order-lab
claude --worktree refund-rule
```

现在两个会话各自在独立的目录和分支上工作。几个注意事项：

- 把 `.claude/worktrees/` 加进 `.gitignore`（order-lab 已经加好了），否则主目录里会出现一堆未跟踪的文件。
- worktree 是一个全新的检出，`target/` 之类的构建产物不会共享，每个 worktree 第一次构建都要重新编译。被 `.gitignore` 忽略的文件（比如 `.env`）默认也不会复制过去，需要的话可以在 `.worktreeinclude` 文件里列出它们。
- 退出会话时，如果 worktree 里有改动，Claude Code 会问你保留还是删除。保留的话，之后可以用它打印出的 `claude --worktree <名字> --resume` 命令回来继续。
- 做完之后，像合并普通分支一样，把 `worktree-coupon` 合并或者提成 PR。

不用 Claude Code 的参数，也可以用 git 命令手动创建：

```sh
git worktree add ../order-lab-coupon -b coupon
cd ../order-lab-coupon && claude
```

## 并行的几种模式

**相互独立的功能。** 最直接的用法：会员折扣在一个 worktree，支付超时在另一个 worktree。前提是它们改的文件尽量不重叠，否则合并时还是会冲突。

**写和审分开。** 上一课讲过：一个会话写，另一个新会话审。官方最佳实践里的例子是：

| 会话 A（写） | 会话 B（审） |
| --- | --- |
| 实现限流中间件 | |
| | 审查 @src/…/RateLimiter.java，找出边界情况、竞态条件、和现有代码不一致的地方 |
| 根据审查意见修改：[粘贴会话 B 的输出] | |

**测试和实现分开。** 一个会话根据 spec 写测试，另一个会话只看测试和 spec 写实现。写实现的会话没法“顺手”改测试来让自己通过，因为测试不是它写的。

**子 agent 的并行。** 在一个会话里也可以让 Claude 同时派出几个子 agent 做调研（第 11 课）。官方文档提到，自定义子 agent 还可以设置在独立的 worktree 里运行，让会修改文件的子 agent 也能安全地并行。

## 非交互模式：claude -p

`claude -p "提示词"` 以非交互的方式运行一次任务，输出结果后退出。它让 Claude Code 可以像普通命令行工具一样放进脚本：

```sh
# 一次性的问题
claude -p "用三句话说明 order-lab 的订单状态流转"

# 通过管道传入数据
mvn -q test 2>&1 | tail -50 | claude -p "解释这些测试失败的原因，不要修改代码"
```

脚本里需要关注几个参数：

| 参数 | 作用 |
| --- | --- |
| `--output-format json` | 输出一个 JSON 对象，`result` 字段是回答，还有 `total_cost_usd` 等用量信息 |
| `--json-schema '<schema>'` | 要求输出符合指定的 JSON Schema，结果在 `structured_output` 字段里 |
| `--allowedTools "Read,Grep,Glob"` | 这些工具无需确认即可使用 |
| `--permission-mode dontAsk` | 没有被预先允许的操作一律拒绝，而不是等待确认（脚本里没有人能确认） |
| `--max-turns 10` | 限制 agent 循环的轮数，到达上限时报错退出 |
| `--max-budget-usd 1.00` | 限制花费，达到上限时停止 |
| `--bare` | 跳过 hooks、skills、MCP、CLAUDE.md 等的自动加载，启动更快，行为更可预测 |

这些参数你在第二部分都见过原型：`--allowedTools` 和 `dontAsk` 是第 12 课的权限规则，`--max-turns` 是第 8 课的步数上限，`--json-schema` 是第 7 课提到的结构化输出。

一个例子：在推送代码之前，让 Claude 用结构化的格式检查一遍改动。

```sh
git diff main...HEAD | claude -p \
  "审查标准输入中的 diff，只报告确定存在的问题，不要报告风格偏好。" \
  --permission-mode dontAsk --allowedTools "Read,Grep,Glob" \
  --max-turns 10 --output-format json \
  --json-schema '{
    "type": "object",
    "properties": {
      "findings": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "file":     { "type": "string" },
            "severity": { "type": "string", "enum": ["high", "medium", "low"] },
            "issue":    { "type": "string" }
          },
          "required": ["file", "severity", "issue"]
        }
      }
    },
    "required": ["findings"]
  }' \
| jq '{findings: .structured_output.findings, cost: .total_cost_usd}'
```

（如果你的主分支叫 `master`，把 `main` 换掉。）结构化的输出可以继续交给脚本处理，比如有 `high` 级别的问题就让推送失败。

另一种常见用法是**批量处理**：对一批文件逐个调用 `claude -p`。

```sh
for f in src/main/java/com/example/order/*.java; do
  echo "== $f"
  claude -p "检查 $f 的公共方法是否都有单元测试覆盖，列出缺失的测试点。不要修改文件。" \
    --permission-mode dontAsk --allowedTools "Read,Grep,Glob" --max-turns 8
done
```

每次调用都是一个独立的会话，互不影响上下文。官方建议先在两三个文件上试，调好提示词再全量运行。

## 放进 CI：GitHub Actions

Anthropic 提供了一个官方的 GitHub Action：[anthropics/claude-code-action](https://github.com/anthropics/claude-code-action)。最简单的配置方式是在 Claude Code 里运行：

```text
/install-github-app
```

它会引导你安装 GitHub App、配置密钥，并创建工作流文件的 PR。之后在 issue 或 PR 的评论里写 `@claude`，就能让它分析代码、实现修改、推送提交。

手动配置的话，一个响应 `@claude` 的最小工作流如下（来自官方文档）：

```yaml
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
```

把 agent 放进流水线，要比在自己电脑上更谨慎：

- **它会读到不可信的内容。** issue 正文、PR 描述、评论都可能来自外部贡献者，其中可能藏着 prompt injection（第 12 课）。给工作流最小的权限，不要让它接触生产环境的密钥。
- **限制成本。** 用 `--max-turns`、`--max-budget-usd` 给每次运行设上限，避免一次失控的运行烧掉大量额度。
- **仍然需要人来合并。** 让它开 PR，而不是直接推送到主分支；PR 照样走第 19 课的审查流程。
- **先从只读的任务开始。** 比如自动审查 PR、解释 CI 失败的原因，熟悉之后再让它修改代码。

## 动手

1. **两个 worktree。** 在 order-lab 里开两个终端，分别运行 `claude --worktree coupon` 和 `claude --worktree timeout`。一个实现“订单可以使用一张固定金额的优惠券，抵扣在满减之后”，另一个实现上一课的“30 分钟未支付不能再支付”（这次用 `Clock`）。两边都完成后，回到主目录，用 `git log --oneline --all --graph` 看两个分支，然后依次合并。
2. **写和审分开。** 选一个 worktree，在它完成后，从主目录开一个新会话审查那个分支：“审查 `worktree-coupon` 分支相对于当前分支的改动，只报告问题。”
3. **脚本化审查。** 把“非交互模式”一节的审查命令保存成 `scripts/ai-review.sh`，在一个有改动的分支上运行，看它输出的 JSON 和花费。
4. **（可选）GitHub Actions。** 如果你有一个自己的 GitHub 仓库，运行 `/install-github-app` 配置它，然后在一个 issue 里 `@claude` 提一个小需求，观察它创建的 PR。

## 小结

- 并行节省的是等待时间，你的注意力仍然是瓶颈。适合并行的是彼此独立、边界清晰的任务。
- 用 `claude --worktree` 或 `git worktree` 让每个会话在独立的目录和分支上工作。
- 常见的并行模式：独立功能分开做、写和审分开、测试和实现分开。
- `claude -p` 让 Claude Code 可以放进脚本；用权限参数、轮数和花费上限控制它的行为和成本。
- 放进 CI 时，注意不可信的输入、最小权限和成本上限，并且始终由人来合并。

## 动手练习

1. 完成前三个实验。合并两个 worktree 的分支时，有没有冲突？如果有，是哪些文件？想一想，怎样拆分任务能减少冲突。
2. 改进 `scripts/ai-review.sh`：当结果里有 `high` 级别的问题时，以非零状态码退出。再把它配置成 git 的 `pre-push` hook。
3. 估算一下：如果团队里每个 PR 都自动运行一次 AI 审查，按第 13 课的方法统计一次审查的平均花费，一个月大概要多少钱？这笔钱和一次线上事故的成本相比如何？
