第 8 课的 MiniAgent 主循环只有几十行：调用模型，如果它要调用工具就执行工具、把结果发回去，否则结束。这一课看一个真实的开源 agent 是怎么做同一件事的。你会发现骨架完全一样，多出来的都是工程问题：持久化、并发、中断、重试、流式输出。

读源码最怕的是迷失在细节里。这一课的方法是**追一条请求**：从你在命令行输入一句话开始，一路追到它变成发给模型的 HTTP 请求，再追回来。为了看清每一步发生了什么，我们用一个模拟的模型服务端运行 opencode，不需要 API key，就能看到 opencode 发出的每一个请求。

本课和后面几课引用的代码，路径都相对于 opencode 仓库的根目录，版本是上一课 checkout 的 `108b988`。

## 仓库的结构

opencode 是一个 monorepo，`packages/` 下有几十个包。读主流程只需要关注几个：

| 包 | 内容 |
| --- | --- |
| `packages/opencode` | 命令行入口、HTTP 服务端、会话与主循环、工具、权限、配置。发布到 npm 的 `opencode-ai` 就是这个包 |
| `packages/tui` | 终端界面，它是服务端的一个客户端 |
| `packages/sdk` | 根据服务端的 OpenAPI 生成的 JavaScript SDK |
| `packages/plugin` | 插件接口（第 27 课） |
| `packages/schema`、`packages/core` | 共享的数据结构、数据库表和工具函数 |
| `packages/web` | 官网和文档，`src/content/docs/` 下是全部文档 |

有一点要特别注意：`packages/core` 里也有 `session/`、`tool/` 等目录，那是一套**正在重写中的新架构**（代码里称为 V2）。仓库根目录的 `specs/v2/session.md` 写着它要满足哪些条件才能替换现在的实现。目前命令行和终端界面走的都是 `packages/opencode/src/session/` 下的旧实现（V1），这一课和后面几课读的都是这一套。`core` 里只有数据库表、提示词片段等少数东西被 V1 直接复用。

读一个正在演进的开源项目，常会遇到这种新旧并存的情况。判断哪套代码是“活的”，最可靠的办法就是我们现在做的：从入口追调用链。

## 入口：客户端与服务端

入口是 `packages/opencode/src/index.ts`，用 yargs 注册了所有子命令。默认命令（直接运行 `opencode`）是 `cli/cmd/tui.ts` 里的 `TuiThreadCommand`，`opencode run` 是 `cli/cmd/run.ts` 里的 `RunCommand`。

opencode 的一个核心设计是**客户端与服务端分离**。会话、主循环、工具执行都在服务端；终端界面只是一个客户端，通过 HTTP 接口发送消息、订阅事件：

- 直接运行 `opencode` 时，服务端运行在一个 Bun Worker 线程里，界面和它之间用一个“假的” fetch 通信：请求地址是 `http://opencode.internal`，实际通过线程间的 RPC 转发（`cli/cmd/tui.ts` 第 210 到 249 行）。加上 `--port` 参数，才会真的监听一个端口。
- `opencode run` 也一样，它在同一个进程里直接调用服务端的处理函数（`cli/cmd/run.ts` 第 948 到 960 行）。加上 `--attach <url>` 就改成连接一个已经在运行的服务端。
- `opencode serve` 只启动服务端，不启动界面。网页版、桌面版、IDE 插件和 SDK 都通过同一套 HTTP 接口工作。

无论哪个客户端，发送消息都是 `POST /session/{sessionID}/message`。在服务端，它由 `server/routes/instance/httpapi/handlers/session.ts` 交给 `SessionPrompt.prompt`，这个函数在 `session/prompt.ts` 里：先把用户消息存进数据库，然后调用 `loop`，`loop` 再调用真正的主循环 `runLoop`。`loop` 还保证同一个会话同时只有一个循环在运行，后来的调用会加入正在运行的那一个。

这种结构和 MiniAgent 差别很大。MiniAgent 是一个单进程的命令行程序，对话历史就在一个 `List` 里。opencode 的会话是服务端的资源，存在 SQLite 里，可以有多个客户端同时观看；界面上看到的每一个字，都是服务端推送的事件。

## 主循环：runLoop

`session/prompt.ts` 第 1081 到 1340 行的 `runLoop` 就是主循环。它有 260 行，去掉日志、错误处理和特殊情况，骨架是这样的（节选，省略处用注释标出）：

```typescript
while (true) {
  // 1. 每一轮都从数据库重新读取历史（已经压缩掉的部分会被过滤）
  let msgs = yield* MessageV2.filterCompactedEffect(sessionID)
  const { user: lastUser, assistant: lastAssistant, finished: lastFinished, tasks } = MessageV2.latest(msgs)

  // 2. 结束条件：最后一条助手消息正常结束，不是因为要调用工具，并且是对最后一条用户消息的回复
  const hasToolCalls = lastAssistantMsg?.parts.some((part) => part.type === "tool" && /* …… */) ?? false
  if (
    lastAssistant?.finish &&
    !["tool-calls", "unknown"].includes(lastAssistant.finish) &&
    !hasToolCalls &&
    lastAssistant.parentID === lastUser.id
  ) {
    break
  }

  step++
  if (step === 1) yield* title({ /* …… */ }).pipe(Effect.ignore, Effect.forkIn(scope))  // 后台生成标题

  // 3. 处理排队的任务：子任务、压缩（第 26、27 课）
  const task = tasks.pop()
  if (task?.type === "subtask") { yield* handleSubtask({ /* …… */ }); continue }
  if (task?.type === "compaction") { /* 执行压缩 */ continue }
  if (lastFinished && /* …… */ (yield* compaction.isOverflow({ tokens: lastFinished.tokens, model }))) {
    yield* compaction.create({ /* …… */ auto: true })
    continue
  }

  // 4. 步数上限和提醒
  const maxSteps = agent.steps ?? Infinity
  const isLastStep = step >= maxSteps
  msgs = yield* SessionReminders.apply({ messages: msgs, agent, session })

  // 5. 新建一条助手消息，准备工具、系统提示和消息，交给 processor 执行这一步
  const tools = yield* SessionTools.resolve({ agent, session, model, /* …… */ })
  const [skills, env, instructions, mcpInstructions, modelMsgs] = yield* Effect.all([ /* …… */ ])
  const result = yield* handle.process({
    system, tools, model,
    messages: [...modelMsgs, ...(isLastStep ? [{ role: "assistant", content: MAX_STEPS_PROMPT }] : [])],
    /* …… */
  })

  // 6. 根据这一步的结果决定继续、停止还是压缩
  if (result === "stop") break
  if (result === "compact") yield* compaction.create({ /* …… */ })
  continue
}
```

和第 8 课的 MiniAgent 对照着读，几个设计差异值得注意。

**历史每一轮都从数据库重新读。** MiniAgent 在内存里维护一个消息列表，每一步往里追加。opencode 每一轮都从数据库读出全部消息，再转换成模型需要的格式。这样做慢一些，但带来了几个好处：进程崩溃后会话可以恢复；多个客户端看到的是同一份数据；压缩、撤销这类操作只需要修改数据库里的标记，下一轮读出来的就是修改后的历史。

**结束条件检查的是“上一步的结果”，而且检查得很谨慎。** MiniAgent 看 `stop_reason` 是否等于 `tool_use`。opencode 看的是上一条助手消息的 `finish`（由 AI SDK 把各家模型的停止原因统一成 `stop`、`tool-calls`、`length` 等），另外还检查消息里有没有工具调用。源码注释解释了原因：有的模型提供商在调用了工具的情况下仍然返回 `stop`。这种防御性的检查，是一个支持几十家模型提供商的项目才会积累下来的经验。

**步数上限默认是无限。** MiniAgent 硬编码了 30 步。opencode 的上限是每个 agent 的 `steps` 配置，默认不限。到达上限时也不是直接中止，而是在消息末尾加一段 `MAX_STEPS_PROMPT`，告诉模型“已经到达最大步数，只能用文字回复”，让它体面地总结当前进度。

**一轮循环可能不调用主模型。** 排队的子任务、需要执行的压缩，都在循环里作为一种“任务”处理，然后 `continue` 进入下一轮。所以“一轮”不等于“一次模型调用”，这让主循环成了整个会话的调度中心。

## 一步：processor 与流式事件

每一步的模型调用交给 `session/processor.ts` 的 `process` 函数（第 641 到 697 行）。它的核心是把模型的流式输出变成一个事件流，逐个处理：

```typescript
const stream = llm.stream(streamInput)

yield* stream.pipe(
  Stream.tap((event) => handleEvent(event)),
  Stream.takeUntil(() => ctx.needsCompaction),
  Stream.runDrain,
)
```

外面再包上一层 `pipe`：

```typescript
.pipe(
  Effect.onInterrupt(() => /* 用户中断：把当前消息标记为已中止 */),
  Effect.catchCauseIf(/* …… */),
  Effect.retry(SessionRetry.policy({ /* …… */ })),   // 按策略重试
  Effect.catch(halt),                                 // 重试用完后的错误处理
  Effect.ensuring(cleanup()),                         // 收尾：把没完成的工具调用标记为中止
)
```

最后根据结果返回 `"compact"`、`"stop"` 或 `"continue"`，交回主循环。

`handleEvent`（第 278 到 551 行）是一个对事件类型的大 `switch`，正是上一课讲的可辨识联合：

| 事件 | 处理 |
| --- | --- |
| `text-start` / `text-delta` / `text-end` | 创建一个文本 part，逐字追加，结束时保存 |
| `reasoning-start` / `-delta` / `-end` | 同上，处理模型的思考内容 |
| `tool-input-start` / `-delta` / `-end` | 模型开始生成工具参数，创建一个状态为 `pending` 的工具 part |
| `tool-call` | 参数生成完毕，状态改为 `running`；在这里做死循环检测（第 25 课） |
| `tool-result` / `tool-error` | 工具执行完毕，状态改为 `completed` 或 `error`，保存输出 |
| `step-start` | 记录一个文件快照，用于撤销（第 26 课） |
| `step-finish` | 记录停止原因、token 用量和费用；检查是否超出上下文，需要时标记压缩 |

每处理一个事件，都会更新数据库并发布一个事件，界面就是靠订阅这些事件实时显示文字和工具调用的。第 8 课的 MiniAgent 用的是非流式调用，一次拿到完整回复；第 6 课演示过流式输出。opencode 把两者结合了：一边流式显示，一边把结构化的结果存下来。

### 重试策略

`session/retry.ts` 定义了重试策略：最多重试 5 次，初始间隔 2 秒，每次翻倍，加 25% 的随机抖动；服务端返回了 `retry-after` 头时按它的要求等待。哪些错误值得重试，除了看 HTTP 状态码，还用一组正则表达式匹配错误信息，比如 `overloaded`、`rate limit`、`ECONNRESET`。上下文超长的错误不重试，而是转去压缩。

opencode 把 AI SDK 自带的重试关掉了（`maxRetries: 0`），自己在外层统一重试，这样重试状态可以显示在界面上（“第 2 次重试，10 秒后”）。第 6 课讲 Java SDK 时说过类似的考虑：重试要放在一个地方做，否则层层重试，等待时间会成倍放大。

### 中断

用户按下 Esc，客户端调用 `POST /session/{id}/abort`。服务端最终会中断（interrupt）正在运行的那个 Effect fiber。Effect 的中断会一层层传播：模型请求通过 `AbortSignal` 被取消，`onInterrupt` 把消息标记为已中止，`cleanup` 等待 250 毫秒让正在执行的工具收尾，仍未完成的标记为“Tool execution aborted”。

下一轮读取历史时，这些被中断的工具调用会被转成内容为 `[Tool execution was interrupted]` 的工具结果。这一点很重要：Anthropic 的 API 要求每个 `tool_use` 都有对应的 `tool_result`（第 7 课），如果中断后留下一个没有结果的 `tool_use`，下一次请求就会报错。

## 工具在哪里执行

读到这里你可能会问：主循环里没有看到“执行工具”的代码，工具是在哪里执行的？

答案在 `session/llm.ts`。opencode 调用模型用的是 Vercel AI SDK 的 `streamText` 函数，工具以 AI SDK 的格式传进去，每个工具都带着一个 `execute` 函数。`streamText` 在一次调用里做了两件事：请求模型，然后执行模型要求的所有工具，把 `tool-result` 事件也放进同一个事件流。opencode 没有设置 `stopWhen` 参数，AI SDK 的默认值是只走一步，所以 `streamText` 执行完工具就结束，返回的停止原因是 `tool-calls`。主循环看到这个停止原因，进入下一轮，从数据库读出包含工具结果的历史，再次调用模型。

也就是说，MiniAgent 一次循环里“调用模型、执行工具”这两件事，在 opencode 里被分到了 AI SDK 和主循环两个地方。工具的 `execute` 函数由 `session/tools.ts` 包装（第 99 到 136 行）：

```typescript
tools[item.id] = tool({
  description: item.description,
  inputSchema: jsonSchema(schema),
  execute(args, options) {
    return run.promise(
      Effect.gen(function* () {
        const ctx = context(args, options)
        yield* plugin.trigger("tool.execute.before", { tool: item.id, /* …… */ }, { args })
        const result = yield* item.execute(args, ctx)
        /* …… */
        yield* plugin.trigger("tool.execute.after", { tool: item.id, /* …… */ }, output)
        return output
      }),
    )
  },
})
```

工具执行前后各触发一次插件钩子，相当于 Claude Code 的 PreToolUse 和 PostToolUse hooks（第 13 课），第 27 课会细讲。`run.promise(...)` 就是上一课说的从 Effect 回到 Promise 的边界，因为 AI SDK 是基于 Promise 的。

同一次回复里有多个工具调用时，AI SDK 会并发执行它们。MiniAgent 是按顺序一个一个执行的。

## 消息的存储：message 和 part

opencode 把会话存在 SQLite 里，主要有三张表：`session`、`message`、`part`。一条消息由多个 part 组成，part 的类型就是上面那些事件处理的结果。用实验包里的 `db.sh` 看看刚才那次会话存了什么：

```sh
./db.sh
```

```text
role       type         detail
user       text         "读一下 hello.txt"
assistant  step-start
assistant  text         我先读一下文件。
assistant  tool         read
assistant  step-finish  tool-calls
assistant  step-start
assistant  text         文件里是一句问候。
assistant  step-finish  stop
```

可以看到两条助手消息，每条对应一步（一次模型调用），各自以 `step-start` 开头、`step-finish` 结尾。第一步的停止原因是 `tool-calls`，主循环因此继续；第二步是 `stop`，主循环结束。工具的输入和输出都存在 `tool` 这个 part 里，下一轮会被转换成 API 需要的 `tool_use` 和 `tool_result`。

完整的 part 类型定义在 `packages/schema/src/v1/session.ts`，除了上面这些，还有 `reasoning`（思考内容）、`file`（附件）、`patch`（这一步改了哪些文件）、`subtask`（排队的子任务）、`compaction`（压缩标记）、`retry`（重试记录）等。

## 三方对照

| | MiniAgent（第 8 课） | opencode | Claude Code |
| --- | --- | --- | --- |
| 进程结构 | 单进程命令行程序 | 服务端加多种客户端，通过 HTTP 和事件流通信 | 单个命令行程序，也提供 SDK 和非交互模式 |
| 对话历史 | 内存中的 `List` | SQLite，每轮重新读取 | 本地 JSONL 文件（第 13 课） |
| 循环结束条件 | `stop_reason != tool_use` | 停止原因不是 `tool-calls`，且没有未处理的工具调用 | 未公开源码，行为相同 |
| 步数上限 | 硬编码 30 步 | 每个 agent 可配置，默认无限；到达上限时让模型用文字总结 | 交互模式无固定上限，`-p` 模式可用 `--max-turns` |
| 模型调用 | 非流式 | 流式，经过 AI SDK 统一多家模型 | 流式 |
| 工具执行 | 主循环里顺序执行 | AI SDK 在一步内并发执行 | 一次回复里的多个工具调用可以并发执行 |
| 重试 | SDK 自带 | 自己实现，最多 5 次，状态显示在界面上 | 自动重试 |
| 中断 | Ctrl+C 结束进程 | 中断 Effect fiber，补齐被中断工具的结果 | Esc 中断，可以继续对话 |

## 动手

1. **读结束条件。** 打开 `packages/opencode/src/session/prompt.ts`，找到 `runLoop`。对照本课的骨架，找出被省略的部分各在处理什么情况。
2. **看事件处理。** 打开 `session/processor.ts`，找到 `case "step-finish"`，看看它记录了哪些用量数据，在什么条件下设置 `needsCompaction`。
3. **改剧本。** 复制 `scenarios/01-read.json` 为 `scenarios/my-test.json`，让模型在第一次回复里同时调用两个 read 工具（读 `hello.txt` 和 `AGENTS.md`），运行 `./run.sh my-test "读两个文件"`，用 `show.py` 看第二次请求里的 `tool_result` 有几个，用 `db.sh` 看数据库里存了几个 tool part。
4. **看标题请求。** 运行 `python3 show.py logs/01-read.jsonl --system`，读请求 1 的完整系统提示。它让模型生成什么样的标题？为什么这类辅助调用适合用一个更小、更便宜的模型？

## 小结

- opencode 是服务端加客户端的结构，终端界面、`opencode run`、网页、SDK 都通过同一套 HTTP 接口驱动服务端里的会话。
- `packages/core` 里是正在重写的新架构，当前命令行走的是 `packages/opencode/src/session/` 下的实现。判断哪套代码在用，要从入口追调用链。
- 主循环 `runLoop` 每一轮从数据库重新读历史，结束条件是上一步没有调用工具且正常结束；子任务和压缩也作为循环里的任务处理。
- 每一步由 processor 处理模型的流式事件，按事件类型更新数据库并推送给界面；外层统一处理中断、重试和收尾。
- 工具由 AI SDK 的 `streamText` 在一步内执行，执行前后会触发插件钩子；主循环负责在工具执行后发起下一次调用。
- 骨架和第 8 课的手写版完全一样，多出来的是持久化、多客户端、流式、重试和中断这些工程问题。
