到目前为止，MiniAgent 处理的都是一句话能说清、十几步能做完的任务。换成“把订单模块里所有用 double 表示金额的地方改成 BigDecimal”，问题就来了：

- 它可能读了三个文件就开始改，改到一半才发现还有别的地方依赖这些字段；
- 任务做到第 40 步时，最初的要求已经埋在几万 token 的工具输出下面，它开始偏离目标（第 5 课讲过，上下文中间的内容最容易被忽略）；
- 为了找出“所有”的地方，它读了几十个文件，上下文很快被填满，之后的每一轮都要为这些内容付费。

这一课给 MiniAgent 加上三个机制，分别解决这三个问题：

| 机制 | 解决什么问题 | Claude Code 中的对应 |
| --- | --- | --- |
| 计划模式 `/plan` | 没想清楚就动手 | Plan Mode |
| 待办清单 `todo_write` | 长任务中丢失方向 | 终端里显示的待办清单 |
| 调研子 agent `task` | 大量探索占满上下文 | 子 agent（subagents） |

完整代码：[MiniAgent.java（第 11 课版本）](/courses/ai-dev/code/11/MiniAgent.java)，在第 10 课版本的基础上修改。

## 为什么“先计划”有用

第 2 课讲过，模型一个 token 一个 token 地生成，每一步都基于前面的全部内容。这意味着：**先写下的内容会约束后面的生成。** 如果模型先写出了“第一步改实体类，第二步改 DTO 和转换器，第三步改计算逻辑，第四步跑测试”，后面的工具调用就会沿着这个计划走。

计划还有一个更重要的作用：**它给了你一个便宜的纠错时机。** 在计划阶段发现“不对，DTO 是对外接口，不能改类型”，只需要说一句话；等 agent 改完二十个文件再发现，就要回滚重来。这和写代码前先做技术方案评审是同一个道理。

## 计划模式

实现计划模式最直接的想法是：进入计划模式时，只把只读工具发给模型。但第 10 课讲过，工具定义在请求的最前面，一改动整个缓存都会失效。所以这一版的做法是**工具列表不变，在执行时拦截**：

```java
if (task.equals("/plan")) {
    planMode = !planMode;
    System.out.println(planMode ? "（已进入计划模式：只调研，不修改）" : "（已退出计划模式）");
    continue;
}
if (planMode) {
    // 工具列表不变（不破坏缓存），用一段提醒告诉模型当前的模式，由 execute 负责拦截
    task = "<system-reminder>当前为计划模式：只能使用只读工具调研代码，不能修改文件或执行命令。"
            + "调研完成后给出分步实施计划，等待用户确认。</system-reminder>\n" + task;
}
conversation.addUserMessage(task);
runAgentLoop(conversation, MAIN);
```

模型怎么知道自己处于计划模式？靠用户消息前面附加的一段提醒。即便它没有遵守提醒、仍然请求写文件，`execute` 也会拒绝，并在错误信息里告诉它该做什么：

```java
if (planMode && !tool.readOnly()) {
    return error(call, "当前为计划模式，不能修改文件或执行命令。请先完成调研并给出计划，等用户确认后再执行。");
}
```

这是一个值得记住的模式：**用提示词引导行为，用代码保证底线。** 提示词让模型大多数时候做对，代码拦截确保它做错时也不会造成影响。

## 待办清单：把目标放在最近的位置

`todo_write` 是一个“没有副作用”的工具：它不读写文件，只是让模型把计划写成一份清单，程序把清单打印出来，再原样返回给模型。

```java
static String todoWrite(ToolUseBlock call) {
    List<?> items = (List<?>) input(call).get("todos");
    List<Todo> updated = new ArrayList<>();
    for (Object item : items) {
        Map<?, ?> todo = (Map<?, ?>) item;
        updated.add(new Todo(String.valueOf(todo.get("content")), String.valueOf(todo.get("status"))));
    }
    todos = updated;
    StringBuilder out = new StringBuilder();
    for (Todo todo : todos) {
        String mark = switch (todo.status()) {
            case "completed" -> "✓";
            case "in_progress" -> "▶";
            default -> "○";
        };
        out.append(mark).append(' ').append(todo.content()).append('\n');
    }
    System.out.print(out.toString().indent(4));
    return "待办清单已更新：\n" + out;
}
```

它的参数 schema 是一个对象数组，每一项有内容和状态：

```java
register(tool("todo_write",
        "创建或更新本次任务的待办清单。每次调用都传入完整的清单（会整体替换旧清单）。",
        true,
        Map.of("todos", Map.of("type", "array", "items", Map.of(
                "type", "object",
                "properties", Map.of(
                        "content", Map.of("type", "string"),
                        "status", Map.of("type", "string",
                                "enum", List.of("pending", "in_progress", "completed"))),
                "required", List.of("content", "status")))),
        List.of("todos"), MiniAgent::todoWrite));
```

一个什么都不做的工具为什么有用？有两个原因：

- **对模型来说，它把目标和进度不断“重新写到”上下文的末尾。** 每次更新清单，完整的计划就会作为最新的内容出现在上下文里，而不是埋在几十轮之前。第 5 课讲过，上下文末尾的内容最不容易被忽略。
- **对你来说，它让 agent 的进度可见。** 你不用读每一步工具调用，看清单就知道它做到哪了，有没有偏离。

系统提示里加了使用规则：三步以上的任务先列清单；同一时间只有一项进行中；每完成一项立即更新。这些规则来自实践：如果不要求“立即更新”，模型常常会做完所有事才一次性把清单全部打勾，清单就失去了意义。

## 子 agent：用独立的上下文做调研

“找出所有用 double 表示金额的地方”需要读很多文件，但真正有用的只是最后那张列表。如果让主 agent 自己做，读过的几十个文件都会留在它的上下文里。

子 agent 的思路是：**开一个新的对话去做调研，只把结论带回来。**

```java
static final String EXPLORER_PROMPT = """

static String runSubAgent(ToolUseBlock call) {
    System.out.println("    ┌ 子 agent：" + arg(call, "description"));
    MessageCreateParams.Builder conversation = MessageCreateParams.builder()
            .model("claude-opus-5-5")
            .maxTokens(16_000L)
            .system(EXPLORER_PROMPT)
            .cacheControl(CacheControlEphemeral.builder().build())
            .addUserMessage(arg(call, "prompt"));
    EXPLORER.tools().values().forEach(t -> conversation.addTool(t.definition()));
    String report = runAgentLoop(conversation, EXPLORER);
    System.out.println("    └ 子 agent 完成，报告 " + report.length() + " 个字符");
    return report;
}
```

对主 agent 来说，`task` 只是一个普通的工具：传入一段说明，拿回一份报告。子 agent 在里面做了 20 步还是 2 步，读了多少文件，主 agent 都看不到，它的上下文只增加了一份报告的长度。

为了让主 agent 和子 agent 共用同一个循环，这一版把它们的区别提取成了一个配置：

```java
record AgentConfig(String indent, Map<String, AgentTool> tools, int maxSteps, boolean compaction) {}

static final AgentConfig MAIN = new AgentConfig("", TOOLS, MAX_STEPS, true);
static final AgentConfig EXPLORER = new AgentConfig("    │ ", subset("list_files", "grep", "read_file"), 30, false);
```

子 agent 只拿到三个只读工具，不压缩上下文（它的任务本来就短），步数上限也更低。`runAgentLoop` 改为返回最后一次回复的文字，这就是子 agent 的报告。

子 agent 的代价和限制也要清楚：

- **总 token 数通常更多，不是更少。** 子 agent 有自己的系统提示和工具定义，探索时读的文件一个也没省。省下的是**主 agent 的**上下文：主对话保持干净，后续每一轮都更便宜、更聚焦。
- **子 agent 看不到主对话。** 它只知道 `prompt` 里写的内容。主 agent 写的说明不完整，它就会调研错方向。所以工具描述里特意强调“prompt 必须写清楚”。
- **适合调研，不适合修改。** 多个 agent 同时改同一批文件，很容易互相覆盖。这一版的子 agent 是只读的，第 20 课讲并行工作时会再讨论怎么安全地让多个 agent 同时写代码。

## 动手

准备一个稍大一点的练习项目。如果手边有自己的 Spring Boot 项目，直接用它（先提交或备份当前改动）；也可以用下面的命令在 `~/agent-lab` 里生成几个类：

```sh
mkdir -p ~/agent-lab/src/shop && cd ~/agent-lab
for name in Order Refund Coupon Invoice; do
cat > src/shop/$name.java <<JAVA
package shop;

public class $name {
    private double amount;
    private String currency = "CNY";

    public double getAmount() { return amount; }
    public void setAmount(double amount) { this.amount = amount; }

    public double withTax(double rate) { return amount * (1 + rate); }
}
JAVA
done
```

**1. 计划模式。** 启动 agent，先进入计划模式：

```text
> /plan
> 把 src/shop 下所有用 double 表示金额的地方改成 BigDecimal，保留两位小数，四舍五入。先调研，再给出计划。
```

观察它的行为：它很可能会调用 `task` 派出子 agent 调研，或者自己用 `grep` 搜索；然后用 `todo_write` 列出计划，最后停下来等你确认。如果它试图修改文件，你会看到计划模式拦截的错误。

**2. 修改计划，再执行。** 对计划提一个修改意见，比如：

```text
> 计划里再加一步：在每个类里写一个简单的 main 方法，检查 withTax 的结果。
```

它会在计划模式下修订计划。确认没问题后，退出计划模式，让它开始执行：

```text
> /plan
> 按计划执行。
```

执行过程中留意清单的更新：每完成一项，它是否立即打勾？

**3. 观察子 agent 的上下文隔离。** 对比主 agent 和子 agent 各自打印的“上下文”数字。子 agent 读过的文件，有没有让主 agent 的上下文变大？

## 小结

- 先写下的计划会约束后续生成，也给了你一个低成本的纠错时机。
- 计划模式的实现：工具列表不变以保护缓存，用提醒引导模型，用代码拦截保证底线。
- 待办清单把目标和进度不断写到上下文末尾，让长任务不跑偏，也让进度可见。
- 子 agent 在独立的上下文里调研，只把报告带回主对话；总 token 不一定更少，但主对话更干净。
- 子 agent 看不到主对话，给它的说明必须完整。

## 动手练习

1. 完成“动手”中的三个实验。第 3 步中，记下子 agent 一共消耗的 token，以及主 agent 的上下文因为这次调研增加了多少。
2. 让主 agent 在一次回复中同时派出两个子 agent（比如分别调研 `Order` 和 `Refund` 的用法）。现在它们是依次执行的。用 `ExecutorService` 改成并行执行，注意子 agent 打印的输出会交错在一起，想办法让输出可读。
3. 写一个任务，让模型有可能把调研交给子 agent，但故意在任务里提到一个只有主对话才知道的约束（比如前面对话里说过“Coupon 类已经废弃，不用管”）。观察子 agent 的报告是否把 Coupon 也算了进去。再想一想：主 agent 应该怎样写 `prompt` 才能避免这个问题？
