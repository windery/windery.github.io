第三部分把方法拆成了一课一课：写需求、计划、反馈闭环、会话管理、项目配置、审查。这一课把它们串起来，在一个更接近真实工作的 Spring Boot 项目里，完整地交付一个功能。

要做的功能是**限量优惠券**：运营创建一批满减券，用户先到先得地领取，下单时使用，取消订单时退回。它不大，但有几处容易出错的地方：金额计算、过期时间、“一人一张”，以及最关键的**高并发下不能超发**。这正是 agent 写出来“看起来没问题，测试也通过”，上线后才出事的那类功能。

## 准备：shop-api 项目

练习项目 shop-api 是一个最小的电商订单服务：Spring Boot 4.1、Java 21、Spring Data JPA、H2 内存数据库、Flyway 管理表结构。已有的功能是下单、查询、支付和取消。你需要 JDK 21 和 Maven。

```sh
cd ~

unzip shop-api.zip && cd shop-api
git init -q && git add -A && git commit -qm "initial"

```

第一次运行会下载依赖，之后应该看到 10 个测试全部通过。也可以先[在浏览器里看一下 README](/courses/ai-dev/code/shop-api/README.md)。

启动服务，用 curl 走一遍现有的流程：

```sh
mvn spring-boot:run
```

另开一个终端：

## 第 1 步：配置项目

在 shop-api 目录里启动 `claude`，先让它生成 CLAUDE.md：

```text
/init
```

`/init` 会读项目，生成一份 CLAUDE.md 草稿。按第 18 课的原则审一遍：**只留模型自己猜不到的东西**。项目结构、用了哪些框架，它读代码就知道；你们团队的约定、容易踩的坑，它猜不到。

对这个项目，最值得写进去的是这几条：

```markdown
## 约定
- 金额用 `BigDecimal`，比较用 `compareTo`，测试用 `isEqualByComparingTo`。
- 当前时间一律来自注入的 `Clock`，不要调用 `Instant.now()`。测试用 `TestClockConfig` 的固定时钟。
- 业务规则失败抛 `BusinessException`（409），找不到资源抛 `NotFoundException`（404），参数错误用 Bean Validation 或 `IllegalArgumentException`（400）。
- 改表只能新增 `src/main/resources/db/migration/V<n>__<说明>.sql`，不要修改已有脚本。

## 测试
- 服务层测试可以加 `@Transactional` 自动回滚。
- 接口测试和并发测试不要加 `@Transactional`：前者要暴露懒加载问题，后者每个线程要独立提交。
- 有并发要求的功能，必须有多线程同时执行的测试。

## 不要做
- 不要修改已有测试的期望值来让测试通过；如果你认为测试本身错了，先停下来说明理由。
```

“接口测试不要加 `@Transactional`”这一条有来历。准备这个练习项目时，接口测试最初加了 `@Transactional`，全部通过；用 curl 实际调用支付接口，却返回了 500，日志里是 `LazyInitializationException`。原因是项目关闭了 open-in-view，接口在事务结束后才把订单转成 JSON，这时再去加载订单明细已经没有数据库会话了。测试加了 `@Transactional`，整个请求都在测试的事务里，问题被掩盖了。去掉注解后，测试立刻复现了这个错误。

这种“只有在这个项目里才知道”的经验，正是 CLAUDE.md 该写的内容。完整版本在参考实现里。

然后把第 16 课的 `verify.sh`（Stop hook）、第 18 课的 `compile.sh`（PostToolUse hook）和 `settings.json` 复制过来。这两个脚本只依赖 `mvn`、`git` 和 `jq`，不用改。最后提交：

```sh
git add CLAUDE.md .claude/settings.json .claude/hooks
git commit -m "Add Claude Code project config"
```

在 Claude Code 里运行 `/hooks`，确认两个 hook 都已注册。

## 第 2 步：需求

用第 14 课的方法，只给一句话，让它采访你：

```text
我要做一个限量优惠券功能：运营创建满减券，数量有限、先到先得，用户领取后下单时使用。
请先用 AskUserQuestion 工具详细地问我，覆盖业务规则、边界情况、并发、和现有订单代码的关系。
不要问显而易见的问题，重点问我可能没想到的难点。问完之后，把完整的 spec 写到 SPEC.md。
```

它的问题取决于它读到了什么代码，每次都不一样。下面这些问题如果它没问到，你要主动补进 spec 里：

- **超发**：很多人同时领最后几张券时怎么办？验收标准里要写明“并发下恰好发出 N 张”。
- **一人一张**：同一个用户连点两次“领取”，会不会领到两张？
- **门槛的边界**：总价恰好等于门槛时能不能用？
- **过期**：领了没用就过期了怎么办？下单时过期和领取时过期分别怎么处理？
- **退券**：订单取消后券还回不回来？退回时券已经过期了呢？
- **范围**：一单能不能用多张券？支付后退款要不要退券？明确写进“不做”。

参考实现里的 SPEC.md 是这样的（节选）：

```markdown
## 规则

1. **创建券**：名称、使用门槛 `threshold`、减免金额 `discount`、发放总量 `totalCount`、截止时间 `validUntil`。
   要求 `threshold > discount > 0`，`totalCount >= 1`，`validUntil` 晚于当前时间，否则返回 400。
2. **领券**：用户按券 id 领取。
   - 已过截止时间：409。
   - 已经领完：409。高并发下也不能超发。
   - 同一个用户对同一张券只能领一次：409。
3. **我的券**：按用户查询领到的券，显示券的信息和状态（AVAILABLE / USED）。
4. **下单用券**：下单时可以带上一张领到的券 `userCouponId`。
   - 券必须属于下单用户、状态是 AVAILABLE、下单时没有过期，商品总价不低于门槛，否则 409。
   - 应付金额 = 商品总价 - 减免金额。订单上记录用了哪张券、减了多少。
   - 下单后券变为 USED。
5. **取消订单**：订单用过的券退回为 AVAILABLE。退回后如果已经过期，就不能再用了（第 4 条会拦住）。

## 不做

- 一张订单用多张券。
- 支付后退款退券。
- 管理接口的鉴权。

## 验收

- `mvn test` 全部通过，以上每条规则都有对应的测试。
- 50 个用户同时抢一张总量为 10 的券，最终恰好发出 10 张。
- 同一个用户并发领同一张券 10 次，最终只有 1 张。
```

注意最后两条验收标准。它们把“不能超发”从一句口号变成了**可以运行的检查**。没有这两条，agent 很可能写一个单线程的“领完之后再领会失败”的测试，然后宣布完成。

SPEC.md 写好后提交它，然后 `/clear`，在干净的上下文里开始下一步。

## 第 3 步：计划

按 `Shift+Tab` 切到计划模式，或者用 `claude --permission-mode plan` 启动：

```text
读 @SPEC.md，制定实现计划。计划里要写明：
1. 表结构的变化（新增哪个 Flyway 脚本）；
2. 防止超发和重复领取的方案，比较至少两种做法的优缺点，说明选哪种、为什么；
3. 事务边界：哪些操作必须在同一个事务里；
4. 要改哪些已有的类，新增哪些类；
5. 测试清单：每条规则对应哪个测试，并发测试怎么写。
先不要写代码。
```

第 2 条是这一步的重点。注意提问的方式是“比较至少两种做法”，而不是“用乐观锁实现可以吗”。后一种问法，按第 3 课讲的“顺着你说”，它多半会同意你。

防超发的常见做法有这几种，你要能判断它选的是否合理：

| 做法 | 说明 | 问题 |
| --- | --- | --- |
| `synchronized` 或 JVM 内的锁 | 在 Java 代码里加锁 | 只在单个实例内有效，服务部署两台就失效 |
| 先查再改 | 读出 `claimedCount`，判断有余量，加一后保存 | 两个请求同时读到相同的值，都认为有余量，**会超发** |
| 乐观锁 `@Version` | 保存时检查版本号，冲突就失败或重试 | 正确；抢券时冲突很多，大量请求要重试 |
| 条件更新 | `update ... set claimed_count = claimed_count + 1 where id = ? and claimed_count < total_count`，看影响行数 | 正确，简单，判断和修改在一条 SQL 里由数据库保证 |
| 悲观锁 `select ... for update` | 先锁住券这一行，再判断和修改 | 正确；事务持锁时间更长 |
| Redis 预扣 | 库存放在 Redis，用原子操作扣减 | 适合极高并发，但要处理 Redis 和数据库的一致性，对这个项目过重 |

“一人一张”也有同样的问题：先查“这个用户领过没有”，再插入记录，两个并发请求可能都查到“没领过”。可靠的做法是在数据库上加**唯一约束** `(coupon_id, customer_id)`，让数据库拒绝第二条记录，代码里再把这个异常转成业务错误。

审计划时，对照第 15 课的清单，再特别看这几处：

- 迁移脚本是**新增**的 `V2__...sql`，没有改 `V1`。
- 防超发的方案是上表中“正确”的几种之一，并且说清了原因。
- “领券”的几步（扣余量、插入记录）在同一个事务里，插入失败时余量也会回滚。
- “下单”和“用券”在同一个事务里，用券失败时订单不会被创建。
- 测试清单里有真正的多线程测试，而且没有加 `@Transactional`。

计划不满意就直接说哪里不对，让它改。满意后按 `Ctrl+G` 可以在编辑器里打开计划做最后的修改。

## 第 4 步：先写测试

批准计划后，先不要让它实现，而是先写测试：

```text
按计划先写测试，覆盖 SPEC.md 的每一条规则和两条并发验收标准。
现在只写测试，不要写实现代码。写完运行 mvn -q test，确认新测试失败（编译失败也算），然后停下来。
```

先写测试的好处在第 16 课讲过：测试是从 spec 推出来的，而不是从实现推出来的，它不会“刚好”和有问题的实现一致。

测试写完后，按第 19 课的方法**先审测试**。最重要的是并发测试，它应该长成这样：

```java
/** 让所有任务在同一时刻开始，返回成功的次数。 */
private int runConcurrently(List<Callable<UserCoupon>> tasks) throws Exception {
    ExecutorService pool = Executors.newFixedThreadPool(tasks.size());
    CountDownLatch start = new CountDownLatch(1);
    List<Future<UserCoupon>> futures = new ArrayList<>();
    for (Callable<UserCoupon> task : tasks) {
        futures.add(pool.submit(() -> {
            start.await();
            return task.call();
        }));
    }
    start.countDown();
    // ……统计成功的次数，失败的必须是 BusinessException
}

@Test
void fiftyCustomersCompeteForTenCoupons() throws Exception {
    Long id = coupon(10).getId();
    List<Callable<UserCoupon>> tasks = new ArrayList<>();
    for (int i = 0; i < 50; i++) {
        String customer = "rush-" + i;
        tasks.add(() -> coupons.claim(id, customer));
    }

    int success = runConcurrently(tasks);

    assertThat(success).isEqualTo(10);
    assertThat(coupons.get(id).getClaimedCount()).isEqualTo(10);
}
```

检查这几点：

- **线程真的同时开始。** 用 `CountDownLatch` 让所有线程等在起跑线上；如果是一个接一个提交、一个接一个执行，测试测的其实是串行。
- **测试类没有 `@Transactional`。** 否则所有调用都在同一个事务里，根本没有并发。
- **断言的是成功次数，而不只是 `claimedCount`。** 下面的实验会说明为什么。
- **失败的调用是预期的业务异常。** 不是随便什么异常都算“领不到”。

### 实验：这个测试能抓住超发吗？

测试只有在实现错误时会失败，才有价值。我们故意写一个“先查再改”的错误实现，看看并发测试的反应。在 `Coupon` 里加一个方法：

```java
public void claimOne() {
    if (claimedCount >= totalCount) {
        throw new BusinessException("优惠券已领完");
    }
    claimedCount++;
}
```

在 `claim` 里用 `coupon.claimOne()` 代替条件更新。单线程的测试全部通过，并发测试失败。在我的机器上连续运行三次，50 个线程抢 10 张券的结果是：

| 次数 | 成功领取 | `claimedCount` 显示 |
| --- | --- | --- |
| 1 | 33 | 10 |
| 2 | 50 | 8 |
| 3 | 34 | 10 |

券发出去了 33 到 50 张，数据库里的计数却显示 10 张甚至更少。这是典型的**丢失更新**：多个事务读到同一个值，各自加一后写回，后写的覆盖了先写的。如果测试只断言 `claimedCount == 10`，第 1、3 次会“通过”，超发就这样溜过去了。这就是上面要求断言成功次数的原因。

这个实验你可以自己做一遍：让 agent 用“先查再改”的方式实现，运行并发测试，然后再换成条件更新。

## 第 5 步：实现

切到自动接受编辑模式（`Shift+Tab` 到 accept edits），让它实现：

```text
实现计划，让所有测试通过。不要修改刚才写的测试；如果你认为某个测试写错了，先停下来告诉我。
```

这时第 1 步配置的 hooks 开始工作：每次改完 `.java` 文件，`compile.sh` 编译一次，编译错误马上交给它；它想结束时，`verify.sh` 运行测试，测试不通过就不让它停。你不用每轮都提醒它“跑一下测试”。

实现过程中，你主要盯两件事：

1. **它有没有动测试。** 随时可以用 `git diff --stat src/test` 看一眼。CLAUDE.md 和提示词里都说了不要改，但第 19 课说过，“放宽已有测试”是最需要警惕的错误模式。
2. **它是不是在原地打转。** 同一个错误修了两三轮还没好，按第 17 课的做法：让它把进展写进 NOTES.md，`/clear`，带着更具体的提示重来。

参考实现里防超发的核心只有一条 SQL：

```java
/**
 * 在还有余量时把已领数量加一，返回受影响的行数（1 表示领到，0 表示已领完）。
 * 判断和更新在同一条 SQL 里完成，数据库的行锁保证并发时不会超发。
 */
@Modifying(clearAutomatically = true)
@Query("update Coupon c set c.claimedCount = c.claimedCount + 1 "
        + "where c.id = :id and c.claimedCount < c.totalCount")
int tryClaimOne(@Param("id") Long id);
```

领券的服务方法：

```java
@Transactional
public UserCoupon claim(Long couponId, String customerId) {
    Coupon coupon = get(couponId);
    Instant now = clock.instant();
    if (coupon.isExpired(now)) {
        throw new BusinessException("优惠券已过期");
    }
    if (userCoupons.existsByCouponIdAndCustomerId(couponId, customerId)) {
        throw new BusinessException("每人只能领取一张");
    }
    if (coupons.tryClaimOne(couponId) == 0) {
        throw new BusinessException("优惠券已领完");
    }
    try {
        return userCoupons.saveAndFlush(new UserCoupon(get(couponId), customerId, now));
    } catch (DataIntegrityViolationException e) {
        // 同一用户的并发请求都通过了查重，唯一约束拦下了后到的那个
        throw new BusinessException("每人只能领取一张");
    }
}
```

几个细节值得留意，审查时也可以拿来对照：

- 查重 `existsBy...` 只是为了给出友好的提示，真正保证“一人一张”的是唯一约束。并发时两个请求都可能通过查重，唯一约束会拦下后到的那个。
- `saveAndFlush` 让插入立即执行，唯一约束冲突在这里抛出，才能被 `catch` 转成业务异常。如果只用 `save`，异常会在事务提交时才抛出，已经在这个方法之外了。
- 插入失败时抛出的 `BusinessException` 让整个事务回滚，前面扣掉的余量也一起回滚，不会白扣。
- 条件更新绕过了 JPA 的实体缓存，`clearAutomatically = true` 让后面重新读到最新的数据。

## 第 6 步：自己验证

测试全部通过之后，按第 19 课的要求**自己运行一次**，不要只相信它贴出来的输出：

```sh
mvn test
mvn spring-boot:run
```

另开一个终端，用 curl 走一遍完整流程（`validUntil` 用 GNU date 生成一天后的时间，macOS 上改成 `date -u -v+1d +%Y-%m-%dT%H:%M:%SZ`）：

```sh
VU=$(date -u -d '+1 day' +%Y-%m-%dT%H:%M:%SZ)

# 创建一张满 300 减 50 的券
curl -s -X POST localhost:8080/api/coupons -H 'Content-Type: application/json' \
  -d "{\"name\":\"满300减50\",\"threshold\":300,\"discount\":50,\"totalCount\":100,\"validUntil\":\"$VU\"}"

# c-1 领券，再领一次应该是 409
curl -s -X POST localhost:8080/api/coupons/1/claim -H 'Content-Type: application/json' -d '{"customerId":"c-1"}'
curl -s -X POST localhost:8080/api/coupons/1/claim -H 'Content-Type: application/json' -d '{"customerId":"c-1"}'
```

## 第 7 步：审查

`/clear` 或者另开一个终端启动新会话，让它审查，按第 19 课“写和审分开”的做法：

```text
审查当前分支相对于第一次提交的全部改动，对照 @SPEC.md 和 @CLAUDE.md，只报告问题，不要修改。
特别检查：并发下是否会超发或重复领取；事务边界；金额计算；时间是否都来自 Clock；已有测试是否被修改。
```

也可以直接运行 `/review`。然后你自己按第 19 课的清单过一遍。针对这个功能，下面几个问题要能回答出来：

- 两个请求同时领最后一张券，代码的哪一行保证只有一个成功？
- 同一个用户同时发两个领券请求，哪一层拦下第二个？
- 下单时用券失败，订单会不会已经被保存了？
- 取消订单退券，和支付并发发生时会怎样？（参考实现没有处理这种情况，订单状态检查和退券在同一个事务里，但没有加锁。它是不是一个需要处理的问题，取决于你们的业务。这类问题适合写进下一轮的需求，而不是让 agent 现在顺手改掉。）

## 第 8 步：提交

让它提交，并写一份 PR 描述：

```text
提交这些改动，提交信息用英文，一句话概括。然后按以下结构写一份 PR 描述到 PR.md：
做了什么、关键设计（尤其是防超发的方案和理由）、测试覆盖、没有做的事情。
```

如果项目在 GitHub 上并且装了 `gh`，可以让它直接 `gh pr create`。注意第 18 课的 settings.json 里 deny 了 `git push`，推送这一步要你自己来做，或者在这个项目里有意识地放开。

PR 描述里最有价值的是“关键设计”和“没有做的事情”。审查你 PR 的同事不一定读过 SPEC.md，他需要知道为什么用条件更新，以及哪些情况是有意不处理的。

## 参考实现

参考实现是一个补丁，包含 CLAUDE.md、SPEC.md 和全部代码，共 27 个测试。在你自己的实现之外，另开一个分支应用它：

```sh
cd ~/shop-api
git stash -u                     # 如果有没提交的改动，先收起来
git switch -c reference <第一次提交的 hash>
curl -LO https://windery.github.io/courses/ai-dev/code/coupon-reference.patch
git apply coupon-reference.patch
mvn test
```

也可以[直接在浏览器里查看补丁](/courses/ai-dev/code/coupon-reference.patch)。

然后用 `git diff --stat reference 你的分支` 对比两边的改动范围，再挑几个关键文件逐个对比。参考实现不是唯一正确的写法，比如用乐观锁也完全可以。对比的重点是：你的版本有没有漏掉某条规则、某个测试，以及两边在设计上的取舍有什么不同。

## 小结

- 一个功能的完整交付是：配置、需求、计划、测试、实现、验证、审查、提交。每一步都有你必须做的判断。
- 把“不能超发”这样的要求写成可以运行的验收标准，agent 才有明确的完成条件。
- 问方案时让它比较多种做法，而不是问“这样可以吗”。
- 先写测试，再用一个故意错误的实现确认测试真的能发现问题。
- 并发测试要让线程同时开始、不加 `@Transactional`、断言真正关心的结果。
- 只在这个项目里才知道的经验，比如 `@Transactional` 测试掩盖懒加载问题，及时写进 CLAUDE.md。

## 动手练习

1. 完成整个流程，在 NOTES.md 里记录每一步的时间、你的纠正次数，以及你认为它做得好和做得不好的地方。
2. 让 agent 用乐观锁（`@Version` 加重试）重新实现防超发，在同一个并发测试下对比两种实现，看一看 50 个线程中有多少次发生了重试。
3. 扩展需求：券增加“开始领取时间” `validFrom`。按本课的流程走一遍，这次试着把第 2 到第 5 步放在同一个会话里，对比上下文的占用和效果。
4. （可选，需要 Docker）把测试数据库从 H2 换成 Testcontainers 启动的 PostgreSQL 或 MySQL，确认并发测试在真实数据库上仍然通过。
