用 Claude Code 一段时间后，很多人会有这种体验：刚开始它又快又准，聊了一两个小时之后，它开始忘记早先说过的约定，反复犯同一个错误，越纠正越乱。

这不是错觉。第 5 课讲过，上下文越长，模型越难关注到其中的每一部分；第 10 课讲过，压缩是有损的。官方最佳实践里有一句话：**上下文窗口是最需要管理的资源。** 这一课讲的就是怎么管理它。

## 会话里都有什么

先回忆一下第 13 课 `/context` 的输出。一个会话的上下文里有：

- **固定部分**：系统提示、工具定义、CLAUDE.md、skills 列表。每个会话都一样，而且会被缓存。
- **增长部分**：你的每一条消息、它的每一次回复、读过的每个文件、跑过的每条命令的输出。

增长部分里，真正对当前任务有用的往往只占一小部分。一次失败的尝试、一段已经被推翻的讨论、三个和当前任务无关的文件，都还在里面，占用空间，分散注意力。

## 六种操作，各管一种情况

| 情况 | 操作 | 效果 |
| --- | --- | --- |
| 开始一个和之前无关的任务 | `/clear` | 清空对话，从干净的上下文开始 |
| 同一个任务做了很久，上下文快满 | `/compact <重点>` | 把对话压缩成摘要，按你指定的重点保留信息 |
| 方向走错了，想退回去重来 | 按两次 `Esc` 或 `/rewind` | 把对话和代码一起回退到之前的某一步 |
| 想试另一种做法，但不想丢掉现在的进展 | `/branch` | 从当前位置分出一个新会话，原来的会话保留 |
| 临时问一个和任务无关的小问题 | `/btw <问题>` | 回答不进入对话历史，不占用上下文 |
| 明天接着做 | `/rename` 起个名字，之后 `claude --continue` 或 `--resume` | 恢复之前的会话 |

### /clear：比你想的更常用

官方最佳实践给了一个很具体的判断标准：**在同一个问题上纠正了它两次以上，就该 `/clear` 了。** 这时上下文里塞满了失败的尝试，新的纠正只是又多了一条。更好的做法是清空，然后把你从失败中学到的东西写进一个更具体的新提示词里。

清空之前，如果有值得保留的进展，让它先写下来：

```text
把目前的进展写到 NOTES.md：已经确认的事实、改过的文件、试过但失败的方法及原因、下一步要做什么。
```

然后 `/clear`，在新会话里说“读一下 @NOTES.md，继续”。这就是第 10 课讲的“结构化笔记”：由你决定什么值得保留，比自动压缩更可控。

### /compact：告诉它什么重要

自动压缩会在上下文快满时触发（第 10 课的 MiniAgent 也是这样做的），但它不知道哪些信息对你重要。手动压缩时可以指定重点：

```text
/compact 保留所有修改过的文件列表、测试命令，以及关于会员折扣计算顺序的决定
```

也可以在 CLAUDE.md 里写一节压缩说明，让每次压缩（包括自动压缩）都遵守：

```markdown
# Compact Instructions
压缩时始终保留：修改过的文件列表、运行测试的命令、用户明确做出的业务决定。
```

压缩之后，项目根目录的 CLAUDE.md、自动记忆和计划模式下写的计划会从磁盘重新注入，最近修改过的几个文件会被重新读取，调用过的 skills 也会在一定额度内重新加载。所以写在根目录 CLAUDE.md 里的约定不会因为压缩而丢失；而子目录里的 CLAUDE.md、带 `paths` 的规则是在读到相关文件时才加载进对话的，会随对话一起被总结掉。这也是第 10 课的结论：长期有效的约定要写进项目记忆，而不是只在对话里说一次。

`/rewind` 的菜单里还有一个更精细的选项：选中某条消息，然后选择“从这里开始总结”或“总结到这里为止”，只压缩一部分对话。

### /rewind：检查点

每次你发送一条消息开始新的一轮，Claude Code 都会创建一个检查点。`/rewind` 可以选择只恢复对话、只恢复代码，或者两者都恢复。

这改变了试错的成本。与其花很多轮对话去说服它不要用某种方案，不如让它先试，不行就回退。但要记住：检查点只记录通过编辑工具做的文件修改，**Bash 命令造成的改动（比如删除文件、修改数据库）不会被记录**。它不能替代 git。

### /branch 和恢复会话

`/branch` 从当前位置复制出一个新会话，你可以在里面尝试另一种做法，原来的会话保持不变，用 `/resume` 可以回去。命令行里的 `--fork-session` 也是同样的效果。

会话会保存在本地，关掉终端也不会丢。用 `/rename` 给会话起一个有意义的名字，比如 `member-discount`，之后用 `claude --resume` 从列表里挑，或者用 `claude --continue` 直接接上最近的一个。官方建议**把会话当成分支来用**：每个工作流有自己的会话，各自保持独立的上下文。

### /btw：不留痕迹的旁支问题

任务做到一半，你突然想问“Java 的 `BigDecimal.setScale` 和 `round` 有什么区别”。直接问，这段问答就会永远留在这个会话的上下文里。用 `/btw` 问，回答不会进入对话历史。

## 一个判断流程

每次开始新任务、或者感觉它“变笨了”的时候，问自己几个问题：

1. **这是一个新任务吗？** 是，就 `/clear`。
2. **它是不是在同一个问题上犯了两次以上的错？** 是，就让它写下进展，然后 `/clear`，带着更好的提示词重来。
3. **刚才那几步是不是走错了方向？** 是，就 `/rewind` 回到走错之前。
4. **任务还没完，但 `/context` 显示上下文已经很满？** 先 `/compact` 并指定重点；或者让它写下进展，然后 `/clear`。
5. **都不是？** 继续。

## 动手

在 order-lab 里做下面几个实验。

1. **看清空的效果。** 让它完成一个小任务（比如“给 `OrderService` 增加一个按客户查询订单的方法，并写测试”）。完成后运行 `/context` 记下消息部分的大小，然后 `/clear`，再运行一次 `/context`。
2. **带重点的压缩。** 让它探索整个项目（“详细讲解这个项目的每一个类”），然后运行 `/compact 只保留和订单状态流转有关的信息`。压缩后问它“DiscountPolicy 的满减规则是什么”，看它是记得、需要重新读文件，还是答错了。
3. **回退。** 让它“把 `InMemoryOrderRepository` 改成用 `TreeMap` 存储”。完成后按两次 `Esc`，选择这条消息之前的检查点，分别试一下“只恢复代码”和“恢复代码和对话”，用 `git diff` 和继续提问来确认效果。
4. **恢复会话。** 用 `/rename lab-17` 命名当前会话，退出 Claude Code，再用 `claude --resume` 找到它并接着对话。

## 小结

- 上下文是最需要管理的资源：越长越贵，越长越不准。
- 新任务用 `/clear`；同一问题纠正两次以上，写下进展后 `/clear` 重来。
- `/compact` 时指定重点；长期有效的约定写进 CLAUDE.md，压缩不会丢失。
- `/rewind` 让试错变便宜，但它只覆盖编辑工具的改动，不能替代 git。
- 用 `/branch` 尝试另一种做法，用 `/rename` 和 `--resume` 把会话当成分支管理，用 `/btw` 问旁支问题。
