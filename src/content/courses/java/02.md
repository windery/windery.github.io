上一篇停在 JVM 初始化完成、准备加载主类的那一刻。这一篇沿着一个类从 `.class` 文件到可以执行的过程往下走，回答两类问题。

第一类是“类”本身：它在什么时候被加载和初始化，由谁加载，两个全名相同的类为什么可能不相等。线上那些看起来像玄学的 `ClassCastException: X cannot be cast to X`、`NoClassDefFoundError`、热部署后的内存泄漏，根源都在这里。

第二类是 `.class` 文件的内容：javac 替你写了哪些你没写的代码。自动装箱、字符串拼接、增强 for、字符串 switch 都是语法糖，用 `javap` 一看就知道它们的真实成本。

本篇所有示例都放在上一篇建好的 `~/java-depth` 目录中，用 `javac -d out` 编译、`java -cp out` 运行。

## 一个类的生命周期

JVM 规范第 5 章把一个类从无到有分成三个阶段：

| 阶段 | 做什么 | 常见异常 |
| --- | --- | --- |
| 加载（Loading） | 类加载器按名字找到字节（通常来自 `.class` 文件或 jar），交给 JVM 解析，生成 `Class` 对象 | `ClassNotFoundException`、`NoClassDefFoundError` |
| 链接（Linking） | 验证字节码合法；为静态字段分配内存并赋零值（准备）；把符号引用解析为直接引用（解析，HotSpot 在首次使用时才做） | `VerifyError`、`NoSuchMethodError`、`IncompatibleClassChangeError` |
| 初始化（Initialization） | 执行静态初始化器 `<clinit>`：静态字段的赋值语句和 `static {}` 块，按源码顺序 | `ExceptionInInitializerError` |

前两个阶段的时机由 JVM 实现决定，可以很早；**初始化的时机则由规范严格规定**：只有在“首次主动使用”时才执行，例如创建实例、调用静态方法、读写非常量的静态字段、反射调用、初始化子类之前先初始化父类，以及 main 所在的主类。

### 实验一：初始化到底什么时候发生

```java
// InitOrder.java
public class InitOrder {
    static class Config {
        static final String NAME = "orders";           // 编译期常量
        static final long STARTED = System.nanoTime();  // 运行期才能算出的值
        static { System.out.println("Config 初始化"); }
    }

    public static void main(String[] args) {
        System.out.println("1. 读取 NAME: " + Config.NAME);
        System.out.println("2. 声明数组: " + new Config[3].length);
        System.out.println("3. 读取 STARTED 之前");
        long t = Config.STARTED;
        System.out.println("4. 读取 STARTED 之后");
    }
}
```

先预测 “Config 初始化” 会出现在哪一行之后，再运行：

```sh
javac -d out InitOrder.java
java -cp out InitOrder
```

```text
1. 读取 NAME: orders
2. 声明数组: 3
3. 读取 STARTED 之前
Config 初始化
4. 读取 STARTED 之后
```

- `Config.NAME` 是编译期常量（`static final` 加上常量表达式）。javac 直接把字符串 `"orders"` 内联到了 main 的字节码里，运行时根本不会访问 Config 类，自然不会触发初始化。
- `new Config[3]` 创建的是数组类 `[LInitOrder$Config;` 的实例，不是 Config 的实例，也不触发初始化。
- `Config.STARTED` 的值要运行时才能算出，读取它是“主动使用”，于是 `<clinit>` 在这一刻执行。

两个实际推论：

1. **修改常量后只重新编译定义它的类是不够的。** 引用方的字节码里存的是旧值，必须一起重新编译。改了公共常量、只发布一个 jar，就会出现“明明改了却不生效”。
2. **静态初始化器里抛出异常，后果比想象的严重。** 第一次失败抛出 `ExceptionInInitializerError`，之后每次使用这个类都抛 `NoClassDefFoundError: Could not initialize class ...`。线上看到后者时，要往日志前面翻，找第一次的那个异常。

## 谁来加载：三层类加载器

从 JDK 9 起，一个普通应用至少涉及三个类加载器：

| 加载器 | 在 Java 中的样子 | 负责 |
| --- | --- | --- |
| bootstrap | `null`（由 JVM 用 C++ 实现） | `java.base` 等核心模块，例如 `java.lang.String` |
| platform | `ClassLoader.getPlatformClassLoader()`，名字是 `platform` | `java.sql`、`java.net.http` 等平台模块。它取代了 JDK 8 的 extension 加载器 |
| app（system） | `ClassLoader.getSystemClassLoader()`，名字是 `app` | classpath 和 module path 上的应用类 |

验证一下。下面的程序打印自己、`java.sql.Connection` 和 `String` 各由谁加载：

```java
// Who.java
public class Who {
    public static void main(String[] args) {
        ClassLoader self = Who.class.getClassLoader();
        System.out.println(self.getClass().getName() + " / " + self.getName());
        System.out.println(java.sql.Connection.class.getClassLoader().getName());
        System.out.println(String.class.getClassLoader());
    }
}
```

```sh
javac -d out Who.java
java -cp out Who
```

```text
jdk.internal.loader.ClassLoaders$AppClassLoader / app
platform
null
```

顺便验证上一篇提到的源码启动模式。不编译，直接 `java Who.java`：

```text
com.sun.tools.javac.launcher.Main$MemoryClassLoader / null
platform
null
```

你的类变成了由 javac 启动器里一个内存加载器加载。写小脚本时这没有影响，但像本篇这样研究类加载、或者像第 03 篇用 JOL 反射读取你自己的类时，结果会不同。这就是本课程统一先 javac 再运行的原因。

### 双亲委派的原始版本

`java.lang.ClassLoader.loadClass` 的默认实现就是“双亲委派”。JDK 21 的源码（去掉了性能计数代码）：

```java
protected Class<?> loadClass(String name, boolean resolve)
    throws ClassNotFoundException
{
    synchronized (getClassLoadingLock(name)) {
        // First, check if the class has already been loaded
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // ClassNotFoundException thrown if class not found
                // from the non-null parent class loader
            }

            if (c == null) {
                // If still not found, then invoke findClass in order
                // to find the class.
                c = findClass(name);
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
}
```

三步：先查缓存，再问父加载器，父加载器找不到才调用自己的 `findClass`。自定义类加载器通常只重写 `findClass`，委派顺序保持不变。这保证了 `java.lang.String` 永远由 bootstrap 加载，应用无法用同名类冒充核心类。

### JDK 9 之后：先按模块找

内置的 platform 和 app 加载器并不直接用上面的实现，而是继承自 `jdk.internal.loader.BuiltinClassLoader`，它的 `loadClassOrNull` 多了一步：

```java
// find the candidate module for this class
LoadedModule loadedModule = findLoadedModule(cn);
if (loadedModule != null) {
    // package is in a module
    BuiltinClassLoader loader = loadedModule.loader();
    if (loader == this) {
        c = findClassInModuleOrNull(loadedModule, cn);
    } else {
        // delegate to the other loader
        c = loader.loadClassOrNull(cn);
    }
} else {
    // check parent
    if (parent != null) {
        c = parent.loadClassOrNull(cn);
    }
    // check class path
    if (c == null && hasClassPath()) {
        c = findClassOnClassPathOrNull(cn);
    }
}
```

（节选并省略了模块系统初始化检查。）它先看类名所在的**包属于哪个已定义的模块**，直接把请求交给那个模块的加载器；只有不属于任何命名模块的类（比如 classpath 上的普通应用类）才走传统的“先问父加载器”路线。所以严格地说，JDK 9 以后的内置加载器是“按模块定位，classpath 部分再委派”。对写业务代码的人来说，结论没有变：核心类只有一份。

## 类的身份：全名加上定义它的加载器

JVM 规范 §5.3 规定：运行时的一个类由**二进制名**和**定义它的加载器（defining loader）**共同确定。同一份 `.class` 文件被两个加载器各自定义，就得到两个互不相干的类型。

### 实验二：同一个文件，两个类

```java
// L02.java
import java.net.URL;
import java.net.URLClassLoader;

public class L02 {
    public static class Payload {
        public Payload() {}
    }

    public static void main(String[] args) throws Exception {
        System.out.println("String 的加载器: " + String.class.getClassLoader());
        ClassLoader app = L02.class.getClassLoader();
        System.out.println("L02 的加载器: " + app.getName());
        System.out.println("它的父加载器: " + app.getParent().getName());

        URL[] path = { L02.class.getProtectionDomain().getCodeSource().getLocation() };
        ClassLoader platform = ClassLoader.getPlatformClassLoader();
        try (var a = new URLClassLoader(path, platform);
             var b = new URLClassLoader(path, platform)) {
            Class<?> ca = a.loadClass("L02$Payload");
            Class<?> cb = b.loadClass("L02$Payload");
            System.out.println("名字相同: " + ca.getName().equals(cb.getName()));
            System.out.println("同一个类: " + (ca == cb));
            Object o = ca.getDeclaredConstructor().newInstance();
            System.out.println("instanceof Payload: " + (o instanceof Payload));
        }
    }
}
```

两个 `URLClassLoader` 指向同一个 `out` 目录，父加载器都是 platform。预测最后三行，然后运行：

```sh
javac -d out L02.java
java -cp out L02
```

```text
String 的加载器: null
L02 的加载器: app
它的父加载器: platform
名字相同: true
同一个类: false
instanceof Payload: false
```

platform 加载器在平台模块里找不到 `L02$Payload`，于是 a、b 各自从目录读取同一个文件并定义它。源码中写的 `Payload` 又是 app 加载器定义的第三个版本。加上 `-Xlog:class+load` 可以亲眼看到这个类被加载了三次：

```sh
java -Xlog:class+load -cp out L02 | grep 'L02\$Payload'
```

```text
[0.058s][info][class,load] L02$Payload source: file:.../java-depth/out/
[0.059s][info][class,load] L02$Payload source: file:.../java-depth/out/
[0.066s][info][class,load] L02$Payload source: file:.../java-depth/out/
```

如果把 `o` 强转成 `Payload`，会得到那个经典的异常。消息里写清了两边各属于哪个加载器，排查时首先看这里：

```text
java.lang.ClassCastException: class L02$Payload cannot be cast to class L02$Payload
(L02$Payload is in unnamed module of loader java.net.URLClassLoader @2a139a55;
 L02$Payload is in unnamed module of loader 'app')
```

再做一个对照：把两处 `new URLClassLoader(path, platform)` 的 `platform` 改成 `app`，重新编译运行，“同一个类”和 “instanceof Payload” 都会变成 `true`。双亲委派先问父加载器，app 在 classpath 上找到了这个类，a 和 b 拿到的都是 app 定义的那一份。

## 框架为什么要打破委派

既然委派这么好，为什么 Tomcat、Spring Boot 都要自己写加载器？因为它们要解决委派解决不了的问题：

| 场景 | 做法 | 原因 |
| --- | --- | --- |
| Tomcat 部署多个 web 应用 | 每个应用一个 `WebappClassLoader`，**先查应用自己的** `WEB-INF/classes` 和 `WEB-INF/lib`，再委派给父加载器（Java SE 核心类除外） | 两个应用可以依赖不同版本的同一个库，互不干扰 |
| JDBC、`ServiceLoader` 等 SPI | 核心库通过**线程上下文类加载器**（TCCL，`Thread.getContextClassLoader()`）加载实现类 | 接口在 platform 或 bootstrap 加载器里，实现在 classpath 上，父加载器看不到子加载器的类，只能“反向”借用 |
| Spring Boot 可执行 jar | 用自己的加载器读取 jar 里嵌套的 `BOOT-INF/lib/*.jar` | 标准 `URLClassLoader` 不支持 jar 套 jar |
| Spring Boot DevTools 热重启 | 依赖放在 base 加载器，项目代码放在可丢弃的 restart 加载器，代码一改就扔掉旧加载器、建新的 | 重新加载项目代码，又不用重新加载所有依赖 |

最后一行也是开发环境里 “`com.acme.Order cannot be cast to com.acme.Order`” 的常见来源：如果某个由 base 加载器加载的组件（例如进程内缓存）持有了旧 restart 加载器创建的对象，重启后它和新加载器里的同名类就不再相等。规则还是那一条：全名加上定义加载器。

热部署还有一个隐患：只要还有任何一个对象引用着旧加载器加载的类，整个旧加载器以及它加载的所有类都无法被 GC 回收。反复热部署后元空间不断上涨，最后报 `OutOfMemoryError: Metaspace`。常见的“钉子”是没有停止的线程、注册到 JDK 全局表里的 JDBC 驱动、`ThreadLocal`。第 04 篇讲 OOM 取证时会再遇到它。

## 实验三：启动一个 Hello World 要加载多少个类

```java
// Hello.java
public class Hello {
    public static void main(String[] args) {
        System.out.println("hi");
    }
}
```

```sh
javac -d out Hello.java
java -Xlog:class+load:file=classes.txt -cp out Hello
wc -l < classes.txt
grep -c 'shared objects file' classes.txt
```

```text
hi
444
440
```

一个只打印一行字的程序加载了 444 个类，其中 440 个标注着 `source: shared objects file`。这是 CDS（Class Data Sharing）：JDK 自带一个预先解析好的核心类归档文件，启动时直接映射进内存，省掉了逐个解析的开销。你的应用类同样可以做成 CDS 归档来加快启动（`-XX:ArchiveClassesAtExit`），这在需要快速扩容的容器环境里有实际价值。

## 字节码：编译器替你写的代码

接下来看 `.class` 文件里的内容。`javap -c -p` 把字节码反汇编成可读的指令：`-c` 显示代码，`-p` 包括 private 成员，`-v` 显示常量池等全部信息。

先建立一个最小的阅读能力。JVM 是**栈式虚拟机**：每个方法调用有一个局部变量表和一个操作数栈，指令从栈上取操作数、把结果压回栈上。记住几类指令就能读懂大半：

| 指令前缀 | 作用 | 例子 |
| --- | --- | --- |
| `iload` / `aload` / `bipush` / `ldc` | 把局部变量或常量压栈（i 是 int，a 是引用） | `aload_1` 压入第 1 号局部变量 |
| `istore` / `astore` | 把栈顶写回局部变量 | `astore_2` |
| `invokevirtual` / `invokeinterface` / `invokestatic` / `invokespecial` | 调用实例方法、接口方法、静态方法、构造器和私有方法 | `invokestatic Integer.valueOf` |
| `invokedynamic` | 第一次执行时由引导方法决定调用目标 | 字符串拼接、lambda |
| `if_icmp*` / `if_acmp*` / `ifeq` | 比较并跳转（icmp 比较 int，acmp 比较引用） | `if_acmpne 39` |
| `getstatic` / `getfield` | 读静态字段、实例字段 | `getstatic System.out` |

### 实验四：装箱与 ==

```java
// L03.java
public class L03 {
    static String label(int n) {
        return "n=" + n;
    }

    public static void main(String[] args) {
        Integer a = 127, b = 127;
        Integer c = 128, d = 128;
        System.out.println(a == b);
        System.out.println(c == d);
        System.out.println(c.equals(d));
        System.out.println(label(3));
    }
}
```

```sh
javac -d out L03.java
java -cp out L03
```

```text
true
false
true
n=3
```

用 javap 看原因：

```sh
javap -c -p -cp out L03
```

- **自动装箱就是一次 `Integer.valueOf` 调用。** 它对 -128 到 127 返回缓存中的同一个对象（上限可以用 `-XX:AutoBoxCacheMax` 调大），范围外每次新建。
- **两个 `Integer` 用 `==` 比较，编译成 `if_acmpne`，比较的是引用。** 所以 127 碰巧相等，128 不相等。`Long`、`Short` 等包装类的缓存范围也是 -128 到 127。业务代码里最常见的形式是 `map.get(a) == map.get(b)`，测试数据小的时候永远通过，上线后数值一大就出错。
- **字符串拼接不再是 `StringBuilder`。** JDK 9 起（JEP 280），`+` 编译成一条 `invokedynamic`，具体用什么策略拼接，由运行时的 `StringConcatFactory` 在第一次执行时决定。很多老文章说“javac 会把 + 优化成 StringBuilder”，那是 JDK 8 的行为。

### 实验五：增强 for 和字符串 switch

```java
// Sugar.java
import java.util.List;

class Sugar {
    static int total(List<String> list) {
        int n = 0;
        for (String s : list) n += s.length();
        return n;
    }

    static int total(String[] array) {
        int n = 0;
        for (String s : array) n += s.length();
        return n;
    }

    static int code(String method) {
        switch (method) {
            case "GET": return 1;
            case "POST": return 2;
            default: return 0;
        }
    }
}
```

```sh
javac -d out Sugar.java
javap -c -p -cp out Sugar | grep -E 'invoke|checkcast|arraylength|aaload|switch|ldc'
```

（`grep` 过滤后的结果。第一行是编译器生成的默认构造器调用父类构造器；常量池编号会因编译器版本略有不同。）

- 对 `List` 的增强 for 展开成 `iterator()`、`hasNext()`、`next()` 三个接口调用，外加一条 `checkcast String`。这条 `checkcast` 是**泛型擦除**留下的痕迹：`Iterator.next()` 在字节码层面返回 `Object`，编译器替你插入了强转。第 09 篇讲泛型时会回到这里。
- 对数组的增强 for 展开成按下标的循环（`arraylength`、`aaload`），循环本身不调用任何方法。
- 字符串 switch 编译成两次 switch：先按 `hashCode()` 跳转，再用 `equals()` 确认（防止哈希冲突），得到一个序号，最后按序号跳到对应分支。所以 `switch` 一个 `null` 字符串会在 `hashCode()` 处抛 `NullPointerException`。

这些都不是“性能问题”，现代 JIT 会把它们优化得很好。读字节码的价值在于：当一段代码的行为和你的直觉不符时，你有办法确认编译器到底生成了什么，而不是去猜，或者去相信一篇过时的博客。

## 动手练习

1. 把实验一中 `NAME` 的值改成 `"payments"`，只重新编译 `Config` 所在的源文件是做不到的（它是嵌套类）。把 `Config` 拆成单独的 `Config.java`，用 `javac -d out Config.java` 只重新编译它，再运行 `InitOrder`，看输出的 NAME 是新值还是旧值，用 `javap -c -cp out InitOrder` 解释原因。
2. 在实验二里加一行 `Payload p = (Payload) o;`，读一遍完整的异常消息。然后按正文所说把父加载器改成 app，确认三行输出都变成 true。
3. 写一个 lambda：`Runnable r = () -> System.out.println("run");`，用 `javap -c -p` 找到它编译成的 `invokedynamic` 和那个名为 `lambda$main$0` 的私有静态方法。再用 `java -Djdk.invoke.LambdaMetafactory.dumpProxyClassFiles=true -cp out 类名` 运行，JDK 21 会把运行时生成的实现类写到当前目录的 `DUMP_LAMBDA_PROXY_CLASS_FILES` 里，文件名形如 `Lam$$Lambda.0x....class`，再用 javap 看看它的 `run` 方法做了什么。

## 小结

- 类的加载和链接时机由实现决定，初始化时机由规范规定：首次主动使用。编译期常量会被内联，读取它不会触发初始化。
- 双亲委派保证核心类唯一。JDK 9 起，内置加载器先按包所属的模块定位加载器，classpath 上的类再走传统委派。
- 类的身份是“全名 + 定义加载器”。`X cannot be cast to X` 先看异常消息里的两个加载器。
- Tomcat、SPI、Spring Boot 打破委派各有原因；可丢弃的加载器如果被引用住，会造成元空间泄漏。
- `javap -c -p` 能看到语法糖的真相：装箱是 `valueOf`，`==` 比较引用，字符串拼接是 `invokedynamic`，增强 for 留下 `checkcast`。

下一篇看类实例化之后的事：一个对象在内存里到底占多少字节，以及 JIT 怎样让同一段代码越跑越快，甚至让 `new` 出来的对象根本不在堆上。
