这一篇回答两个在后端开发里经常被拍脑袋的问题。

第一个是**内存**：“一百万条记录放进本地缓存要多少内存？”很多人按字段大小相加，得到的数字往往只有真实值的五分之一。差距来自对象头、对齐填充、包装类型和引用，这些都可以精确测量。做 AI 应用时这个问题会更常见：embedding 向量、会话上下文、检索结果，都是想放在进程内缓存里的东西。

第二个是**性能**：“这里 new 一个对象会不会太浪费？”“这个方法调用会不会有开销？”答案取决于 JIT 编译器做了什么。同一段代码，刚启动时由解释器执行，热起来之后被编译成机器码，内联、逃逸分析之后，有些对象分配会被完全消除。

两个问题的共同点是：**凭直觉的答案常常是错的，而 JDK 提供了测量的工具。**

## 准备：下载 JOL

本篇的内存实验使用 OpenJDK 官方的 JOL（Java Object Layout）。它是一个小 jar，读取的是当前运行中 JVM 的真实字段偏移，不是理论推算。项目本身的用法和原理，见 [openjdk/jol 项目概览与用法](/projects/openjdk-jol/01/)。

```sh
cd ~/java-depth
mkdir -p lib
curl -fLo lib/jol-core-0.17.jar \
  https://repo1.maven.org/maven2/org/openjdk/jol/jol-core/0.17/jol-core-0.17.jar
```

用 JOL 的示例编译和运行时要带上 classpath：

```sh
javac -cp lib/jol-core-0.17.jar -d out Xxx.java
java -cp out:lib/jol-core-0.17.jar Xxx
```

Windows 上 classpath 分隔符是分号：`-cp "out;lib/jol-core-0.17.jar"`。

运行时 JOL 会先打印一两行 `# WARNING`，说明它无法动态 attach 自身或使用 Serviceability Agent。这不影响字段布局的结果，下文的输出省略了这些行。

## 一个对象由什么组成

在 64 位 HotSpot 上，一个普通对象由三部分组成：

| 部分 | 大小（JDK 21 默认） | 内容 |
| --- | --- | --- |
| mark word | 8 字节 | 哈希码、GC 分代年龄、锁状态 |
| class pointer | 4 字节（压缩类指针开启） | 指向类的元数据，在元空间里 |
| 数组长度 | 4 字节，仅数组有 | 元素个数 |
| 实例字段 | 按类型 | 字段可能被重排 |
| 对齐填充 | 补到 8 的倍数 | 对象起始地址按 8 字节对齐 |

所以普通对象头是 12 字节，数组头是 16 字节。

### 实验一：Object 和一个业务类

```java
// L04.java
import org.openjdk.jol.info.ClassLayout;

public class L04 {
    static class Order {
        boolean paid;
        long id;
        int quantity;
        String sku;
    }

    public static void main(String[] args) {
        System.out.println(ClassLayout.parseInstance(new Object()).toPrintable());
        System.out.println(ClassLayout.parseClass(Order.class).toPrintable());
    }
}
```

Order 的四个字段按声明加起来是 1 + 8 + 4 + 4 = 17 字节（引用按 4 字节算）。先猜一个 Order 实例实际占多少，字段会不会按声明顺序排。

```sh

java -cp out:lib/jol-core-0.17.jar L04
```

- `new Object()` 没有任何字段，也要 16 字节：12 字节对象头加 4 字节对齐。

## 压缩指针与 32 GB 界限

JVM 在 64 位平台上保存引用时，默认用 4 字节而不是 8 字节，这叫 compressed oops（ordinary object pointers）。因为对象按 8 字节对齐，地址的低 3 位总是 0，所以 32 位数字左移 3 位就能寻址 2<sup>32</sup> × 8 = 32 GB 的堆。

```sh
for x in 31g 32g 33g; do
  echo -n "$x: "
  java -Xmx$x -XX:+PrintFlagsFinal -version 2>/dev/null | grep ' UseCompressedOops ' | awk '{print $4}'
done
```

```text
31g: true
32g: false
33g: false
```

堆一旦达到 32 GB，压缩指针自动关闭，每个引用变成 8 字节。用 `-XX:-UseCompressedOops` 重新运行实验一，可以看到 Order 从 32 字节涨到 40 字节：

```text
 24   1            boolean Order.paid                N/A
 25   7                    (alignment/padding gap)
 32   8   java.lang.String Order.sku                 N/A
Instance size: 40 bytes
```

注意 class pointer 仍是 4 字节，因为“压缩类指针”是另一个独立的开关。实际意义是：**把堆从 31 GB 调到 33 GB，能放下的对象可能反而更少。** 需要大堆时，要么留在 31 GB 以内，要么直接上到 48 GB 以上，让多出来的空间抵消引用变大的代价。

不同大小的堆，压缩指针的模式也不同，`-Xlog:gc+init` 会显示出来：2 GB 堆是 `Enabled (32-bit)`，地址直接用不需要移位；31 GB 堆是 `Enabled (Non-zero disjoint base)`，需要加基址和移位。这些对写代码的人是透明的，了解即可。

### JDK 25：Compact Object Headers

JDK 24 的 JEP 450 以实验特性引入了 compact object headers，JDK 25 的 JEP 519 把它转为正式特性。开启 `-XX:+UseCompactObjectHeaders` 后，mark word 和 class pointer 合并进 8 字节，普通对象头从 12 字节缩到 8 字节。**这是 JDK 25 才有的特性，JDK 21 上没有这个开关。** 小对象越多的服务（缓存、消息、图结构）收益越明显，升级到 JDK 25 时值得评估。

## 实验二：估算一张缓存的真实大小

单个对象只是开始。估算缓存时，要沿着引用把整张对象图加起来。JOL 的 `GraphLayout` 就是做这件事的：

```java
// CacheFootprint.java
import java.util.HashMap;
import org.openjdk.jol.info.GraphLayout;

public class CacheFootprint {
    public static void main(String[] args) {
        var cache = new HashMap<Long, Long>();
        for (long i = 0; i < 1_000_000; i++) {
            cache.put(i + 1000, i + 1000);
        }
        System.out.println(GraphLayout.parseInstance(cache).toFootprint());
    }
}
```

key 和 value 都是 long，原始数据是 100 万 × 16 字节 = 16 MB。先估算一下，再运行：

```sh
javac -cp lib/jol-core-0.17.jar -d out CacheFootprint.java
java -cp out:lib/jol-core-0.17.jar CacheFootprint
```

```text
java.util.HashMap@2503dbd3d footprint:
     COUNT       AVG       SUM   DESCRIPTION
         1   8388624   8388624   [Ljava.util.HashMap$Node;
   2000000        24  48000000   java.lang.Long
         1        48        48   java.util.HashMap
   1000000        32  32000000   java.util.HashMap$Node
   3000002            88388672   (total)
```

88 MB，是原始数据的 5.5 倍。逐项拆开：

| 组成 | 单个大小 | 怎么算的 |
| --- | --- | --- |
| `Long` | 24 字节 | 12 字节头 + 8 字节 long，long 要 8 字节对齐，从偏移 16 开始，共 24 |
| `HashMap.Node` | 32 字节 | 12 字节头 + `int hash` 4 + key、value、next 三个引用各 4 = 28，对齐到 32 |
| 桶数组 | 约 8 MB | 100 万条按负载因子 0.75 扩容到 2<sup>21</sup> 个槽，每槽一个 4 字节引用 |

缩小它的办法，按效果排序：

1. **换成存原始类型的集合**，例如 fastutil 的 `Long2LongOpenHashMap` 或 Eclipse Collections 的 `LongLongHashMap`。它们用两个 `long[]` 存 key 和 value，没有 Node，也没有 Long，同样的数据大约 32 MB（数组按容量预留了空位）。
2. **能用 int 就不用 long，能用原始数组就不用对象列表。** 存 embedding 向量时，`float[]` 比 `List<Float>` 小得多：每个元素 4 字节，后者是 4 字节引用加 16 字节的 Float 对象。
3. **升级到 JDK 25 并开启 compact object headers**，每个对象省 4 字节。对这张表来说是 300 万个对象，省下约 12 MB。

`GraphLayout` 统计的是“从这个对象出发能到达的所有对象”，被其他地方共享的对象也会算进来。它回答“这张图有多大”，不完全等于“删掉它能释放多少”。后者要用堆转储工具算 retained size，第 04 篇会讲。

## JIT：同一段代码为什么越跑越快

接下来是性能。HotSpot 执行 Java 代码有三种方式：解释器逐条执行字节码，C1 编译器快速编译出一般质量的机器码，C2 编译器根据运行数据（profile）做激进优化。JDK 8 起默认开启**分层编译**（tiered compilation），把它们组织成 5 个层级：

| 层级 | 执行方式 | 说明 |
| --- | --- | --- |
| 0 | 解释执行 | 起点，同时累计调用次数和循环回跳次数 |
| 1 | C1，无 profile | 简单方法（如 getter）直接编译到这一层就够了 |
| 2 | C1，有限 profile | C2 队列太长时的过渡 |
| 3 | C1，完整 profile | 最常见的中间状态：编译后的代码继续收集类型和分支数据 |
| 4 | C2 | 根据第 3 层收集的 profile 做激进优化 |

一个方法从 0 升到 3，再升到 4，由计数器阈值决定（例如 `Tier3InvocationThreshold=200`、`Tier4InvocationThreshold=5000`，实际判断还会结合循环次数和编译队列长度）。正在运行的长循环也能中途切换到编译后的代码，这叫 **OSR**（on-stack replacement）。

### 实验三：看着代码被编译

```java
// L05.java
import java.lang.management.ManagementFactory;

public class L05 {
    record Point(int x, int y) {}

    static int distance(int x, int y) {
        Point p = new Point(x, y);
        return Math.abs(p.x()) + Math.abs(p.y());
    }

    static long run(int times) {
        long sum = 0;
        for (int i = 0; i < times; i++) {
            sum += distance(i, -i);
        }
        return sum;
    }

    public static void main(String[] args) {
        var threads = (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
        long tid = Thread.currentThread().threadId();
        for (int round = 1; round <= 3; round++) {
            long before = threads.getThreadAllocatedBytes(tid);
            long sum = run(10_000_000);
            long bytes = threads.getThreadAllocatedBytes(tid) - before;
            System.out.printf("第 %d 轮: 每次调用约 %.1f 字节 (sum=%d)%n",
                    round, bytes / 10_000_000.0, sum);
        }
    }
}
```

先用 `-XX:+PrintCompilation` 看编译过程：

```sh
javac -d out L05.java
java -XX:+PrintCompilation -cp out L05 | grep -E 'L05'
```

```text
59   78       1       L05$Point::x (5 bytes)
59   79       1       L05$Point::y (5 bytes)
60   82       3       L05::distance (26 bytes)
60   83       3       L05$Point::<init> (15 bytes)
60   84       4       L05::distance (26 bytes)
61   82       3       L05::distance (26 bytes)   made not entrant
62   85 %     3       L05::run @ 4 (27 bytes)
63   86       3       L05::run (27 bytes)
63   87 %     4       L05::run @ 4 (27 bytes)
66   85 %     3       L05::run @ 4 (27 bytes)   made not entrant
...
```

（节选。）每列依次是：启动后的毫秒数、编译任务编号、标记、层级、方法名。

- `Point::x` 和 `Point::y` 是简单访问器，直接编译到第 1 层。
- `distance` 先到第 3 层，1 毫秒后又被 C2 编译到第 4 层；随后第 3 层的旧版本被标记为 `made not entrant`，新的调用不再进入它。
- 带 `%` 的是 OSR 编译，`@ 4` 表示从字节码偏移 4（循环开头）切入。`run` 只被调用了 3 次，远没到调用次数阈值，但它的循环跑了上千万次，所以通过 OSR 在第一轮里就换上了编译后的代码。

整个程序启动后 60 毫秒左右，热点代码就已经是 C2 编译的版本了。也就是说，**任何不做预热的性能测量，测到的主要是解释器和 C1。**

`made not entrant` 也可能来自**去优化**（deoptimization）：C2 基于 profile 做了乐观假设（例如“这个接口只有一个实现”），后来假设不成立（加载了第二个实现类），已编译的代码就作废，退回解释执行再重新编译。线上服务偶尔出现的性能抖动，有时就是这个原因。

## 内联与逃逸分析

C2 最重要的优化是**内联**：把被调用方法的代码直接展开到调用处。它不只是省掉了一次调用，更重要的是让编译器能在更大的范围里分析代码。默认情况下，字节码不超过 35 字节的方法（`MaxInlineSize`）总会被考虑内联，热点方法可以放宽到 325 字节（`FreqInlineSize`）。

内联之后，编译器才能做**逃逸分析**（escape analysis）：判断一个对象有没有“逃出”当前编译的代码范围，即有没有被存进字段、被返回、被传给没能内联的方法。如果没有逃逸，C2 可以做**标量替换**（scalar replacement）：把对象拆成几个局部变量，根本不在堆上分配。

### 实验四：消失的对象

还是 L05。`distance` 每次调用都 new 一个 Point，按前面学的规则，Point 是 12 字节头加两个 int，对齐后 24 字节。程序用 `getThreadAllocatedBytes` 统计当前线程在堆上分配了多少字节。先预测每次调用分配多少，再运行：

```sh
java -cp out L05
```

```text
第 1 轮: 每次调用约 0.0 字节 (sum=99999990000000)
第 2 轮: 每次调用约 0.0 字节 (sum=99999990000000)
第 3 轮: 每次调用约 0.0 字节 (sum=99999990000000)
```

（第 1 轮偶尔会显示 0.1，那是编译完成之前的少量分配。）

3000 万次 new，几乎没有在堆上分配任何东西。`distance` 被内联进 `run` 的循环，`Point` 的构造器和访问器也被内联，C2 看到 p 从未离开循环体，于是把它拆成了 x、y 两个局部变量。

逐个关掉前提条件，做对照实验：

```sh
java -XX:-DoEscapeAnalysis -cp out L05   # 关闭逃逸分析
java -XX:-Inline -cp out L05             # 关闭内联
java -XX:TieredStopAtLevel=1 -cp out L05 # 只用 C1，不用 C2
java -Xint -cp out L05                   # 只用解释器（会慢很多）
```

四种情况的输出都是每次调用稳定 24.0 字节，正好是一个 Point 的大小：

```text
第 1 轮: 每次调用约 24.0 字节 (sum=99999990000000)
第 2 轮: 每次调用约 24.0 字节 (sum=99999990000000)
第 3 轮: 每次调用约 24.0 字节 (sum=99999990000000)
```

`-XX:-Inline` 这一组最能说明问题：逃逸分析本身是开着的，但构造器和访问器没有内联，`p` 被当作参数传给了一个编译器“看不进去”的方法，只能假设它逃逸了。C1 则根本不做逃逸分析。

最后做一个反例：在 `distance` 里把 Point 存进一个静态列表（`static final List<Point> KEEP = new ArrayList<>();`，然后 `KEEP.add(p);`）。对象逃出了方法，不管开不开逃逸分析都必须在堆上分配，实测每次调用 32 到 40 字节（Point 本身 24 字节，加上 ArrayList 扩容的开销）。

这个实验的结论有两面：

- **小的临时对象往往很便宜。** 不要为了“省一次 new”把代码写得难读。record、`Optional`、迭代器这类短命对象，在热点路径上常常会被消除。
- **但前提很脆弱。** 方法太大没被内联、调用点是多态的、对象被放进集合或字段，优化就会失效。是否真的消除了分配，要像本例一样测量。

## 测量的正确姿势

把这一篇的两部分放在一起，会发现同一个教训：

- 内存要用 JOL 测，不要按字段相加；整张对象图用 `GraphLayout`，线上用堆转储。
- 性能要在 JIT 稳定之后测，并且要防止编译器把你的测试代码优化掉。用 `System.nanoTime()` 包住一个方法调用 100 次，测到的是解释器；如果结果没有被使用，C2 还可能把整段计算当作死代码消除。

微基准的正确做法是用 JMH，它负责预热、多次 fork、防止死代码消除并给出误差范围，第 13 篇会专门讲。

## 动手练习

1. 给 Order 再加一个 `byte status` 字段，先预测它会被放在哪个偏移、实例大小变不变，再用 JOL 验证。
2. 把实验二的 `HashMap<Long, Long>` 换成 `HashMap<String, String>`，key 和 value 都是 `"user-" + i` 这样的字符串，测一下 100 万条的大小，再算算字符串部分占了多少。
3. 在 L05 的 `distance` 方法上加 `synchronized` 修饰（变成 `static synchronized`），运行看看分配量有没有变化，再用 `-XX:+PrintCompilation` 观察。想一想锁和逃逸分析之间有什么关系（提示：搜索 lock elision）。
4. 用 `-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining -XX:+PrintCompilation` 运行 L05，在输出里找到 `L05::distance` 被内联进 `run` 的那一行，看看 JIT 给出的原因。

## 小结

- 64 位 HotSpot 上普通对象头 12 字节，数组头 16 字节，对象按 8 字节对齐，字段会被重排。17 字节的数据可能占 32 字节。
- 堆小于 32 GB 时引用占 4 字节，达到 32 GB 后变成 8 字节。JDK 25 的 compact object headers 能把对象头缩到 8 字节。
- 估算缓存要看整张对象图：一个 `HashMap<Long, Long>` 的条目约 80 字节，是原始数据的 5 倍。原始类型集合和原始数组是最有效的压缩手段。
- 分层编译让热点代码在几十毫秒内从解释执行升到 C2；OSR 让长循环中途切换；假设失效时会去优化。
- 内联是逃逸分析的前提。不逃逸的对象可以被标量替换，不在堆上分配；但这个优化很脆弱，要测量确认。

第一部分到这里结束。你现在能用 `jcmd` 看清一个 JVM 进程，用 `javap` 看清编译器生成的代码，用 JOL 和分配统计看清内存。第二部分会用这些工具进入垃圾回收：对象什么时候被认为是垃圾，GC 怎样回收它们，以及线上内存问题怎么取证。
