每天都在写 `public static void main`，但敲下 `java -jar app.jar` 之后、main 方法执行之前，JVM 已经做了很多决定：用哪种垃圾收集器、堆最大多大、启动几个编译线程。这些决定直接影响线上服务的延迟和内存，而它们大多是“自动”的，没写在任何配置文件里。

这一篇先建立一张全景图：一个 Java 进程里到底有什么，这些东西是谁、在什么时候、依据什么创建的，以及怎样用 JDK 自带的 `jcmd` 把它们一一看清。后面所有文章都会用到这里的工具和思路。

## 准备环境

本课程的示例以 **JDK 21** 为基线（文中用 JDK 21.0.11、x86_64 Linux 实测）。用到 JDK 25 才有的特性时会单独标注。先确认工具链：

```sh
java -version
javac -version
jcmd -h | head -3
```

建一个练习目录，后面每篇的代码都放在这里：

```sh
mkdir -p ~/java-depth && cd ~/java-depth
```

示例都是单个 `.java` 文件。为了让类加载器、JIT 等行为和真实项目一致，本课程统一先用 `javac` 编译到 `out` 目录，再用 `java -cp out` 运行，而不是直接 `java Foo.java`。后者（JEP 330 的源码启动模式）会在内存里编译，并用一个专门的类加载器加载你的类，第 02 篇会讲到这会带来什么差别。

## 从敲下命令到进入 main

`java` 命令本身只是一个很小的启动器（launcher，源码在 JDK 的 `src/java.base/share/native/libjli/java.c`）。它做的事情可以概括为：

1. **解析命令行**：区分启动器自己的选项（`-cp`、`-jar`）、JVM 选项（`-Xmx`、`-XX:...`）和传给 main 的参数。
2. **加载 libjvm**：找到 JVM 动态库，通过 JNI 调用 `JNI_CreateJavaVM` 创建虚拟机。
3. **JVM 初始化**：这是最重的一步。JVM 处理参数，按机器条件推导没写明的配置，初始化堆和 GC，创建一批自己的线程，加载 `java.base` 中的核心类，初始化系统类加载器。
4. **加载主类并调用 main**：启动器在名为 `main` 的线程里，通过系统类加载器加载主类，找到 `public static void main(String[])` 并调用它。

第 3 步里的“按机器条件推导”，HotSpot 称为 **ergonomics**。它是本篇的重点之一，因为同一个 jar 包在笔记本、4 核云主机和 1 核容器里，会得到完全不同的默认配置。

## 实验一：Java 代码能看到的线程

先写一个程序，打印 JVM 的几项基本信息，然后保持运行，方便用 `jcmd` 观察：

```java
// JvmTour.java
import java.lang.management.ManagementFactory;

public class JvmTour {
    public static void main(String[] args) throws InterruptedException {
        Runtime rt = Runtime.getRuntime();
        System.out.println("PID: " + ProcessHandle.current().pid());
        System.out.println("CPU 数: " + rt.availableProcessors());
        System.out.println("最大堆: " + rt.maxMemory() / 1024 / 1024 + " MB");

        var names = Thread.getAllStackTraces().keySet().stream()
                .map(Thread::getName).sorted().toList();
        System.out.println("Java 线程: " + names);

        for (var gc : ManagementFactory.getGarbageCollectorMXBeans()) {
            System.out.println("GC: " + gc.getName());
        }

        System.out.println("保持运行 120 秒，可以在另一个终端用 jcmd 观察……");
        Thread.sleep(120_000);
    }
}
```

运行之前，先猜一猜：除了 main，还会有几个线程？会看到 GC 线程吗？

```sh
javac -d out JvmTour.java
java -cp out JvmTour
```

在一台 4 核、容器内存限额约 13.4 GB 的 Linux 机器上，输出如下：

```text
PID: 869
CPU 数: 4
最大堆: 3422 MB
Java 线程: [Common-Cleaner, Finalizer, Notification Thread, Reference Handler, Signal Dispatcher, main]
GC: G1 Young Generation
GC: G1 Concurrent GC
GC: G1 Old Generation
保持运行 120 秒，可以在另一个终端用 jcmd 观察……
```

有三点值得注意：

- **main 只是六个 Java 线程之一。** 另外五个都是 daemon 线程，在 main 被调用之前就已经由 JVM 创建好了。
- **名单里没有任何 GC 线程或编译线程。** 它们确实存在，只是对 `Thread.getAllStackTraces()` 不可见，下一个实验会把它们找出来。
- **GC 的 MXBean 名字暴露了收集器。** 三个以 G1 开头的 bean 说明 JVM 自动选择了 G1。最大堆 3422 MB 也不是谁配置的，而是 ergonomics 算出来的。

如果你的输出中文显示为问号，说明终端编码不是 UTF-8。Linux 和 macOS 上设置 `LANG=zh_CN.UTF-8` 或 `LC_ALL=C.UTF-8`；Windows 上先执行 `chcp 65001`，或给 java 加 `-Dstdout.encoding=UTF-8`。

## 实验二：用 jcmd 看到全部线程

保持 JvmTour 运行，打开另一个终端。`jcmd` 不带参数时列出本机所有 Java 进程：

```sh
jcmd
```

```text
869 JvmTour
```

然后打印这个进程的全部线程栈，这里只保留每个线程的标题行：

```sh
jcmd 869 Thread.print | grep '^"'
```

```text
"main" #1 [871] prio=5 os_prio=0 cpu=83.41ms elapsed=2.40s
"Reference Handler" #9 [879] daemon prio=10 os_prio=0 cpu=0.41ms elapsed=2.38s
"Finalizer" #10 [880] daemon prio=8 os_prio=0 cpu=0.35ms elapsed=2.38s
"Signal Dispatcher" #11 [881] daemon prio=9 os_prio=0 cpu=0.36ms elapsed=2.38s
"Service Thread" #12 [882] daemon prio=9 os_prio=0 cpu=0.21ms elapsed=2.38s
"Monitor Deflation Thread" #13 [883] daemon prio=9 os_prio=0 cpu=0.55ms elapsed=2.38s
"C2 CompilerThread0" #14 [884] daemon prio=9 os_prio=0 cpu=14.80ms elapsed=2.38s
"C1 CompilerThread0" #16 [885] daemon prio=9 os_prio=0 cpu=32.25ms elapsed=2.38s
"Notification Thread" #17 [886] daemon prio=9 os_prio=0 cpu=0.14ms elapsed=2.37s
"Common-Cleaner" #18 [887] daemon prio=8 os_prio=0 cpu=0.43ms elapsed=2.37s
"Attach Listener" #19 [934] daemon prio=9 os_prio=0 cpu=0.46ms elapsed=0.10s
"VM Thread" os_prio=0 cpu=0.87ms elapsed=2.38s
"VM Periodic Task Thread" os_prio=0 cpu=2.73ms elapsed=2.39s
"G1 Service" os_prio=0 cpu=0.21ms elapsed=2.40s
"G1 Refine#0" os_prio=0 cpu=0.19ms elapsed=2.40s
"G1 Conc#0" os_prio=0 cpu=0.08ms elapsed=2.40s
"G1 Main Marker" os_prio=0 cpu=0.16ms elapsed=2.40s
"GC Thread#0" os_prio=0 cpu=0.13ms elapsed=2.40s
```

（行尾的 `tid=`、`nid=` 等字段已省略，后面排查问题时会用到 `nid`。）

一个什么都不做的程序，有 18 个线程。标题行里有 `#数字` 的是 JavaThread，即 JVM 内部表示 Java 线程的对象；没有编号的是纯粹的 VM 内部线程。方括号里的数字是操作系统的线程号。它们的职责如下：

| 线程 | 职责 |
| --- | --- |
| main | 执行你的 main 方法 |
| Reference Handler | 把 GC 发现已失效的 Reference（软、弱、虚引用）放进各自的 ReferenceQueue |
| Finalizer | 调用对象的 `finalize()`。finalization 已在 JDK 18 由 JEP 421 标记为弃用、待移除 |
| Signal Dispatcher | 处理发给 JVM 的操作系统信号，例如 `kill -3` 触发线程转储 |
| Service Thread | 处理 JVM 内部的杂项任务，例如低内存检测 |
| Monitor Deflation Thread | 回收不再使用的重量级锁（ObjectMonitor） |
| C2 / C1 CompilerThread | JIT 编译线程，第 03 篇会详细讲 |
| Notification Thread | 发送 JMX 通知，例如 GC 通知 |
| Common-Cleaner | 执行 `java.lang.ref.Cleaner` 注册的清理动作，很多堆外资源靠它释放 |
| Attach Listener | 第一次有工具（jcmd、jstack、Arthas）attach 时才创建，注意它的 elapsed 只有 0.10s |
| VM Thread | 执行需要所有 Java 线程停下来的操作（safepoint 操作），例如某些 GC 阶段、线程转储 |
| VM Periodic Task Thread | 周期性任务，例如采样 |
| G1 Service / Refine / Conc / Main Marker | G1 的后台线程：服务任务、维护 remembered set、并发标记 |
| GC Thread#0 | 执行 GC 停顿阶段工作的线程 |

C1/C2 编译线程是 JavaThread（有编号），但被刻意对 Java 代码隐藏，所以 `getAllStackTraces()` 看不到它们。

这张表的实际用处在于排查问题：线上 CPU 飙高时，`top -H -p <pid>` 能找到最忙的系统线程号，把它和 `Thread.print` 里的方括号数字（或十六进制的 `nid`）对上，就知道是业务线程、GC 线程还是编译线程在消耗 CPU。只看 Java 代码能拿到的线程列表，GC 和编译这两大嫌疑人是看不见的。

## ergonomics：没写的配置是怎么来的

继续对同一个进程提问，看 JVM 最终生效的参数：

```sh
jcmd 869 VM.flags
```

```text
-XX:CICompilerCount=3 -XX:ConcGCThreads=1 -XX:G1ConcRefinementThreads=4
-XX:G1HeapRegionSize=2097152 -XX:InitialHeapSize=224395264
-XX:MaxHeapSize=3588227072 -XX:MaxNewSize=2151677952 -XX:MinHeapSize=8388608
-XX:ReservedCodeCacheSize=251658240 -XX:+SegmentedCodeCache
-XX:+UseCompressedOops -XX:+UseG1GC ...
```

（原输出是一行，这里按宽度折行并省略了部分参数。）

启动命令里一个参数都没写，这里的每一项都是推导出来的。用 `-Xlog:gc*` 能看到推导的依据：

```sh
java -Xlog:gc*:stdout -version | head -12
```

```text
[0.006s][info][gc     ] Using G1
[0.008s][info][gc,init] CPUs: 4 total, 4 available
[0.008s][info][gc,init] Memory: 13680M
[0.008s][info][gc,init] Compressed Oops: Enabled (Zero based)
[0.008s][info][gc,init] Heap Region Size: 2M
[0.008s][info][gc,init] Heap Min Capacity: 8M
[0.008s][info][gc,init] Heap Initial Capacity: 214M
[0.008s][info][gc,init] Heap Max Capacity: 3422M
```

（节选。）可以把推导规则归纳成下表：

| 配置 | 默认推导规则 | 本机结果 |
| --- | --- | --- |
| 垃圾收集器 | 服务器级机器用 G1，否则用 Serial | G1 |
| 最大堆 `MaxHeapSize` | 可用内存 × `MaxRAMPercentage`（默认 25%） | 13680M / 4 ≈ 3422M |
| 初始堆 `InitialHeapSize` | 可用内存 × `InitialRAMPercentage`（默认 1/64） | 214M |
| G1 region 大小 | 按最大堆计算，取 1M 到 32M 之间的 2 的幂 | 2M |
| JIT 编译线程数 `CICompilerCount` | 按 CPU 数计算 | 3 |
| 压缩指针 | 最大堆小于约 32 GB 时开启 | 开启 |

### 什么是“服务器级机器”

收集器的选择看起来最“自动”，也最容易出事。它的逻辑在 HotSpot 源码里只有十几行。`src/hotspot/share/gc/shared/gcConfig.cpp`：

```cpp
void GCConfig::select_gc_ergonomically() {
  if (os::is_server_class_machine()) {
    FLAG_SET_ERGO_IF_DEFAULT(UseG1GC, true);   // 省略了条件编译
  } else {
    FLAG_SET_ERGO_IF_DEFAULT(UseSerialGC, true);
  }
}
```

`src/hotspot/share/runtime/os.cpp` 中的 `os::is_server_class_machine()` 决定什么算服务器级：

```cpp
const unsigned int server_processors          = 2;
const physical_memory_size_type server_memory = 2UL * G;
const physical_memory_size_type missing_memory = 256UL * M;
...
if ((os::active_processor_count() >= (int)server_processors) &&
    (phys_mem >= server_memory - missing_memory)) {
  ...
}
```

也就是说，**至少 2 个可用处理器，并且至少约 1792 MB（2 GB 减 256 MB）内存**，才会选 G1（代码里还有一段按物理封装数的检查，这里省略）。在容器里，“可用处理器”和“内存”读取的是 cgroup 限额，不是宿主机的配置。

### 实验三：在“小机器”上启动

不用真的找一台 1 核机器，用 `-XX:ActiveProcessorCount` 让 JVM 以为只有 1 个 CPU：

```sh
java -XX:ActiveProcessorCount=1 -Xlog:gc -version | head -1
java -Xlog:gc -version | head -1
```

```text
[0.005s][info][gc] Using Serial
[0.006s][info][gc] Using G1
```

再用 JvmTour 验证（它会等 120 秒，看完输出可以 Ctrl+C 结束）：

```sh
java -XX:ActiveProcessorCount=1 -cp out JvmTour
```

GC 那几行会变成：

```text
GC: Copy
GC: MarkSweepCompact
```

Copy 和 MarkSweepCompact 就是 Serial 收集器的新生代和老年代。Serial 只用一个线程做 GC，停顿时间随堆大小线性增长。一个在 Kubernetes 里配置成 `cpu: 1` 的 Java 服务，如果没有显式指定收集器，就是这种状态。

### 调整默认值的正确方式

容器部署时，最常见的需求是“让堆占容器内存的大部分”。与其写死 `-Xmx`，更推荐用百分比，这样调整容器规格时不用改启动参数：

```sh
java -XX:MaxRAMPercentage=75 -XshowSettings:vm -version 2>&1 | head -2
```

```text
VM settings:
    Max. Heap Size (Estimated): 10.02G
```

一份生产环境的最小启动参数清单：

```sh
java \
  -XX:+UseG1GC \
  -XX:MaxRAMPercentage=75 \
  -Xlog:gc*:file=/var/log/app/gc.log:time,uptime:filecount=5,filesize=20m \
  -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/app/ \
  -jar app.jar
```

每一项都是在回答一个问题：用什么收集器（不交给 ergonomics 猜）、堆多大、出问题时有没有 GC 日志可看、OOM 时有没有现场可查。剩下 25% 的容器内存留给堆外：元空间、线程栈、JIT 代码缓存、直接内存，第 04 篇会逐一讲。

## 实验四：看一眼堆

还是对运行中的 JvmTour：

```sh
jcmd 869 GC.heap_info
```

```text
 garbage-first heap   total 221184K, used 3121K [0x000000072a200000, 0x0000000800000000)
  region size 2048K, 1 young (2048K), 0 survivors (0K)
 Metaspace       used 885K, committed 1088K, reserved 1114112K
  class space    used 93K, committed 192K, reserved 1048576K
```

逐行读：

- 堆当前提交了 221184K（就是初始堆 214M 左右），只用了 3 MB 多。方括号里是堆的虚拟地址范围，上限 `0x800000000` 正好是 32 GB，这和压缩指针有关，第 03 篇会解释。
- G1 把堆切成 2 MB 的 region，此刻只有 1 个年轻代 region 在用。
- Metaspace 存放类的元数据，在堆外。“reserved 1114112K”只是预留的虚拟地址空间，不是真的占用了 1 GB 内存；真实占用看 committed。

## jcmd 速查

本篇用到的命令，加上几个后面会常用的：

| 命令 | 回答的问题 |
| --- | --- |
| `jcmd` | 本机有哪些 Java 进程 |
| `jcmd <pid> help` | 这个 JVM 支持哪些诊断命令 |
| `jcmd <pid> VM.version` | JDK 版本 |
| `jcmd <pid> VM.command_line` | 启动命令行与 classpath |
| `jcmd <pid> VM.flags` | 最终生效的 JVM 参数，包括推导值 |
| `jcmd <pid> VM.system_properties` | 系统属性 |
| `jcmd <pid> Thread.print` | 全部线程栈，包括 JVM 内部线程 |
| `jcmd <pid> GC.heap_info` | 堆的分区和占用 |
| `jcmd <pid> GC.class_histogram` | 每个类的实例数和字节数（会触发一次 Full GC，线上慎用） |
| `jcmd <pid> GC.heap_dump <file>` | 生成堆转储 |
| `jcmd <pid> JFR.start duration=60s filename=rec.jfr` | 录制 60 秒飞行记录 |

`jstack`、`jmap`、`jinfo` 这些老工具的功能，`jcmd` 都覆盖了，Oracle 的文档也推荐优先使用 `jcmd`。

`jcmd` 通过 attach 机制连接目标进程，要求执行者和目标进程是**同一个操作系统用户**。在容器里排查时，通常需要先 `kubectl exec` 进入容器，用与应用相同的用户执行。

## 动手练习

1. 用 `-XX:ActiveProcessorCount=2` 和 `-XX:ActiveProcessorCount=8` 分别启动 JvmTour，用 `jcmd <pid> VM.flags` 对比 `CICompilerCount`、`ConcGCThreads` 的变化，再用 `Thread.print` 数一数 `GC Thread#` 有几个。注意 JDK 21 默认按需创建 GC 线程（`UseDynamicNumberOfGCThreads`），刚启动、还没发生过 GC 时可能只有一个。
2. 用 `-XX:+UseZGC` 启动 JvmTour，看 GC MXBean 的名字和 `Thread.print` 里的 GC 线程有什么不同。
3. 找一个你手头的 Spring Boot 服务，启动后执行 `jcmd <pid> Thread.print | grep -c '^"'`，数一数它有多少线程，再按线程名前缀分组，看看哪些是 Tomcat、哪些是连接池、哪些是 JVM 自己的。

答案没有标准值，重要的是养成习惯：**对 JVM 的任何默认行为，先用工具确认，再下结论。**

## 小结

- `java` 命令是启动器，真正的工作在 JVM 初始化阶段：解析参数、推导配置、创建 GC 和编译线程、加载核心类，最后才在 main 线程中调用 main。
- 一个空程序也有十几个线程。GC、编译等内部线程对 Java 代码不可见，必须用 `jcmd Thread.print` 才能看到。
- GC 收集器、堆大小、编译线程数都由 ergonomics 按 CPU 和内存推导。少于 2 个 CPU 或内存不足约 1792 MB 时，默认收集器会退回 Serial。生产环境应显式指定。
- `jcmd` 是对运行中 JVM 提问的统一入口。

下一篇从 main 线程拿到的第一件东西说起：主类是怎样被找到、加载和初始化的，以及编译器在 `.class` 文件里替你写了哪些代码。
